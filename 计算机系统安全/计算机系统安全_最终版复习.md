# 计算机系统安全最终版复习

> 说明：本版根据 `计算机系统安全` 文件夹内的中文课件、题目文件、已有总结和实验材料整理。理论部分覆盖课程主要章节；实验部分只整理前三个实验：Set-UID 与环境变量、Shellshock、Buffer Overflow。

## 总复习主线

这门课可以用一句话串起来：

```text
攻击者利用程序对“权限、输入、内存、环境、文件状态、CPU 行为”的错误假设，
让程序执行本不该执行的操作，或泄露本不该泄露的信息。
```

### 考点地图

| 模块 | 重点对象 | 一句话记忆 |
|---|---|---|
| Linux 基础 | UID/GID、权限、sudo、capability、shadow | 权限判断主要看数字身份和访问控制规则 |
| Set-UID | RUID/EUID、system、execve、权限泄露 | Set-UID 让普通用户通过受限程序临时使用文件所有者权限 |
| 环境变量 | fork、execve、PATH、LD_PRELOAD、secure_getenv | 环境变量是用户可控输入，高权限程序不能信任 |
| Shellshock | Bash 函数导入、CGI、HTTP Header | `() { :; }; command` 让环境变量变成命令执行入口 |
| Buffer Overflow | 栈、返回地址、NOP sled、shellcode | 超长输入覆盖返回地址，劫持控制流 |
| Return-to-libc/ROP | NX 绕过、system、/bin/sh、gadget | 不执行栈代码，转而复用已有代码 |
| Format String | `%x`、`%s`、`%n` | 把用户输入当格式串会导致读写任意内存 |
| Race Condition | TOCTTOU、符号链接、原子性 | 检查和使用之间对象被替换 |
| Dirty COW | 写时复制、MAP_PRIVATE、竞态 | 利用内核 COW 竞态写只读映射 |
| Meltdown/Spectre | transient execution、cache side channel | CPU 瞬态执行留下 cache 痕迹，攻击者测时间恢复秘密 |

### 实验范围

只复习前三个实验：

1. Set-UID 特权程序与环境变量实验；
2. Shellshock 实验；
3. Buffer Overflow Server / SetUID 实验。

后续实验只在理论章节里作为概念出现，不按实验步骤复习。

### 最短背诵路径

1. 先背 `RUID/EUID`、`system/execve`、`fork/execve` 环境变量传递。
2. 再背三条攻击链：Set-UID 环境变量攻击、Shellshock CGI 攻击、Buffer Overflow 覆盖返回地址。
3. 然后背四组横向比较：`system` vs `execve`、Buffer Overflow vs Format String、Race Condition vs Dirty COW、Meltdown vs Spectre。
4. 最后背防御：最小权限、完整路径、输入长度检查、StackGuard、NX、ASLR、KPTI、barrier/retpoline。

## S01：Linux Security Basics

### 核心一句话

```text
Linux 权限判断依赖 UID/GID、文件权限、ACL、sudo 授权和 capability；root 的本质是 UID 0。
```

### 用户、组与身份

- 每个用户有唯一数字 `UID`，每个组有 `GID`。
- `/etc/passwd` 存账户基本信息，第三字段是 UID，第四字段是 GID。
- `/etc/shadow` 存密码哈希，普通用户不能直接读。
- root 特权来自 `UID = 0`，不是来自用户名 `root`。
- 一个用户可以属于多个组；访问控制可能同时考虑 owner、group、others。

### 文件权限

普通文件权限：

```text
r：读文件内容
w：修改文件内容
x：执行文件
```

目录权限：

```text
r：列目录
w：创建、删除、改名目录项
x：进入目录、访问目录下已知文件名
```

八进制权限：

```text
r = 4
w = 2
x = 1

chmod 4755 file
4    -> Set-UID 位
755  -> owner rwx，group r-x，others r-x
```

默认权限：

- 普通文件通常从 `666` 开始，再减去 `umask`；
- 目录通常从 `777` 开始，再减去 `umask`；
- `umask` 是屏蔽权限，不是添加权限。

### sudo 与 root shell

`sudo` 通过 `/etc/sudoers` 授权普通用户以特权执行指定命令。

```text
sudo command     推荐：只用特权执行单个命令
sudo -s          获取 root shell
sudo bash        获取 root shell
sudo su          切换到 root
```

不建议长期使用 root shell，因为所有后续命令都会带 root 权限，误操作风险高。

### POSIX Capabilities

capability 把 root 权限拆成更细粒度能力。

例子：

- `ping` 需要原始套接字，常见能力是 `CAP_NET_RAW`；
- Wireshark 图形界面不应整体带特权，抓包组件 `dumpcap` 才需要特权。

安全思想：

```text
不要把整个程序变成 root。
只把必要能力授予必要组件。
```

### 认证与密码哈希

- 密码不应明文存储，应存哈希。
- `salt` 用来让相同密码产生不同哈希，抵抗彩虹表。
- 字典攻击尝试常见密码；暴力攻击遍历可能密码空间。

### 大题模板

```text
Linux 内核主要根据数字 UID 判断用户身份。
UID 0 被视为超级用户，可以绕过很多普通访问控制。
用户名 root 本身没有特殊魔法。
如果其他账户 UID 也被设为 0，它同样会拥有 root 权限。
因此安全管理应保护 UID/GID、/etc/passwd、/etc/shadow 和 sudoers 配置。
```

## S02：Set-UID Programs

### 核心一句话

```text
Set-UID 程序运行时 EUID 变成程序文件所有者，普通用户因此能通过受限程序临时使用特权。
```

### RUID、EUID、SUID

| 名称 | 含义 | 作用 |
|---|---|---|
| RUID | real user ID，真实用户 ID | 表示谁启动了进程 |
| EUID | effective user ID，有效用户 ID | 内核做权限检查时主要看它 |
| SUID | saved set-user-ID | 用于程序临时降权后恢复权限 |

执行普通程序时：

```text
RUID = EUID = 启动程序的用户
```

执行 root 拥有的 Set-UID 程序时：

```text
RUID = 普通用户
EUID = root
```

### 创建 Set-UID 程序

常见步骤：

```bash
sudo chown root program
sudo chmod 4755 program
```

注意：

- `4` 表示 Set-UID 位；
- `chown` 通常会清除 Set-UID 位，所以顺序一般是先 `chown`，再 `chmod 4755`。

### Set-UID 为什么危险

Set-UID 不是直接把 root 权限交给用户，而是让用户通过程序逻辑间接使用权限。

危险来自：

1. 程序输入校验不足；
2. 调用外部命令方式不安全；
3. 信任环境变量；
4. 缓冲区溢出或格式字符串漏洞；
5. 降权不彻底；
6. 文件描述符、临时文件、符号链接造成权限泄露。

### `system()` vs `execve()`

`system(command)`：

```text
实际执行 /bin/sh -c command
会经过 shell
受 PATH、IFS、shell 元字符、环境变量影响
代码和数据容易混在一起
Set-UID 程序中危险
```

`execve(path, argv, envp)`：

```text
直接执行指定路径的程序
参数通过 argv 数组传入
环境变量由 envp 明确指定
不经过 shell
更适合特权程序
```

重点：

```text
execlp、execvp、execvpe 会像 shell 一样按 PATH 查找程序，也可能被 PATH 攻击。
更安全的做法是使用绝对路径和 execve。
```

### 权限泄露

典型场景：

1. root Set-UID 程序先以 root 权限打开敏感文件；
2. 程序调用 `setuid(getuid())` 降权；
3. 但打开的文件描述符仍然有效；
4. 后续启动 shell 或子进程时，攻击者仍可通过这个 fd 写敏感文件。

结论：

```text
降权前必须关闭不再需要的敏感文件描述符。
```

### 防御原则

- 最小权限：只在必要代码段保持特权。
- 尽早降权：完成特权操作后立即降权。
- 明确路径：不要依赖 `PATH`。
- 避免 `system()`：优先 `execve()`。
- 清理环境变量：高权限程序不要继承不可信环境。
- 检查所有输入：长度、格式、路径、文件类型都要检查。

### 大题模板

```text
Set-UID 程序运行时 EUID 会变为程序文件所有者。
如果该文件由 root 拥有，普通用户运行它时，进程的 EUID 就是 root。
内核做访问控制时主要看 EUID，因此程序可以执行特权操作。
但用户只能通过程序写好的逻辑使用这些权限。
如果程序错误地调用 system()、信任环境变量、存在缓冲区溢出或权限泄露，
攻击者就可能突破原本限制，滥用 EUID=root。
```

## S03：Environment Variables

### 核心一句话

```text
环境变量是用户可控输入；普通程序可以使用，高权限程序必须把它当作攻击面。
```

### Shell 变量与环境变量

```bash
FOO=bar        # shell 变量，只在当前 shell 内部有效
export FOO     # 导出后成为环境变量，可以传给子进程
unset FOO      # 删除变量
```

区别：

- shell 变量只属于当前 shell；
- 环境变量会被传递给子进程；
- 子进程修改自己的环境变量不会反向影响父进程。

### `fork()` 和 `execve()` 对环境变量的影响

`fork()`：

```text
子进程通常继承父进程的环境变量。
```

`execve()`：

```c
int execve(const char *pathname, char *const argv[], char *const envp[]);
```

第三个参数决定新程序的环境：

```text
execve(path, argv, NULL)      不传环境变量
execve(path, argv, environ)   继承当前环境变量
execve(path, argv, custom)    传入自定义环境变量
```

### 常见危险环境变量

| 环境变量 | 风险 |
|---|---|
| `PATH` | shell 或 `execvp` 查找命令时可能执行攻击者程序 |
| `LD_PRELOAD` | 普通程序中可预加载攻击者共享库 |
| `LD_LIBRARY_PATH` | 改变动态库搜索路径 |
| `IFS` | 影响旧 shell 分词 |
| `PWD` | 用户可控，不应当作真实当前目录 |
| `LANG`、`NLSPATH` | 某些库函数可能间接受影响 |

`PWD` 与 `getcwd()`：

```text
PWD 是环境变量，用户可伪造。
getcwd() 向内核查询当前目录，更可靠。
```

### 动态链接器防御

危险：

```text
LD_PRELOAD 和 LD_LIBRARY_PATH 可以改变程序加载的库。
```

防御：

```text
当 EUID != RUID 时，动态链接器通常会忽略危险的 LD_* 环境变量。
```

因此：

- 对普通程序，`LD_PRELOAD` 可生效；
- 对 Set-UID 程序，危险 `LD_*` 通常被过滤。

### `getenv()` 与 `secure_getenv()`

```c
char *getenv(const char *name);
char *secure_getenv(const char *name);
```

- `getenv()` 直接读取环境变量；
- `secure_getenv()` 在安全执行场景下返回 `NULL`，适合库代码避免被 Set-UID 程序间接利用。

### 环境变量攻击链

典型 `PATH` 攻击：

```text
Set-UID 程序调用 system("ls")
system 启动 /bin/sh -c "ls"
shell 按 PATH 查找 ls
攻击者把恶意 ls 放到 PATH 前面
Set-UID 程序以 root EUID 执行恶意程序
```

### 大题模板

```text
环境变量由用户控制，父进程可以传给子进程。
Set-UID 程序运行时带有高权限，如果它直接或间接依赖环境变量，
攻击者就可能通过 PATH、LD_PRELOAD、LD_LIBRARY_PATH 等改变程序行为。
即使程序没有显式调用 getenv()，system()、shell、动态链接器和库函数也可能使用环境变量。
因此特权程序应该清理环境变量，使用绝对路径，避免 system()，必要时使用 secure_getenv()。
```

## W06：Shellshock

### 核心一句话

```text
Shellshock 是 Bash 从环境变量导入函数定义时，错误执行函数定义后面命令的漏洞。
```

### 必背 payload

```bash
() { :; }; command
```

含义：

```text
() { :; }    看起来像一个 Bash 函数定义
command      漏洞 Bash 错误继续执行的攻击命令
```

### 漏洞原因

旧版 Bash 支持通过环境变量传递函数定义：

```text
环境变量值以 () { 开头
Bash 把它解释成函数定义
```

漏洞版本的问题是：

```text
Bash 导入函数定义后，没有正确停止解析，
继续执行了函数定义后面的命令。
```

### CGI 攻击链

CGI 会把 HTTP 请求信息转换成环境变量：

```text
User-Agent  -> HTTP_USER_AGENT
Referer     -> HTTP_REFERER
Cookie      -> HTTP_COOKIE
自定义 Header -> HTTP_*
```

攻击链：

```text
攻击者构造恶意 HTTP Header
Web 服务器把 Header 变成 CGI 环境变量
CGI 脚本由漏洞 Bash 解释执行
Bash 导入环境变量时触发 Shellshock
攻击者命令在服务器上执行
```

### 实验常见 curl 方式

```bash
curl -A '() { :; }; /bin/cat /etc/passwd' http://victim/cgi-bin/vul.cgi
curl -e '() { :; }; /bin/ls /' http://victim/cgi-bin/vul.cgi
curl -H 'X-Test: () { :; }; /usr/bin/id' http://victim/cgi-bin/vul.cgi
```

记忆：

- `-A` 设置 `User-Agent`；
- `-e` 设置 `Referer`；
- `-H` 设置自定义 Header。

### 可读与不可读文件

```text
/etc/passwd 通常全局可读，所以可被读取。
/etc/shadow 通常只有 root 可读，普通 Web/CGI 权限通常不能读。
```

### 反向 shell 思路

反向 shell 的本质：

```text
受害服务器主动连回攻击者，
把 shell 的 stdin/stdout/stderr 绑定到 TCP 连接。
```

为什么常用反向 shell：

- 服务器可能在 NAT 或防火墙后面；
- 入站连接可能被拦截；
- 出站连接更容易成功。

### 防御

- 升级 Bash；
- CGI 不使用 Bash 解释不可信请求；
- 过滤或限制危险环境变量；
- Web 服务使用最小权限账户运行；
- 对外部命令调用做白名单和隔离。

### 大题模板

```text
Shellshock 漏洞发生在 Bash 从环境变量导入函数定义时。
攻击者把 HTTP Header 设置成形如 () { :; }; command 的字符串。
Web 服务器运行 CGI 时，会把 Header 转换成环境变量。
如果 CGI 脚本由漏洞 Bash 执行，Bash 会把环境变量前半部分当函数定义，
又错误执行后面的 command。
因此攻击者可以通过 HTTP 请求在服务器上执行命令。
```

## S04：Buffer Overflow

### 核心一句话

```text
缓冲区溢出是程序把过长输入写入固定大小缓冲区，覆盖相邻内存，最终劫持控制流。
```

### 栈帧基础

函数调用时栈上通常包含：

```text
局部变量
保存的 frame pointer
返回地址
函数参数或调用相关数据
```

如果局部缓冲区在栈上，且程序无边界检查地复制输入：

```c
char buffer[100];
strcpy(buffer, input);
```

攻击者可让输入超过 `buffer` 长度，覆盖返回地址。

### 典型 payload

```text
NOP sled + shellcode + repeated return address
```

组成：

- `NOP sled`：提高返回地址命中概率；
- `shellcode`：攻击者希望执行的机器码；
- `return address`：覆盖原返回地址，指向 NOP sled 或 shellcode；
- `offset`：从 payload 起点到返回地址位置的距离。

### exploit.py 三个关键量

```python
content = bytearray(0x90 for i in range(517))
content[start:start + len(shellcode)] = shellcode
content[offset:offset + L] = (ret).to_bytes(L, byteorder='little')
```

必须理解：

| 变量 | 含义 |
|---|---|
| `start` | shellcode 放在 payload 中的位置 |
| `ret` | 覆盖返回地址的值，通常指向 NOP sled |
| `offset` | payload 中返回地址应该写入的位置 |
| `L` | 地址长度，32 位为 4，64 位为 8 |

### 32 位与 64 位差异

- 32 位地址长度 4 字节；
- 64 位地址长度 8 字节；
- 64 位地址常含 `0x00` 字节，遇到 `strcpy()` 这类字符串函数会提前截断；
- 64 位参数传递和调用约定也更复杂。

### 防御

| 防御 | 作用 | 局限 |
|---|---|---|
| StackGuard / Canary | 检测返回地址前的栈破坏 | 泄露 canary 后可绕过 |
| NX / DEP | 禁止栈上代码执行 | 可用 return-to-libc 或 ROP |
| ASLR | 随机化地址 | 信息泄露或暴力猜测可削弱 |
| PIE | 随机化程序代码段 | 需要编译支持 |
| 安全函数 | 限制复制长度 | 用错仍可能出问题 |

### 大题模板

```text
程序在栈上分配固定大小缓冲区，却用 strcpy 等无边界检查函数复制用户输入。
攻击者构造超长输入，使其先填满缓冲区，再覆盖保存的 frame pointer 和返回地址。
返回地址被改成指向 NOP sled 或 shellcode 的地址。
函数返回时 CPU 从被篡改的返回地址继续执行，
从而执行攻击者准备的代码或跳转到已有代码。
```

## S05：Return-to-libc / ROP

### 核心一句话

```text
当 NX 禁止执行栈上 shellcode 时，攻击者可以不注入代码，而是复用 libc 或程序已有代码。
```

### Return-to-libc

核心目标：

```text
覆盖返回地址为 system()
让 system() 的参数指向 "/bin/sh"
可选地让 system() 返回到 exit()
```

典型栈布局：

```text
返回地址 -> system()
system 返回地址 -> exit()
system 参数 -> "/bin/sh"
```

为什么能绕过 NX：

```text
NX 禁止栈上数据作为代码执行。
Return-to-libc 执行的是 libc 中已有的合法代码，不需要执行栈上的 shellcode。
```

### ROP

ROP 使用很多短代码片段：

```text
gadget = 以 ret 结尾的已有指令片段
```

攻击者把多个 gadget 地址放到栈上，函数返回后连续执行这些片段，组合成复杂行为。

### 防御

- ASLR 随机化 libc 和栈地址；
- PIE 随机化程序地址；
- StackGuard 检测返回地址附近破坏；
- CFI 限制非法控制流；
- 最小化可用 gadget。

### 大题模板

```text
NX 只能阻止攻击者执行栈上的 shellcode。
但程序和 libc 中原本就有可执行代码。
Return-to-libc 通过覆盖返回地址，让程序跳到 libc 的 system()，
再把 "/bin/sh" 的地址布置成 system 的参数。
这样攻击者没有执行注入代码，却仍能获得 shell。
ROP 进一步把多个以 ret 结尾的小片段串联起来，构造任意计算。
```

## S06：Format String Vulnerability

### 核心一句话

```text
格式字符串漏洞来自把用户输入直接作为 printf 的格式串，导致攻击者读写栈和内存。
```

危险写法：

```c
printf(user_input);
```

安全写法：

```c
printf("%s", user_input);
```

### 常见格式符

| 格式符 | 作用 | 攻击意义 |
|---|---|---|
| `%x` | 按十六进制打印栈上数据 | 泄露栈内容 |
| `%s` | 把栈上值当地址打印字符串 | 任意地址读 |
| `%n` | 把已打印字符数写入指定地址 | 任意地址写 |
| `%hn` | 写 2 字节 | 精细写入 |
| `%hhn` | 写 1 字节 | 精细写入 |

### `%n` 必背

`%n` 不打印内容，而是：

```text
把到目前为止 printf 已输出的字符数，
写入对应参数指向的地址。
```

如果攻击者能控制格式串和栈上参数，就可能把指定值写到指定地址。

### 攻击目标

常见目标：

- 返回地址；
- GOT 表项；
- 函数指针；
- 关键变量。

### Buffer Overflow vs Format String

| 项目 | Buffer Overflow | Format String |
|---|---|---|
| 根因 | 写入超过缓冲区长度 | 用户输入被当作格式串 |
| 危害 | 覆盖返回地址、控制流劫持 | 任意读、任意写 |
| 关键函数 | `strcpy`、`gets`、`sprintf` | `printf`、`fprintf`、`snprintf` |
| 典型符号 | NOP sled、shellcode、ret | `%x`、`%s`、`%n` |

### 大题模板

```text
如果程序调用 printf(user_input)，用户输入会被 printf 当成格式字符串解析。
攻击者可以用 %x 读取栈上的数据，用 %s 把栈上值当地址读取内存，
还可以用 %n 把已经输出的字符数写入指定地址。
当攻击者把目标地址布置到栈上并控制输出长度时，
就可能修改返回地址、GOT 表项或关键变量，从而劫持程序控制流。
```

## S07：Race Condition

### 核心一句话

```text
竞态条件漏洞来自检查和使用不是同一个原子操作，攻击者在中间窗口替换对象。
```

### TOCTTOU

```text
TOC：time of check，检查时刻
TOU：time of use，使用时刻
```

漏洞模式：

```c
if (access(path, W_OK) == 0) {
    fd = open(path, O_WRONLY);
    write(fd, data, len);
}
```

问题：

```text
access 检查的是 path 当时指向的文件。
open 使用的是 path 后来指向的文件。
攻击者可在两者之间把 path 替换成符号链接。
```

### 典型攻击链

```text
程序检查 /tmp/XYZ 是否可写
攻击者让 /tmp/XYZ 此刻指向普通可写文件
检查通过
攻击者迅速把 /tmp/XYZ 改成指向 /etc/passwd 的符号链接
程序以 root 权限 open/write
敏感文件被写入
```

### `stat()` vs `fstat()`

`stat(path)`：

```text
根据路径取文件状态，路径可能被替换。
```

`fstat(fd)`：

```text
根据已经打开的文件描述符取状态，绑定的是已打开对象，更可靠。
```

### 防御

- 避免先检查再使用；
- 使用 `open()` 后再 `fstat()` 验证；
- 使用 `O_NOFOLLOW` 防符号链接；
- 使用安全临时文件函数；
- 降低特权；
- 把关键操作变成原子操作。

### 大题模板

```text
竞态条件漏洞通常发生在程序先检查文件权限或状态，随后再打开或使用该文件。
如果检查和使用之间存在时间窗口，攻击者就可以把路径指向的文件替换掉，
例如替换为指向敏感文件的符号链接。
程序检查的是安全对象，但实际使用的是攻击者替换后的对象。
防御思路是避免 TOCTTOU，使用文件描述符绑定对象，并让检查和使用尽量原子化。
```

## S08：Dirty COW

### 核心一句话

```text
Dirty COW 利用 Linux 写时复制的竞态条件，让只读私有映射被错误写回底层文件。
```

### COW 正常流程

`MAP_PRIVATE` 私有映射正常语义：

```text
多个进程可共享同一物理页读取。
当某进程尝试写入时，内核复制一个私有页。
写入只影响私有副本，不应修改底层只读文件。
```

### Dirty COW 攻击思路

攻击者反复竞争两个操作：

```text
madvise()    让内核丢弃私有映射页
write 操作   通过 /proc/self/mem 写映射内存
```

竞态成功时，内核可能错误地把写入作用到底层只读文件对应页面。

### 为什么属于 Race Condition

```text
Dirty COW 的本质是内核中 COW 处理流程存在竞态。
攻击者通过大量重复操作扩大命中概率。
```

### 防御

- 更新内核补丁；
- 限制本地低权限用户；
- 监控异常写 `/proc/self/mem`；
- 避免依赖单一权限边界。

### 大题模板

```text
正常情况下，MAP_PRIVATE 映射的写入只会修改进程自己的私有副本，
不会改变底层只读文件。
Dirty COW 利用写时复制实现中的竞态窗口，
让 madvise 丢弃页面和写内存操作并发发生。
竞态成功时，内核错误地把写入应用到底层文件页，
从而让普通用户修改本不该修改的只读文件。
```

## S09：Shellcode

### 核心一句话

```text
Shellcode 是攻击 payload 中用于直接执行目标行为的小段机器码，常见目标是 execve("/bin/sh")。
```

### 32 位 Linux `execve`

系统调用：

```c
execve("/bin/sh", argv, NULL);
```

32 位 Linux 常见寄存器约定：

```text
eax = 11        系统调用号 execve
ebx = "/bin/sh" 字符串地址
ecx = argv      参数数组地址
edx = envp      环境变量数组地址，NULL
int 0x80        触发系统调用
```

### 为什么 shellcode 不能有 `0x00`

很多漏洞使用字符串函数复制 payload，例如 `strcpy()`。

```text
0x00 是 C 字符串结束符。
payload 中如果出现 0x00，复制会提前停止。
```

### 去 0 方法

- 用 `xor reg, reg` 生成 0，而不是直接写立即数 0；
- 用压栈构造字符串；
- 使用移位、加减等方式构造常量；
- 用 `jmp-call-pop` 获取字符串地址。

### `jmp-call-pop`

目的：

```text
在 shellcode 中定位内嵌字符串地址。
```

原理：

```text
call 会把下一条指令地址压栈；
下一条指令地址正好是字符串地址；
pop 取出这个地址。
```

## H01：Meltdown / Spectre

### 核心一句话

```text
Meltdown 和 Spectre 都利用 CPU 瞬态执行留下的 cache 痕迹泄露秘密。
```

### Flush+Reload

核心步骤：

```text
Flush：把探测数组从 cache 中清除。
Victim：让秘密值影响一次内存访问，例如 array[secret * 4096]。
Reload：逐个访问 array[i * 4096] 并测量时间。
判断：访问最快的 i 就是 secret。
```

为什么用 `256 * 4096`：

```text
secret 是一个字节，有 256 种可能。
4096 用来拉开不同 secret 对应地址，避免落入同一个 cache line。
```

### Meltdown

```text
利用非法访问内核地址时，异常处理前的瞬态执行。
攻击目标通常是内核/用户隔离。
异常最终会发生，但 cache 副作用已经留下。
```

攻击链：

```text
访问内核秘密地址
CPU 瞬态执行读取 secret
用 secret 访问 array[secret * 4096]
异常发生，架构状态回滚
cache 状态未完全回滚
攻击者 Reload 恢复 secret
```

防御：

```text
KPTI/KAISER：用户态页表不映射大部分内核内存。
```

### Spectre

```text
利用分支预测错误，让 CPU 瞬态执行本不该执行的路径。
攻击目标常是同一进程内的软件隔离或沙箱边界。
```

攻击链：

```text
训练分支预测器，让 CPU 预测边界检查会通过
传入越界索引
CPU 瞬态执行越界读取 secret
用 secret 改变 cache 状态
攻击者 Flush+Reload 恢复 secret
```

防御：

- 插入 speculation barrier；
- retpoline；
- 减少敏感数据同地址空间暴露；
- 浏览器降低计时精度、隔离站点；
- 微码和编译器缓解。

### Meltdown vs Spectre

| 项目 | Meltdown | Spectre |
|---|---|---|
| 利用点 | 异常处理前的瞬态执行 | 分支预测错误 |
| 典型边界 | 用户态/内核态 | 同进程内软件边界 |
| 攻击对象 | 内核数据 | 任意受害代码中的秘密 |
| 防御 | KPTI 较有效 | 无单一简单软件方案 |
| 关键共同点 | cache 侧信道 | cache 侧信道 |

### 大题模板

```text
攻击者先 flush 探测数组。
CPU 在瞬态执行中读取 secret，并用 secret 访问 array[secret * 4096]。
虽然异常或预测错误会使架构状态回滚，但 cache 状态不会完全回滚。
攻击者随后 reload 每个 array[i * 4096] 并测量时间。
访问最快的 i 对应的 cache line 已经被加载，因此 i 就是 secret。
```

## 实验 1：Set-UID 特权程序与环境变量

### 实验核心

```text
验证用户可控环境变量如何影响普通程序和 Set-UID 程序，
并理解 system、execve、动态链接器和文件描述符泄露的安全差异。
```

### 必会现象

1. `fork()` 子进程继承父进程环境变量。
2. `execve()` 第三个参数决定新程序环境变量。
3. `execve(..., NULL)` 不传环境变量。
4. `execve(..., environ)` 继承环境变量。
5. `system()` 会启动 shell，因此受 `PATH` 等环境变量影响。
6. `execve()` 直接执行指定程序，更安全。
7. `LD_PRELOAD` 对普通程序有效，对 Set-UID 程序通常被过滤。
8. Set-UID 程序降权前打开的敏感 fd 如果不关闭，会造成 capability leak。

### `myprintenv.c`

作用：

```text
fork 后让子进程或父进程打印 environ。
用于观察 fork 是否继承环境变量。
```

结论：

```text
子进程会继承父进程的环境变量。
```

### `myenv.c`

关键代码：

```c
execve("/usr/bin/env", argv, NULL);
```

结论：

```text
第三个参数为 NULL，所以新程序 /usr/bin/env 看不到原来的环境变量。
如果改成 environ，则会继承当前环境变量。
```

### `catall.c`

程序构造命令：

```c
sprintf(command, "%s %s", "/bin/cat", argv[1]);
system(command);
```

风险：

```text
system 会调用 shell。
如果 argv[1] 包含 shell 元字符，可能造成命令注入。
如果程序依赖相对命令名，也可能受 PATH 攻击。
```

更安全方式：

```c
v[0] = "/bin/cat";
v[1] = argv[1];
v[2] = NULL;
execve(v[0], v, NULL);
```

### `cap_leak.c`

攻击点：

```text
程序以 root 权限 open("/etc/zzz", O_RDWR | O_APPEND)
随后 setuid(getuid()) 降权
但 fd 没有关掉
再 execve("/bin/sh")
shell 虽然低权限运行，但仍继承了已打开的敏感 fd
```

结论：

```text
权限不只体现在 UID 上，也体现在已经打开的资源句柄上。
降权前要关闭敏感 fd。
```

### 实验大题模板

```text
Set-UID 程序运行时 EUID 可能是 root。
如果它调用 system()，shell 会使用用户可控的环境变量和命令字符串，
攻击者可能通过 PATH 或 shell 元字符控制执行结果。
execve() 更安全，因为它直接执行指定路径，并通过 argv/envp 显式传参。
此外，Set-UID 程序降权前打开的敏感文件描述符如果没有关闭，
低权限 shell 仍可能继承该 fd，造成权限泄露。
```

## 实验 2：Shellshock

### 实验核心

```text
HTTP Header -> CGI 环境变量 -> 漏洞 Bash -> 命令执行。
```

### 实验文件

- `vul.cgi`：使用 `#!/bin/bash_shellshock`，输出 Hello World；
- `getenv.cgi`：打印 CGI 进程环境变量；
- `docker-compose.yml`：受害容器 IP 为 `10.9.0.80`。

### CGI 环境变量观察

`getenv.cgi` 使用：

```bash
strings /proc/$$/environ
```

作用：

```text
打印当前 CGI 进程环境变量，用来观察 HTTP Header 如何进入环境变量。
```

### Header 到环境变量

| curl 参数 | HTTP Header | CGI 环境变量 |
|---|---|---|
| `-A` | `User-Agent` | `HTTP_USER_AGENT` |
| `-e` | `Referer` | `HTTP_REFERER` |
| `-H 'X: v'` | `X` | `HTTP_X` |

### 命令执行 payload

```bash
() { :; }; /usr/bin/id
```

含义：

```text
前半部分伪装成 Bash 函数定义；
后半部分是希望漏洞 Bash 执行的命令。
```

### 常考命令意图

```text
/bin/cat /etc/passwd     通常成功，因为 passwd 可读
/bin/cat /etc/shadow     通常失败，因为 shadow 需要 root 权限
/usr/bin/id              查看 CGI 运行身份
/bin/ls /                查看目录
```

### 反向 shell

核心解释：

```text
攻击者监听端口。
受害 CGI 执行命令，让 Bash 主动连接攻击者。
连接建立后，把 Bash 的标准输入、输出、错误重定向到网络连接。
攻击者就能远程交互式执行命令。
```

### 实验大题模板

```text
实验中的 CGI 脚本使用漏洞版本 Bash 作为解释器。
当攻击者把 User-Agent、Referer 或自定义 Header 设置成
() { :; }; command 时，Web 服务器会把 Header 变成 CGI 环境变量。
漏洞 Bash 启动时解析这些环境变量，把前半部分当函数导入，
又错误执行后面的 command。
因此攻击者能通过一次 HTTP 请求让服务器执行命令。
```

## 实验 3：Buffer Overflow

### 实验核心

```text
远程或本地输入进入 vulnerable program，
strcpy() 把超长数据复制到栈缓冲区，
覆盖返回地址后跳到 NOP sled / shellcode。
```

### Server 实验关键代码

`server-code/stack.c`：

```c
#ifndef BUF_SIZE
#define BUF_SIZE 200
#endif

int bof(char *str)
{
    char buffer[BUF_SIZE];
    strcpy(buffer, str);
    return 1;
}

int main(int argc, char **argv)
{
    char str[517];
    int length = fread(str, sizeof(char), 517, stdin);
    dummy_function(str);
}
```

关键点：

- `str` 最多读 517 字节；
- `buffer` 只有 `BUF_SIZE`；
- `strcpy(buffer, str)` 没有边界检查；
- `dummy_function()` 插入额外栈帧，使布局更贴近真实场景；
- 程序可打印 buffer 地址和 frame pointer，方便计算 offset。

### `exploit.py` 关键结构

```python
content = bytearray(0x90 for i in range(517))
content[start:start + len(shellcode)] = shellcode
content[offset:offset + L] = (ret).to_bytes(L, byteorder='little')

with open('badfile', 'wb') as f:
    f.write(content)
```

必须会解释：

```text
content：攻击输入，总长度 517。
0x90：NOP，组成 NOP sled。
shellcode：真正执行的代码。
start：shellcode 放置位置。
ret：写入返回地址的值，通常指向 NOP sled。
offset：返回地址在 payload 中的位置。
little endian：x86 地址按小端序写入。
```

### Level 思路

Level 1：

```text
给出 buffer 地址和 frame pointer。
可以直接计算返回地址位置：
offset ≈ frame pointer 到 buffer 起点距离 + 返回地址相对 frame pointer 的距离。
```

Level 2：

```text
不给准确 frame pointer。
使用 NOP sled，并在 payload 的多个可能 offset 位置重复写 ret，提高命中率。
```

64 位难点：

```text
地址为 8 字节，可能包含 0x00。
strcpy 遇到 0x00 会停止复制，所以 payload 构造更困难。
```

### 防御与实验对应

| 防御 | 实验意义 |
|---|---|
| ASLR | 地址随机化，ret 难猜 |
| StackGuard | canary 被破坏时程序终止 |
| NX | 栈不可执行，shellcode 不能直接跑 |
| 输入长度检查 | 根除 `strcpy` 越界 |

### 实验大题模板

```text
漏洞程序把 517 字节输入读入 str，再用 strcpy 复制到较小的栈缓冲区 buffer。
由于 strcpy 不检查目标缓冲区大小，攻击者输入会越过 buffer 边界，
覆盖保存的 frame pointer 和返回地址。
exploit.py 用 0x90 构造 NOP sled，把 shellcode 放入 payload，
再在 offset 处写入指向 NOP sled 的返回地址 ret。
当 bof 函数返回时，CPU 跳到攻击者指定地址，最终滑入 shellcode 执行。
```

## 横向比较与高频大题

### `system()` vs `execve()`

| 项目 | `system()` | `execve()` |
|---|---|---|
| 是否经过 shell | 是，`/bin/sh -c` | 否 |
| 参数传递 | 一个命令字符串 | 路径、argv、envp 分离 |
| 受 PATH 影响 | 可能 | 使用绝对路径时不受影响 |
| 命令注入风险 | 高 | 低 |
| Set-UID 中是否推荐 | 不推荐 | 推荐 |

### Buffer Overflow vs Format String

```text
Buffer Overflow：攻击者写太多，覆盖相邻内存。
Format String：攻击者控制格式串，让 printf 帮忙读写内存。
```

### Race Condition vs Dirty COW

```text
Race Condition：广义竞态，常见于检查和使用之间。
Dirty COW：Linux 内核写时复制实现中的特定竞态漏洞。
```

### StackGuard vs NX vs ASLR

```text
StackGuard：检测栈返回地址附近是否被改。
NX：禁止在栈上执行 shellcode。
ASLR：随机化地址，使 ret、libc、栈地址难猜。
```

### 最可能考的大题模板

#### 1. 为什么 `system()` 不适合 Set-UID 程序？

```text
system() 会调用 /bin/sh -c command。
shell 会解释元字符，并可能按 PATH 查找命令。
Set-UID 程序运行时 EUID 可能是 root，
攻击者可以通过环境变量或命令字符串影响 shell 行为。
因此 system() 会把用户可控输入和高权限执行结合起来，容易造成提权。
更安全的做法是使用绝对路径、execve()、固定 argv 和受控 envp。
```

#### 2. Shellshock 攻击如何发生？

```text
攻击者把 HTTP Header 设置成 () { :; }; command。
Web 服务器运行 CGI 时把 Header 转换成环境变量。
漏洞 Bash 启动后从环境变量导入函数定义，
却错误执行函数定义后面的 command。
因此一次 HTTP 请求就能触发服务器命令执行。
```

#### 3. 缓冲区溢出攻击如何构造？

```text
找到无边界检查的复制操作，例如 strcpy。
确定局部缓冲区到返回地址的 offset。
构造 NOP sled、shellcode 和返回地址。
把返回地址覆盖成指向 NOP sled 的 ret。
函数返回后控制流跳转到攻击者 payload。
```

#### 4. Return-to-libc 如何绕过 NX？

```text
NX 阻止栈上 shellcode 执行，但不阻止 libc 代码执行。
攻击者覆盖返回地址为 system()，
把 "/bin/sh" 地址作为参数放到栈上，
可选地把返回地址设置为 exit()。
程序返回后执行 libc 中已有 system()，从而绕过 NX。
```

#### 5. 格式字符串漏洞如何修改内存？

```text
如果程序调用 printf(user_input)，攻击者输入会被当成格式串。
%x 可以泄露栈内容，%s 可以读取地址指向的字符串，
%n 可以把已输出字符数写入指定地址。
攻击者把目标地址布置到栈上，并控制输出长度，
就能修改返回地址、GOT 表项或关键变量。
```

#### 6. Meltdown/Spectre 如何通过 cache 泄露数据？

```text
攻击者先清空探测数组 cache。
CPU 在瞬态执行中读取 secret，并访问 array[secret * 4096]。
瞬态执行结果虽然被回滚，但 cache 状态保留。
攻击者重新访问 array[i * 4096] 并测量时间。
最快的 i 表示对应 cache line 被加载过，因此 i 就是 secret。
```

### 最后压缩成 10 句话

1. root 的本质是 `UID = 0`。
2. Set-UID 程序权限检查主要看 `EUID`。
3. `system()` 经过 shell，`execve()` 不经过 shell。
4. 环境变量是用户可控输入。
5. Shellshock 的 payload 是 `() { :; }; command`。
6. Buffer Overflow 覆盖返回地址。
7. Format String 利用 `%n` 写内存。
8. Race Condition 的核心是检查和使用之间有窗口。
9. Dirty COW 是 COW 内核竞态。
10. Meltdown/Spectre 都用 cache 侧信道恢复瞬态执行中的秘密。
