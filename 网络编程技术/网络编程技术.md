第二章：
考点为TCP连接建立和终止（二选一）：
-TCP连接建立：TCP三次握手的过程，客户端和服务器的状态转换图，TCP连接建立的过程，TCP连接建立的错误处理
-TCP连接终止：TCP四次挥手的过程，客户端和服务器的状态转换图，TCP连接终止的过程，TCP连接终止的错误处理
--详细解释：
TCP连接建立的过程：
1.服务器必须准备好接受外来的连接，通过调用socket，bind和listen函数来创建一个TCP套接口，称为被动打开。
2.客户端通过调用connect函数进行主动打开。这引起客户TCP发送一个SYN分节（表示同步）。
3.服务器必须确认客户的SYN，同时自己也得发送一个SYN分节。
4.客户必须确认服务器的SYN。
TCP连接终止的过程：
1.某个应用进程先调用close，称这一段执行为主动关闭，TCP发送一个FIN分节。
2.接收到FIN的另一端执行被动关闭。
3.一段时间后，接受到文件结束符的应用进程将调用close关闭他的套接口。
4.接收到这个FIN的原发送方TCP(即执行主动关闭的那一端)对他进行确认。
套接口对：一个TCP连接的套接口对是一个定义该连接的两个端点的四元组：{源IP地址，源端口号，目的IP地址，目的端口号}。每个TCP连接都有一个唯一的套接口对。
标识每个端点的两个值通常称为一个套接口。
TCP端口号与并发服务器：并发服务器中主服务器循环派生子进程来处理每个新的连接。

通用套接口地址结构:
当作为参数传递给任一个套接口函数时，套接口地址结构总是通过指针来传递，但通过指针来取得此参数的套接口函数必须处理来自所支持的任何协议族的套接口地址结构。
int bind(int, struct sockaddr*, socklen_t);
struct sockaddr{
    uint8_t sa_len;/*结构体变量的长度*/
    sa_family_t sa_family;/*地址族，AF_xxx*/
    char sa_data[14];/*协议地址，最多14字节*/
};
#define SA struct sockaddr
struct sockaddr_in serv;
bind(sockfd, (SA*) &serv, sizeof(serv));
从应用程序开发人员的观点来看，通用的套接口地址结构的唯一用途是给执行特定于协议的地址结构的指针转换类型。
IPV6套接口地址结构体：
struct in6_addr{

};
struct sockaddr_in6{

    uint32_t sin6_flowinfo;/*IPv6流信息*/

这个结构体类型的变量占用28字节，其中前22字节与IPv4套接口地址结构体相似，后6字节包含IPv6特有的成员。
值-结果参数：
当把套接口地址结构传递给套接口函数时，总是通过指针来传递的，即传递的是一个指向结构的指针。结构的长度也作为参数来传递。
1)从进程到内核传递套接口地址结构有3个函数:
bind、connect和sendto
其中一个参数是指向套接口地址结构的指针，另一个参数是结构的大小，如:
struct sockaddr_in serv;
connect(sockfd,(SA*)&serv,sizeof(serv));
由于指针和指针所指结构的大小都传递给内核，所以从进程到内核要确切拷贝多少数据是知道的。
2)从内核到进程传递套接口地址结构有4个函数:
accept、recvfrom、getsockname和getpeername
这四个函数的两个参数是：指向套接口地址结构的指针和指向表示结构大小的整数的指针，如:
struct sockaddr_in cliaddr;
socklen_t cliaddr_len = sizeof(cliaddr);
accept(listenfd,(SA*)&cliaddr,&cliaddr_len);
为何将结构大小由整数改为指向整数的指针呢?
-当函数被调用时，结构大小是一个值(此值告诉内核该结构的大小，使内核在写此结构时不至于越界)，当函数返回时，结构大小又是一个结果(它告诉进程，内核在此结构中确切存储了多少信息)，这种参数类型叫值一结果参数。
readn,writen和readline函数：
#include "unp.h"
ssize_t readn(int filedes,void * buff,size_t nbytes);/*从文件描述符filedes中读取nbytes字节到buff中，直到读到EOF或出错*/
ssize_t writen(int filedes,const void * buff,size_t nbytes);/*从buff中写nbytes字节到文件描述符filedes中，直到写完或出错*/
ssize_t readline(int filedes,void * buff,size_t maxlen);/*从文件描述符filedes中读取一行到buff中，直到读到换行符或EOF或出错*/
它们分别读取的字节数为nbytes、nbytes和maxlen，返回值为实际读取的字节数。
第四章：
基本套接口函数：
1.socket函数：创建一个套接口，返回一个文件描述符
例：int sockfd(int family,int type,int protocol);/*family:协议族，type:套接口类型，protocol:协议.协议族的类型：AF_INET、AF_INET6等，套接口的类型：SOCK_STREAM（TCP）、SOCK_DGRAM（UDP）等*/
2.connect函数：主动打开一个连接
例：int connect(int sockfd,const struct sockaddr *serv_addr,socklen_t addrlen);/*sockfd:套接口文件描述符，serv_addr:指向服务器套接口地址结构的指针，addrlen:结构的大小，套接口地址结构必须还有服务器的IP地址和端口号，客户在调用connect前不必非得调用bind函数，因为如果必要的话内核会选择源IP地址和一个临时端口*/
-如果是TCP套接口，connect函数会执行TCP三次握手的过程来建立连接，如果连接成功则返回0，否则返回-1并设置errno，返回错误可能有以下几种情况：
1.服务器没有运行或没有监听客户连接请求
2.服务器的连接请求队列已满
3.服务器的防火墙或路由器阻止了连接请求
4.服务器的IP地址或端口号错误
5.网络故障或连接超时
-RST分节：如果服务器没有运行或没有监听客户连接请求，服务器会发送一个TCP RST分节来拒绝连接请求，客户收到这个分节后会返回ECONNREFUSED错误。有三个条件可以产生RST分节：SYN到达某个端口但此端口没有在监听的服务器，TCO想取消一个已有连接，TCO收到了一个根本不存在的连接上的分节。
3.bind函数：将套接口与一个地址绑定，分配一个本地协议地址
例：int bind(int sockfd,const struct sockaddr *my_addr,socklen_t addrlen);/*sockfd:套接口文件描述符，my_addr:指向套接口地址结构的指针，addrlen:结构的大小，套接口地址结构必须包含服务器的IP地址和端口号，对于TCP来说，调用函数bind可以指定一个端口号，可以指定一个IP地址，可以都指定，也可以一个不指定*/
-如果调用bind函数时没有指定IP地址，内核会自动选择一个IP地址来绑定套接口，这个IP地址是服务器的一个有效IP地址，客户可以通过这个IP地址来连接服务器。
-当服务器启动时要捆绑众所周知的端口
-进程可以把一个特定的IP地址捆绑到他的套接口上，但此IP地址必须是主机的一个接口。
-如果TCP服务器不把IP地址捆绑到套接口上，内核会把客户所发的SYN所在分组的目的IP地址作为服务器源IP地址来捆绑套接口，这样客户就可以通过这个IP地址来连接服务器。
-若IP地址为通配地址，端口为0，内核选择IP地址和端口
-若IP地址为通配地址，端口非0，内核选择IP地址，进程指定端口
-若IP地址为本地IP地址，端口为0，进程指定IP地址，内核选择端口
-若IP地址为本地IP地址，端口非0，进程指定IP地址和端口
4.listen函数：监听连接请求
例：int listen(int sockfd,int backlog);/*sockfd:套接口文件描述符，backlog:连接请求队列的最大长度，服务器调用listen函数来监听连接请求，backlog参数指定了连接请求队列的最大长度即最大连接个数，如果连接请求队列已满，服务器会拒绝新的连接请求，返回ECONNREFUSED错误*/
-仅被TCP套接口使用，且它只做了两件事：1.当函数socket创建一个套接口时，他被假设为一个主动套接口，也就是说，他是一个将调用connect发卡连接的客户套接口，函数listen将未连接的套接口转换成被动套接口，指示内核应该接受指向此套接口的连接请求；2.指定连接请求队列的最大长度（第二个参数）
-为了理解参数backlog的含义，我们必须明白对于给定的监听套接口，内核心需要维护两个队列：已完成连接队列（三次握手完成但未被accepe取走），未完成连接队列（两次握手队列），两队列之和不超过backlog参数指定的值。
-backlog的值应该设为5或更大，backlog的值越大，服务器能够同时处理的连接请求就越多，但过大的值可能会浪费系统资源。一个方法是假设一个缺省值，但允许命令行选项或者环境变量来覆盖这个缺省值。当指定的值比内核所支持的值要大时，也不受影响，因为内核能把所给的值改为内核所支持的最大值。
5.accept函数：接受连接请求，由TCP服务器调用，从已完成连接队列头返回下一个已完成连接，若已完成连接队列为空，则进程睡眠（假定套接口为缺省的阻塞方式）
例：int accept(int sockfd,struct sockaddr *cliaddr,socklen_t *addrlen);/*sockfd:监听套接口文件描述符，cliaddr:指向套接口地址结构的指针，addrlen:指向表示结构大小的整数的指针，后两个参数用来返回连接对方进程的协议地址。addrlen是值结果参数，调用前，我们将由*addlen所指的整数值置为由cliaddr所指的套接口地址结构的长度，返回时，此整数值即为由内核存在此套接口地址结构内的准确字节数*/
-如果函数accept成功，则返回一个内核自动生成的一个新的描述字代表与客户的TCP连接，当我们讨论函数accept时，我们常把它的第一个参数称为监听套接口描述字（由函数socket生成的描述字，用作函数bind和listen的第一个参数），把它的返回值称为已连接套接口描述字。
并发服务器：
例：
#include<unistd.h>
pid_t fork(void);/*创建一个子进程，返回值为子进程ID，父进程返回子进程ID，子进程返回0，出错返回-1*/
-fork在子进程返回0而不是父进程ID，原因是子进程只有一个父进程，它总可以调用getppid来得到;而父进程有许多子进程，它没有办法来得到各子进程的ID。如果父进程想跟踪所有子进程的ID，它必须记住fork的返回值。
fork的两个典型的应用：
-一个进程可为自己创建一个拷贝，这样，当一个拷贝处理一个操作时，其他的拷贝可以执行其他的任务。这是非常典型的网络服务器。
-一个进程想执行其他的程序，由于创建新进程的唯一方法是调用fork，进程首先调用fork来生成一个拷贝，然后其中一个拷贝(通常为子进程)调用exec来代替自己去执行新程序。
例：
pid_t pid;
int listenfd, connfd;
listenfd = Socket( ... );
/* fill in sockaddr_in{) with server's well-known port*/
Bind(listenfd, ... );
Listen(listenfd, LISTENQ);
for (;;)
{
    connfd = Accept (listenfd, .. );/ * probably blocks */
    if( (pid =Fork()) == 0){
        Close(listenfd); /* child closes listening socket，子进程不用监听 */
        doit(connfd);/*process the request，父进程不用通信*/
        Close(connfd);/* done with this client*/
        exit(0);    /* child terminates */
    }
    Close(connfd);    /* parent closes connected socket*/
}
close函数：关闭一个套接口，释放与此套接口相关的资源
例：int close(int sockfd);/*sockfd:套接口文件描述符，close函数关闭一个套接口，释放与此套接口相关的资源，如果套接口是一个TCP连接的已连接套接口，那么close函数会执行TCP连接终止的过程来关闭连接*/
-TCP套接口的close其缺省功能是将套接口做上“已关闭”标记，并立即返回到进程。这个套接口描述字不能再为进程所用:它不能用作为函数read或write的参数，但TCP将试着发送已排队待发的任何数据，然后按正常的TCP连接终止序列进行操作。
-描述字访问计数：
当并发服务器中父进程关闭已连接套接口时，他只是将描述子的访问计数值减一。由于访问计数值仍大于零，这次close调用并不引发TCP的四分组连接终止序列。对于父进程和子进程间共享已连接套接口的并发服务器来说，这正是所期望的。
getsockname和getpeername函数：
例：
#include<sys/socket.h>
int getsockname(int sockfd, struct sockaddr *addr, socklen_t *addrlen);/*sockfd:套接口文件描述符，addr:指向套接口地址结构的指针，addrlen:指向表示结构大小的整数的指针，后两个参数用来返回套接口的协议地址。addrlen是值结果参数，调用前，我们将由*addlen所指的整数值置为由addr所指的套接口地址结构的长度，返回时，此整数值即为由内核存在此套接口地址结构内的准确字节数*/
int getpeername(int sockfd, struct sockaddr *addr, socklen_t *addrlen);/*sockfd:套接口文件描述符，addr:指向套接口地址结构的指针，addrlen:指向表示结构大小的整数的指针，后两个参数用来返回套接口的协议地址。addrlen是值结果参数，调用前，我们将由*addlen所指的整数值置为由addr所指的套接口地址结构的长度，返回时，此整数值即为由内核存在此套接口地址结构内的准确字节数*/
-这两个函数或返回与套接口关联的本地协议地址（getsockname）和与套接口关联的远程协议地址（getpeername）。
所有的客户和服务器都从调用socket开始返回一个套接口描述字。然后，户调用connect，服务器调用bind、listen和accept。套接口一般由标准的close函数关闭。
第五章：
TCP回射服务器/客户端程序：
-回射服务器程序：Scoket,Bind, Listen, Accept, Fork，str_echo,Close
-str_echo函数:Readline, writen
-回射客户端程序：Socket, Connect, Inet_pton, str_cli
-str_cli函数: Fgets, writen, Readline,Fputs
正常启动与终止：
-./tcpserv01 &
-服务器启动后，调用socket、bind、listen和accept，并阻塞于accept调用（还没有启动客户）。
-客户调用socket和connect，后者引起TCP的三路握手过程。当三路握手完成后，connect返回客户，accept返回服务器，连接建立，接着执行以下步骤：
--客户调用str_cli函数，该函数将阻塞于fgets调用，因为我们还从未输入过一行文本。
--当accept返回服务器后，服务器调用fork。由于子进程调用str_echo，此函数调用readline，它又因调用read而阻塞，等待客户送出一行。
--另一方面，服务器父进程再次调用accept阻塞，等待下一个客户连接。
至此，我们有三个进程，它们都在睡眠（阻塞）：客户、服务器父进程和服务器子进程。

在标准输入上输入，得到回射。键入EOF字符（Ctrl+D）以终止客户。
--当我们键入EOF（Ctrl+D）字符时，fgets返回一个空指针，于是str_cli返回。
--当str_cli返回到客户的函数main时，main通过调用exit终止。
--进程终止处理的一部分是关闭所有打开的描述字，所以客户套接字由内核关闭。这导致客户TCP发送一个FIN给服务器，服务器TCP则以ACK响应，这就是TCP连接终止序列的前半部分。
--当服务器TCP接收FIN时，服务器子进程阻塞于readline调用，于是readline返回0，这导致函数str_echo返回服务器子进程的main。
--服务器子进程通过调用exit来终止。
--服务器子进程中打开的所有描述字随之关闭。由于子进程关闭已连接套接口引发TCP连接终止序列的最后两个分节。至此，连接完全终止，客户套接口进入TIME_WAIT状态。
--进程终止处理的另一部分是在服务器子进程终止时，内核给父进程发一个信号SIGCHLD。这在本例中发生了，但我们在代码中未捕获这个信号，而这个信号的缺省动作是忽略的。
现在，子进程的状态是Z（僵尸）。
wait和waitpid函数：
#include<sys/wait.h>
pid_t wait(int *status);/*等待任一子进程终止，返回值为终止子进程的ID，status:指向整数的指针，用来返回子进程的终止状态*/
pid_t waitpid(pid_t pid,int *status,int options);/*等待特定子进程终止，返回值为终止子进程的ID，pid:指定要等待的子进程ID，status:指向整数的指针，用来返回子进程的终止状态，options:选项参数*/
-当父进程调用wait或waitpid函数时，如果有子进程已经终止，内核会立即返回该子进程的ID和终止状态；如果没有子进程已经终止，父进程会被阻塞，直到有子进程终止。
-作用：父进程调用wait或waitpid函数来等待子进程终止，并回收子进程的资源，防止僵尸进程的产生。用于处理SIGCHLD信号的程序。
-wait的阻塞模式：当父进程调用wait函数时，如果没有子进程已经终止，父进程会被阻塞，直到有子进程终止。
-waitpid的非阻塞循环模式：当父进程调用waitpid函数时，如果没有子进程已经终止，父进程会立即返回-1，并设置errno为ECHILD。父进程可以在一个循环中调用waitpid函数来检查是否有子进程已经终止，如果没有则继续执行其他任务。
-SIGCHLD信号的特点：当子进程终止时，内核会给父进程发送一个SIGCHLD信号。父进程可以捕获这个信号来调用wait或waitpid函数来回收子进程的资源，防止僵尸进程的产生。
例：
#include "unp.h"
void sig_chld(int signo)
{
    pid_t pid;
    int stat;
    while((pid = waitpid(-1, &stat, WNOHANG)) > 0)
        printf("child %d terminated\n", pid);/*回收子进程资源，防止僵尸进程的产生,循环防止SIGCHLD合并*/
    return;
}

I/0复用：
-当一个进程需要同时处理多个套接口时，I/O复用是一个非常有用的技术。I/O复用允许一个进程同时监视多个文件描述符，当其中一个或多个文件描述符准备好进行I/O操作时，进程就可以对它们进行处理，这个能力被称为IO复用，是由select、poll和epoll等系统调用提供的。
-IO复用典型网络应用场合：
1.服务器需要同时处理多个客户连接请求
2.服务器需要同时处理多个已连接套接口上的数据传输
3.服务器需要同时处理多个套接口上的连接请求和数据传输
4.服务器需要同时处理多个套接口上的连接请求、数据传输和定时器事件
5.服务器需要同时处理多个套接口上的连接请求、数据传输、定时器事件和信号事件
IO模型：
1.阻塞IO模型：在这种模型中，进程在进行I/O操作时会被阻塞，直到操作完成。这种模型简单易用，但效率较低，因为进程在等待I/O完成时无法执行其他任务。
2.非阻塞IO模型：在这种模型中，进程在进行I/O操作时不会被阻塞，如果I/O操作无法立即完成，系统会返回一个错误（如EWOULDBLOCK），进程可以继续执行其他任务。这种模型提高了效率，但编程复杂度较高。
3.IO复用模型：在这种模型中，进程可以同时监视多个文件描述符，当其中一个或多个文件描述符准备好进行I/O操作时，进程就可以对它们进行处理。这种模型结合了阻塞和非阻塞的优点，提高了效率，同时保持了编程的相对简单。
4.信号驱动IO模型：在这种模型中，进程可以注册一个信号处理函数，当某个文件描述符准备好进行I/O操作时，系统会发送一个信号给进程，触发信号处理函数的执行。这种模型可以实现异步I/O，但编程复杂度较高。
5.异步IO模型：在这种模型中，进程可以发起一个异步I/O操作，系统会在操作完成后通知进程（通过信号、回调函数或其他机制）。这种模型可以实现完全的异步I/O，但编程复杂度较高。
各种IO模型的比较：
1.阻塞IO模型流程：进程发起I/O操作 -> 进程被阻塞 -> I/O操作完成 -> 进程继续执行
2.非阻塞IO模型流程：进程发起I/O操作 -> I/O操作无法立即完成 -> 系统返回错误 -> 进程继续执行其他任务
3.IO复用模型流程：进程监视多个文件描述符 -> 文件描述符准备好进行I/O操作 -> 进程处理准备好的文件描述符
4.信号驱动IO模型流程：进程注册信号处理函数 -> 文件描述符准备好进行I/O操作 -> 系统发送信号 -> 信号处理函数执行
5.异步IO模型流程：进程发起异步I/O操作 -> 系统处理I/O操作 -> I/O操作完成 -> 系统通知进程 -> 进程处理完成的I/O操作
Select函数：
#include<sys/select.h>
#include<sys/time.h>
int select(int nfds, fd_set *readfds, fd_set *writefds, fd_set *exceptfds, struct timeval *timeout);
/*nfds:监视的文件描述符数量，readfds:指向fd_set类型的指针，表示要监视的可读文件描述符集合，writefds:指向fd_set类型的指针，表示要监视的可写文件描述符集合，exceptfds:指向fd_set类型的指针，表示要监视的异常文件描述符集合，timeout:指向timeval结构体的指针，表示等待文件描述符准备好的最长时间*/
struct timeval{
    long tv_sec;/*秒*/
    long tv_usec;/*微秒*/
};
有三种可能：
1.永远等待下去：仅在有一个描述字准备好IO时才会返回，为此，我们将参数timeout置为NULL。
2.等待一段时间：在有一个描述字准备好IO时返回，但不超过由参数timeout指定timeval结构中指定的秒数和微秒数。
3.不等待：立即返回，称之为轮询，为实现这一点，参数timeout必须指向一个timeval结构，并且该结构的tv_sec和tv_usec成员都必须置为0。

select会修改传入的集合，调用 select 前，readset 中保存的是：
我想监听哪些描述符。调用 select 返回后，readset 被修改为：哪些描述符真的已经准备好了。

select 的返回值
返回值 = 已准备好的描述符总数
例如有 3 个描述符被监听，其中 2 个准备好了，那么 select 返回 2。
其他情况：
返回 0：超时，没有任何描述符准备好
返回 -1：出错，例如被信号中断
所以一般代码会这样判断：
nready = select(maxfdp1, &rset, NULL, NULL, NULL);

if (nready < 0) {
    // 出错
} else if (nready == 0) {
    // 超时
} else {
    // 有描述符准备好了
}

基本思想是：
一个服务器进程同时监听：1. 监听套接字：负责接收新连接；2. 已连接套接字：负责处理各个客户端发来的数据。

poll函数：
#include<sys/poll.h>
int poll(struct pollfd *fdarray, unsigned long nfds, int timeout);/*fdarray:指向pollfd结构体数组的指针，nfds:数组中元素的数量，timeout:等待文件描述符准备好的最长时间，单位为毫秒，INFTIM表示无限等待,0表示不等待,>0表示等待指定时间*/
struct pollfd{
    int fd;/*要监视的文件描述符*/
    short events;/*要监视的事件，POLLRDNORM（0x40）表示普通数据可读，POLLWRNORM（0x400）表示普通数据可写，POLLERR（0x800）表示发生错误，POLLHUP（0x1000）表示发生挂断，POLLNVAL（0x2000）表示无效的文件描述符,描述字不是一个打开的文件*/
    short revents;/*返回的事件，由内核设置，表示哪些事件已经准备好*/
};
poll和select的比较：
1.接口设计：poll使用一个结构体数组来监视文件描述符，而select使用一个位图（fd_set）。poll的接口更灵活，可以监视更多的文件描述符，而select受限于FD_SETSIZE。
2.性能：poll在监视大量文件描述符时性能较好，因为它不需要像select那样扫描整个位图来检查哪些文件描述符准备好了。poll只需要扫描结构体数组，效率更高。
3.可移植性：select在许多系统上得到广泛支持，而poll在某些旧系统上可能不被支持。因此，select具有更好的可移植性。
4.功能：poll提供了更多的事件类型，如POLLERR、POLLHUP和POLLNVAL，可以更细粒度地监视文件描述符的状态，而select只能监视可读、可写和异常事件。
epoll函数：
#include<sys/epoll.h>
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);/*epfd:由epoll_create返回的epoll实例的文件描述符，events:指向epoll_event结构体数组的指针，用于返回准备好的事件，maxevents:数组中元素的数量，timeout:等待文件描述符准备好的最长时间，单位为毫秒，-1表示无限等待,0表示不等待,>0表示等待指定时间*/

int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);/*epfd:由epoll_create返回的epoll实例的文件描述符，op:操作类型，EPOLL_CTL_ADD表示添加一个文件描述符，EPOLL_CTL_MOD表示修改一个文件描述符，EPOLL_CTL_DEL表示删除一个文件描述符，fd:要操作的文件描述符，event:指向epoll_event结构体的指针，指定要监视的事件*/
LT和ET模式：
1. LT（Level Triggered）模式：在这种模式下，当一个文件描述符准备好进行I/O操作时，epoll_wait会持续返回该文件描述符，直到应用程序处理完它。这种模式类似于select和poll的行为。
2. ET（Edge Triggered）模式：在这种模式下，当一个文件描述符从未准备好到准备好的状态发生变化时，epoll_wait只会返回该文件描述符一次。应用程序必须在处理完该文件描述符后再次调用epoll_wait来检查它是否仍然准备好。这种模式效率更高，但编程复杂度较高。
epoll和select/poll的比较：
-select：老式方案，用位图，最大 fd 数有限，每次都要全量扫描。
-poll：改进了 select 的 fd 数量限制，用数组保存 fd，但仍然需要全量扫描。
-epoll：Linux 高性能方案，事件提前注册到内核，事件发生后直接返回就绪 fd，不需要每次全量扫描。
-select / poll：应用程序每次问内核：“这些 fd 里面哪些好了？”
-epoll：应用程序先告诉内核：“这些 fd 我关心”，之后内核主动把好了的 fd 返回给你。
-select 和 poll 是轮询式检查，复杂度是 O(N)；
-epoll 是事件驱动式通知，通常只处理就绪事件，更适合 Linux 下的大规模并发网络服务器。

UDP的connect函数：
-TCP 调用 connect 时，会发生真正的连接建立过程，也就是 三次握手。
-但是 UDP 是无连接协议，所以 UDP 调用 connect 时：
--不会发送三次握手报文；
--不会和对方建立真正的连接；
--只是内核记录对方的 IP 地址和端口号。
也就是说，UDP 的 connect 本质上是：在本地套接字中保存一个默认通信对象。
未连接 UDP 套接字和已连接 UDP 套接字：
-未连接 UDP 套接字：unconnected UDP socket，当我们创建UDP套接口时，缺省为此
-已连接 UDP 套接字：connected UDP socket，对UDP套接口调用connect函数的结果
--注意，这里的“已连接”不是 TCP 那种真正连接，而是说该 UDP 套接字已经指定了默认对端地址。
未连接 UDP 套接字怎么发送数据？
-如果 UDP 套接字没有调用 connect，每次发送数据时都必须指定目的 IP 和端口。通常使用：sendto(sockfd, buf, len, 0, (struct sockaddr *)&servaddr, sizeof(servaddr));因为 UDP 没有默认对端，所以每次都要告诉内核：这次数据发给谁？也就是：目的 IP 是什么？目的端口是多少？
已连接 UDP 套接字怎么发送数据？
-如果 UDP 套接字调用了 connect，发送数据时就不需要指定目的 IP 和端口了。可以直接使用：send(sockfd, buf, len, 0);因为 UDP 已经有了默认对端，所以每次发数据时内核就知道：这次数据发给谁？也就是：目的 IP 是什么？目的端口是多少？
已连接 UDP 套接字怎么接收数据？
-未连接 UDP 套接字一般用：
recvfrom(sockfd, buf, len, 0, (struct sockaddr *)&cliaddr, &len);因为它可能收到来自任何主机、任何端口的数据报，所以需要 recvfrom 返回发送方地址。但是已连接 UDP 套接字可以用：read(sockfd, buf, len);或者：recv(sockfd, buf, len, 0);因为它只接收来自 connect 指定对端的数据报。不是指定对端发来的 UDP 数据报，会被内核过滤掉。
UDP connect 后发生的三个变化：
1.发送时不用再指定目的地址
2.接收时只接收指定对端的数据报
3.异步错误会由已连接UDP套接口返回给进程
什么时候可以使用 UDP connect？
-仅在进程用UDP套接口与确定的唯一对方通信时，UDP客户或者服务器才可以调用connect。（所谓的连接）
-给一个UDP套接口多次调用connect，对于已连接UDP套接口来说，进程可给那个套接口再次调用connect以达到下面两个目的之一：
--指定新的IP地址和端口号来替换原来的默认对端地址
--断开套接口（设置套接口地址结构的地址族（为AF_UNSPEC））

getservbyport和getservbyname函数：
#include<netdb.h>
struct servent *getservbyname(const char *name, const char *proto);/*name:服务名称，proto:协议名称，返回值为指向servent结构体的指针，出错返回NULL*/
struct servent{
    char *s_name;/*服务的正式名称*/
    char **s_aliases;/*服务的别名列表，以NULL结尾*/
    int s_port;/*服务端口号，网络字节序*/
    char *s_proto;/*服务使用的协议名称，如"tcp"或"udp"*/
};
struct servent *sptr;
sptr = getservbyname("domain", "udp");
sptr =getservbyname("ftp","tcp");
sptr=getservbyname("ftp",NULL);
sptr = getservbyname("ftp","udp");
